# AI 요청 서비스와 OpenAI 코드 생성

작성: 2026-10-14. AI 계획의 5단계와 첫 제공자 생성 어댑터·작업실 UI를 구현했다. 실제 자격 증명으로 생성·테스트가 성공했는지는 별도 검증 결과로 기록한다. 자동 테스트의 제공자 응답은 대체 응답이다.

## 사용자 흐름

1. 로그인 후 작업실에서 OpenAI 연결과 모델을 선택한다. 목록이 만료됐다면 새로고침한다.
2. 전략 템플릿을 최대 3개 선택하거나 추가 요청을 입력한다. 선택 순서의 가중치는 5·3·1이다. 같은 아이템의 획득·회피를 함께 선택하면 서버가 충돌을 안내한다.
3. `AI 코드 생성`은 새 전체 코드를, `현재 코드 수정`은 요청 시점의 편집 코드 파일 사본을 사용한다. 템플릿 코드 생성은 기존의 외부 호출 없는 기능으로 유지한다.
4. 준비 → 대기 → 생성 → 실행 검사 상태를 표시한다. 코드 내용은 진행 이벤트에 포함하지 않는다.
5. 완료 시 후보 코드·전략 설명·사용 토큰·실행 검사 결과를 표시한다. 검사 실패 후보도 진단과 함께 볼 수 있지만 적용 버튼은 비활성화한다.
6. 적용은 사용자가 직접 호출하며 자동 저장하지 않는다. 요청 이후 문서 이름이나 코드가 바뀌었다면 교체 여부를 확인하고, 적용은 편집기 undo로 되돌릴 수 있다.
7. 새로고침 시 같은 유효 로그인 세션의 요청·후보를 복원한다. 브라우저 sessionStorage에는 요청 ID만 보관한다. 복원 후보는 기존 편집 기준을 복원하지 않으므로 적용 전에 확인한다. 새 문서·불러오기·전략 변경·다음 생성·적용 시 이전 요청을 폐기한다.

코드·요청문이 외부 AI로 전송됨과 API 사용료 가능성을 UI에 표시한다. Google OAuth나 서비스 사용자 이메일·신원·로그인 토큰·API 키를 AI 입력에 넣지 않는다. Claude·Gemini는 연결 확인·모델 조회를 유지하지만 실제 생성 버튼은 아직 지원하지 않는다.

## 구성과 경계

- `src/ai/input.js`: 전략 입력 검증과 공통 규약 구성. 게임 API·규칙 문서, 기준 예제, 실제 `TURN_LIMIT_MS`를 읽는다. 요청별 입력에는 의도·전략 순서·자연어와 수정할 코드만 넣는다.
- `src/ai/request-service.js`: 메모리 요청 메타데이터, 소유자·로그인 세션·연결 리비전·모델 검증, 입력·후보 파일, 큐·만료·취소·구독을 관리한다. 저장소 잠금 안에서 외부 생성이나 코드 검사를 수행하지 않는다.
- `src/ai/openai-generation.js`: 고정된 OpenAI Responses API로 호출한다. JSON schema로 전체 `source`와 한국어 `explanation`을 요청한다. 도구·외부 코드 실행·대화 연결·자동 재시도·다른 제공자로 자동 전환은 사용하지 않는다. `store:false`, `truncation:disabled`를 지정한다. 이 설정이 제공자의 모든 보관 정책을 없앤다는 의미는 아니다.
- `src/runtime/preflight.js`: 기존 별도 검사 프로세스를 재사용하며 취소 신호를 추가했다. 실제 경기의 알고리즘 프로세스를 중단하는 변경은 없다. 구문·사용 제한·미선언 이름 및 샘플 2개×플레이어 4명×호출 3회 검사를 수행한다. 모든 맵·모든 턴의 성공을 보장하지는 않는다.
- `public/ai-scripting.js`: 준비·파일 업로드·시작·SSE·후보 조회·복원·취소. 편집기는 응답 이후에도 자동 변경되지 않는다.

API는 `POST /api/ai/requests`, `PUT /:id/source`, `POST /:id/start`, `GET /:id`, `GET /:id/events`, `GET /:id/source`, `DELETE /:id`로 구성한다. 기존 AI API와 동일하게 로그인·동일 Origin·소유권 검사를 적용한다. 준비 요청 ID를 알더라도 다른 계정·다른 로그인 세션은 상태·SSE·코드에 접근할 수 없다.

SSE는 순번과 현재 상태 스냅샷을 전송한다. 재접속마다 현재 상태를 보내므로 과거 이벤트 로그 전체를 저장하지 않는다. 완료 상태 전달 후 닫고, 연결 실패 시 상태 API로 확인한다. 전체 100개·요청당 5개 구독 제한과 느린 소비자 버퍼 제한을 둔다.

### 실제 진행 정보 표시

OpenAI 호출에 `stream:true`를 지정해 요청 접수·텍스트 증분·완료 이벤트를 받는다. `response.created`/`response.in_progress`는 접수 확인, `response.output_text.delta`는 응답 수신으로 표시한다. 수신량은 구조화된 응답 텍스트의 문자 수이며 코드만의 길이나 토큰 수·완료 퍼센트가 아니다. AI 입력·출력 한도나 프롬프트를 늘리지 않으며 진행 확인용 AI 호출·자동 재시도는 추가하지 않는다.

화면은 요청→응답 수신→코드 검사 단계, 현재 단계의 로딩 표시, 경과 초, 실제 수신 문자 수, 마지막 유효 응답 이후 시간을 표시한다. 첫 응답이 없으면 대기 중으로, 15초 이상 새 유효 응답이 없으면 마지막 응답 시각과 대기 안내로 표시한다. 연결이 끊겼다고 단정하거나 가상의 퍼센트를 만들지 않는다. 경과 시간은 서버 시작/현재 시각을 기준으로 브라우저가 매초 계산한다. 완료·실패·취소·문서 전환 시 타이머를 정리하며 화면 복원에서도 서버 시각과 카운터를 사용한다. 모션 줄이기 설정을 존중한다.

진행 메타데이터는 `phase`, `receivedChars`, `lastResponseAt`과 시작/종료/서버 시각만 추가한다. 서버는 증분을 약 200ms 간격으로 합쳐 전달하고 단계 전환은 즉시 전달한다. 단계나 수신량의 후퇴와 취소 이후의 늦은 진행 이벤트는 무시한다. 중간 코드·추론 원문·외부 응답 본문은 SSE에 넣지 않고, 최종 응답을 해석·검사한 뒤에만 기존 후보 조회 API로 코드를 제공한다.

`src/ai/response-stream.js`는 UTF-8/행 경계가 네트워크 청크와 달라도 이벤트를 파싱한다. 이벤트 4MiB·전체 스트림 16MiB·수신 문자 수 4Mi 제한을 적용한다. 완료 이벤트 없는 EOF, 형식 오류, 스트림 중 실패/거부, 취소는 정상 후보로 처리하지 않는다. 스트림에서 발생한 크레딧/사용 한도 오류에도 기존 안전한 오류 분류를 적용한다. 중간 종료 시 자동으로 다시 생성하지 않으며 재시도는 사용자 액션이다.

## 수명·한도·파일

기본 전체 실행 2개·계정별 실행 1개, 대기 10개·계정별 대기 1개, 입력 준비 20개·계정별 준비 2개다. 보관 후보와 준비·대기·진행 요청을 합쳐 계정별 최대 3개로 제한한다. 입력 준비 수명 2분, 대기 포함 요청 제한 2분, 완료 후보 수명 15분이다. 메타데이터 전체는 1000개로 제한하고 계정별 종료·폐기 메타데이터를 정리한다. 제공자 호출·검사가 실제로 끝나기 전에는 취소·시간 초과 상태라도 실행 슬롯을 반환하지 않는다.

입력 사본·후보는 기본 `data/ai/requests/<pid>-<uuid>.js`에 보관한다. 계정 JSON/DB에는 코드 원문을 넣지 않는다. 입력은 요청 완료·실패·취소 시, 후보는 폐기·만료·로그아웃·연결 변경·서버 종료 시 정리한다. 열린 후보 파일은 조회 핸들이 닫힌 뒤 지운다. 시작 시 종료된 프로세스의 남은 파일을 회수하며 다른 살아 있는 프로세스의 파일은 지우지 않는다. 파일 정리 실패와 PID 재사용 상황은 운영 복구 점검 대상이다.

`AI_MAX_INPUT_BYTES=131072`는 규약과 요청·수정 코드의 합산 UTF-8 바이트 한도다. 제품의 알고리즘 파일 보관 크기 제한이 아니라 AI 전송 정책이다. 코드를 조용히 자르지 않는다. 실제 모델별 토큰 한도는 제공자에서 추가 검증하며, 초과 오류는 별도로 안내한다. 현재 정확한 모델별 토큰 계산·한도 자동 조회는 제공하지 않는다. `AI_MAX_OUTPUT_TOKENS=8192`는 생성/추론 출력 상한이다. 응답이 출력 한도에서 잘리거나 거부·형식 오류가 발생하면 성공 후보로 처리하지 않는다. 스트리밍 이벤트는 4MiB·전체 전송은 16MiB에서 차단하고 비스트리밍 오류 응답은 4MiB로 제한한다.

임시 연결은 서버 메모리에 있으므로 재시작 후 키를 화면에서 다시 등록해야 한다. 영구 키 설정을 사용자의 동의 없이 활성화하지 않는다. 로컬 서버도 Google/OpenAI에 외부 접속 가능한 환경에서 실행해야 한다.

## 검증·후속

### 2026-10-14 실제 생성 결과 확인

사용자가 API 크레딧 충전 후 작업실에서 실제 OpenAI 코드 생성에 성공했고, `실행 검사 통과 · 사용 토큰 3539`와 반환된 코드·전략 설명을 제공했다. 모델 ID와 입력/출력 토큰 분리값은 제공되지 않아 정확한 비용은 계산하지 않았다. API 성공은 사용자 화면 보고로 확인하고, 아래 실행 검증은 전달받은 코드를 그대로 사용해 별도로 수행했다. 추가 외부 API 호출은 하지 않았다.

코드는 매 턴 myPosition에서 BFS로 벽을 제외한 최단 경로의 첫 방향을 반환한다. 동일 크기 맵에서 typed array 탐색 버퍼를 재사용하고, 코인이 없거나 도달하지 못하면 -1을 반환한다. 단일 파일·동기 실행·필수 메서드·방향 반환 규약을 따른다. 고액 코인 우선이나 아이템 목표 선택은 포함하지 않는다.

공통 검사 24회 호출을 통과했다. 실제 Match/플레이어 자식 프로세스로 샘플 2개를 단독 플레이했다. 테스트 시간 단축을 위해 액션 50ms, HurryUp 시작 60초, 아이템 최초 출현 60초로 설정하고 테스트 중 아이템·HurryUp이 개입하지 않게 했다. 운영 맵 파일은 변경하지 않았다.

| --- | --- | ---: | ---: | ---: |
| 교차로 12×10 | 모든 코인 수집 | 2840 / 2840 | 102 | 약 0.19ms |
| 네 개의 안뜰 20×16 | 모든 코인 수집 | 7200 / 7200 | 280 | 약 0.30ms |

두 경기 모두 벽 충돌·패널티·시간 초과·예외·잘못된 반환은 0회였다. 경쟁/아이템/랜덤 기믹 조건의 전략 성능이나 모든 입력에서의 성공을 보장하는 검증은 아니다. 전달된 코드와 실행 보고서는 Git에서 제외된 `artifacts/ai-live-nearest-coin.js`, `artifacts/ai-live-nearest-coin-report.json`에 보관했다. 실제 AI 수정 호출·사용자 화면의 테스트/저장까지 완료했는지는 별도 확인이 남아 있다.

OpenAI의 HTTP 429를 전부 요청 과다로 취급하지 않는다. 선불 크레딧 소진, 프로젝트/조직 지출 한도, 조직 사용 한도, 요청·토큰 처리 한도, 이전 `insufficient_quota`, 확인되지 않은 제한을 구분한다. 서버 자체의 작업 한도도 별도로 표시한다. 분류에는 알려진 `error.code`/`error.type`만 사용하고 외부 원문 메시지는 전달하지 않는다. `AI_DIAGNOSTICS=true`로 시작한 로컬 서버는 정규화된 오류 분류·발생 영역·허용된 제공자 코드만 로그에 출력하며 키·사용자 식별자·요청문·코드는 출력하지 않는다. 기본은 비활성이다. 근거: [OpenAI 오류 코드](https://developers.openai.com/api/docs/guides/error-codes).

전체 자동 테스트 167개를 통과했다. 생성 테스트는 공통 입력·고정 호출 경로·구조화 결과·원문 비밀 비노출·잘림/거부·과도한 입력·실제 실행 검사·소유권·파일 사본·취소 뒤 슬롯·시간 초과·로그아웃·중복 시작·만료를 검증한다. HTTP 검사에는 SSE와 후보 다운로드를 포함한다. 확장한 AI 브라우저 검사는 실제 검사와 생성·수정·명시적 적용·undo·새로고침 복원·검사 실패·취소 뒤 늦은 응답을 검증하며 외부 AI 응답만 대체한다.

후속은 실제 사용자 연결로 생성·수정·플레이 검증, Claude·Gemini 생성 어댑터, 실제 모델 한도·배포 네트워크·부하 검증이다. 개인정보 운영 준비는 배포 전 마지막 필수 단계로 유지한다. 자동 수정 반복이나 자동 경기 실행은 추가하지 않았다.

공식 구현 근거: [OpenAI 텍스트 생성](https://developers.openai.com/api/docs/guides/text), [구조화된 출력](https://developers.openai.com/api/docs/guides/structured-outputs), [스트리밍 응답](https://developers.openai.com/api/docs/guides/streaming-responses). Responses API는 최종 응답 배열의 assistant message에서 output_text를 수집하며 reasoning 항목을 코드로 취급하지 않는다.
