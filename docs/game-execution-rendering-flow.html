브라우저 렌더링 전체 흐름

운영 BE · 게임 엔진 · 알고리즘 실행기 · 전량 로그를 분리한 목표 설계

전체 구성도 서비스별 기능 배치실행 단계시퀀스 차트화면과 기록장애·미구현 범위
목표 구조 문서입니다. 현재는 통합 Node.js 서버와 참가자별 알고리즘 프로세스 구조입니다. C# 운영 BE·실행 관리자·게임별 엔진 프로세스·전량 수집은 아직 구현 전입니다. 이 HTML은 외부 스크립트/폰트/CDN 없이 세 SVG 차트를 포함합니다.

1. 전체 구성도

브라우저는 하나의 공개 주소로 접속합니다. 운영 BE는 C#, 게임 엔진은 Node.js를 유지하고 실행 관리자가 경기마다 독립 프로세스를 만듭니다. 수집기는 저장 구현과 분리된 계약을 사용합니다.

1.1 서비스별 기능 배치

게임마다 새 Node.js 프로세스를 생성합니다. 상주 게임 실행 관리 서비스가 각 게임의 준비 시점에 프로세스를 만들고, 그 안에서 같은 게임 엔진 프로그램의 독립 인스턴스를 실행합니다. 한 게임 안에서는 매 턴 이 프로세스를 재생성하지 않으며 종료/실패 처리 후 정리합니다.

각 서비스 안에 어떤 기능이 들어가고, 웹서버·상주 서비스·경기별 프로세스·내부 모듈 중 어떤 형태로 실행되는지 표시합니다. 큰 박스는 별도 호스트/컨테이너를 의미하지 않습니다. 실행 관리자는 엔진과 별도 상주 서비스로 두는 권장안입니다.

브라우저에는 렌더러·애니메이션·편집/관리 UI·상태 수신이 위치합니다. 기능의 실행 형태와 수명을 구분한 상세 표는 Markdown 문서에 보관합니다. Node.js 엔진과 실행 관리자 모두 현재 구현 전인 목표 구조입니다.

2. 화면이 그려지기까지

실제 계산 성능이 승부에 반영되는 독립 턴을 유지합니다. 계산 결과가 준비되면 해당 플레이어의 액션을 시작하고, 액션이 끝나면 같은 인스턴스의 다음 계산을 요청합니다. 공통 판단 지연·다른 플레이어의 결과 대기·계산 시간을 없애는 논리 시간 보정은 적용하지 않습니다. 호출 인프라 비용은 별도로 최소화·검증하며 실행기 추상화·독립 실행 작업 계획에 단계별 작업과 완료 기준을 보관했습니다. 실행기 직접 호스팅/IPC의 최종 선택은 검증 후 확정합니다.

01 페이지·에셋 로드

FE가 HTML·JS·CSS·캐릭터/코인/아이템 이미지를 제공합니다. 브라우저는 렌더링 코드를 준비하고 실제 맵과 참가자 상태는 서버에서 받습니다.

02 경기 요청·프로세스 준비

운영 BE가 권한을 확인하고 코드·맵·옵션을 고정합니다. 실행 관리자가 게임 엔진을 만들고 엔진은 참가자 실행기를 준비합니다. 기록 세션은 준비 실패부터 수집합니다.

03 초기 상태·카운트다운

ready 이후 초기 전체 상태와 시작 기준을 전달합니다. 경기 ID로 SSE를 구독하고 자산/화면 준비와 서버 시작 시점을 맞춥니다. 응답과 구독 사이에는 최신 상태로 동기화합니다.

04 독립 턴·실제 판정

실행기가 방향·상태·소요 시간을 반환합니다. 엔진이 이동/충돌/망치/점프와 실제 액션 완료·점수·효과를 확정합니다. 점프는 알고리즘 호출을 생략하고 실제 목적지를 기록합니다.

05 상태 전달·프레임 보간

엔진 → 관리자 → 운영 BE → FE → 브라우저로 상태를 전달합니다. 브라우저는 출발/목표·서버 액션 시간으로 이동을 보간하고 이미지·이펙트를 표시합니다. 점수는 서버 확정값을 따릅니다.

06 게임오버·완결·정리

최종 상태로 약 3초 게임오버 후 포디엄을 표시합니다. 실행기 종료·로그 내구/완결 확인·결과 요약 반영을 별도로 수행하고 엔진을 정리합니다. 실패는 미완결/미반영 상태로 구분합니다.

브라우저에 영상 프레임을 보내는 방식이 아닙니다. 예를 들어 서버가 400ms 이동을 지정하면 브라우저가 중간 위치를 그립니다. 상태 전송의 전체 snapshot/변경분 방식과 주기는 부하 검증 후 결정하며, 지연 메시지 때문에 액션 시간을 매번 처음부터 다시 시작하지 않습니다.

3. 시간순 시퀀스 차트

페이지 로드부터 경기 준비·독립 턴·렌더링·종료까지의 논리 순서입니다. 액션 시작과 완료는 서로 다른 시점이며, 종료 화면 표시와 기록/DB 완료도 구분합니다.

4. 화면 스트림과 실행 원본

구분 화면용 SSE 실행 원본 저널
목적 현재 상태를 지연 적게 표시 모든 턴·액션·맵 변화·실제 랜덤 결과 보관
순번 화면 전용 sequence 경기 전역 seq·플레이어 turnId·호출 ID
지연/포화 최신 상태로 병합·재동기화. 손실 불가 제어 메시지는 별도 처리 조용한 드롭 금지. 제한된 큐·오류 통지·명시적 실행 정책
재연결 권한 확인 후 최신 전체 상태로 복원 브라우저 연결과 무관하게 수집
완료 의미 화면 표시 수신 접수와 내구 확인·완결 receipt를 구분

운영 DB에는 계정·알고리즘 메타데이터·맵·결과 요약/기록 참조를 보관합니다. 알고리즘 원문/경기 사본은 파일로 유지하고 모든 실행 이벤트를 운영 사용자 문서에 누적하지 않습니다.

5. 장애와 아직 남은 결정

  • 연결 단절: 같은 경기의 최신 상태로 재구독합니다. SSE 단절이나 FE 재시작 자체가 경기 종료/재생성 명령은 아닙니다.
  • 엔진 실패: 관리자가 해당 경기 실패를 기록하고 남은 실행기/연결/임시 파일을 정리합니다. 자동으로 처음부터 재경기하지 않습니다.
  • 시간 초과: 알고리즘 500ms는 해당 호출만 중단합니다. 경기 동안 같은 프로세스/인스턴스를 유지하며 저장/전송 대기를 알고리즘 시간으로 계산하지 않습니다.
  • 공유 자원: 경기별 프로세스로 이벤트 루프/메모리를 분리해도 호스트 CPU·메모리·디스크 경합은 남습니다. 자원 한도·동시 경기 수·종료 기한을 검증해야 합니다.
  • 다국어: 현재 JavaScript/QuickJS만 구현되어 있습니다. C#/C++/Python은 중단 후 동일 인스턴스 재호출 등을 통과한 실행기를 후속 연결합니다.
  • 재시작과 내구성: 운영 BE/관리자 재기동 시 매핑·미반영 결과·자식 프로세스 복구 정책이 필요합니다. 비동기 버퍼만으로 호스트 장애까지 무손실을 보장하지 않습니다.

구체 내부 프로토콜·관리/수집 프로세스 배치·화면 전송 주기·내구 수준·운영 주소/TLS/VPN·DB 제품과 위치는 구현/배포 단계에서 확정합니다.
