# 남은 구현·배포 작업

- 정리일: 2026-11-20.
- 기준 커밋: `8b626ba` — C4-C/D 리뷰의 게임 자원 범위·검사 시도 순서·파일 정리 문제 3건 수정.
- 이 문서는 현재 상태의 요약이다. 과거 계획의 미착수 문구와 충돌하면 최신 구현 결과와 이 문서를 우선한다.
- 현재 공개 지원 언어는 **JavaScript**다. C#은 내부 opt-in 후보이며 공개 저장·플레이·UI 지원을 활성화하지 않았다.
- 후속 구현: [직접 호출·프로필 v3·운영 준비](csharp-readiness-2026-11-19.md). 로컬 호출 비용 비교와 debug/진단·초기 운영 정책을 구현했다. 실제 Linux 격리·메모리 압박/운영 부하 채택 판정과 공개 제품 연결은 남아 있다.
- GC 후속: [누적 할당 guard·GC 구간/실제 DLL 호스트 후보](csharp-gc-window-candidate-2026-11-20.md)를 검증했다. 500ms 선점 보장과 기본 정책 채택은 미완료이며 전체 할당 경로·혼합 게임 메모리 admission/부하를 더 확인한다.
- 최신 GC 후속: [프로필 v4 사전 할당·호스트 감시·게임 단위 admission](csharp-allocation-admission-2026-11-20.md)을 구현했다. 내부 scope/동시 실행 시험까지이며 실제 Node 경기/기록 계약·사양별 자원 정책·장시간 부하와 최종 채택은 남아 있다.
- 최신 실제 게임 후속: [Node 게임 GC 연결·실행 정책·동시 부하](csharp-gc-actual-games-2026-11-20.md)를 수행했다. 실제 게임/전량 로그/최종 결과 연결과 오류별 재사용 정책을 구현했다. 180초 목표의 두 게임 부하는 약 97초·8,714턴에서 GC 예약 실패로 종료됐으므로 GC 기본 채택은 거절한다. 짧은 CPU 상한 시험의 통과로 이를 해결 완료로 취급하지 않는다.
- 최신 복구 후보: [GC 진입 압축·메모리 반환 v2](csharp-gc-entry-recovery-2026-11-20.md)는 같은 메모리 한도의 반복 10,000회와 실제 두 게임 180초 목표를 통과했다. 로컬 반복 예약 문제는 보완했지만 기본값/공개 지원은 계속 비활성이다. 운영 장시간·사양별 부하와 엄격한 정지/native 경계·Linux 격리 채택 관문은 남아 있다.
- 관련: [진행 기록](progress.md), [실행기 공통·언어별 계획](restricted-language-runners-plan.md), [BE 분리 결과](backend-split-completion.md).

## 2. 다음 우선순위 — C# 채택 관문 마무리

C4-D 후속으로 턴 직접 IPC·동일 BFS 비교, debug/문자열 제한·운영 감시/캐시 정책과 실제 GC 게임/기록 연결을 구현했다. [최신 GC 진입 복구](csharp-gc-entry-recovery-2026-11-20.md)를 기준으로 남은 채택 관문을 진행한다. 로컬 반복 예약 실패를 보완했으며 다음 핵심은 실제 배포 사양·긴 부하/장애와 Linux 격리 및 엄격한 정지 경계의 판정이다. 정식 지원 판정을 마친 상태는 아니다.

| 순서 | 남은 작업                      | 현재 상태와 완료 기준                                                                                                                                                                             |
| ---- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 호출 비용의 운영 환경 재측정   | 직접 IPC·같은 BFS·위치 교환과 최대 맵/실제 2게임 부하를 로컬 검증했다. 배포 환경의 동시 경기·CPU 배치와 잔여 호출 비용은 재측정한다.                                                              |
| 2    | 중단 안전성·허용 API 최종 판정 | timeout/잘못된 방향 재사용, 예외·operation-limit/GC 실패 종료와 로컬 반복 예약의 v2 복구를 검증했다. 기본 활성화는 보류하며 엄격한 500ms 정지/native 경계·추가 허용 API와 배포 부하 판정이 남는다. |
| 3    | 진단·운영 모니터링 보완        | Debug.Print·타입/guard 위치 진단·내부 종료 통계는 구현했다. 실제 배포의 지표/경보·보유 정책과 호스트 장애의 운영 대응을 검증한다.                                                                 |
| 4    | Linux·운영 격리                | 인수 코드/계층 자원 검사는 작성했으나 Linux 실행 환경이 없어 미실측이다. cgroup 위임·부모 장애/회수, 파일/네트워크 격리·비관리자·외부 감독을 실제 환경에서 검증한다.                              |
| 5    | 캐시·자원·부하 정책 승인       | 디스크 여유 보호와 최근 접근/lease 기반 캐시 정리·dry-run은 구현했다. 계정 삭제/보유·도구 버전 전환·혼합 경기 자원·백업/복구·부하/장애와 재리뷰를 완료한다.                                       |
| 6    | 공개 제품 연결                 | 채택 관문 통과 후 계정 C# 저장·경기/이전 경기 snapshot·capability와 언어 선택·에디터·샘플·규약 안내를 연결한다. 현재 미구현/비활성이며 프롬프트 고도화 범위는 별도로 확정한다.                    |

계산 완료 즉시 액션, 액션 완료 즉시 다음 계산을 유지한다. 빠른 계산이 승부에 반영되어야 하므로 고정 대기·공통 판단 라운드·논리 시간 보정으로 호출 비용을 숨기지 않는다. 매 턴 컴파일하거나 정상 시간 초과마다 프로세스를 재시작하지 않는다.

## 3. 이후 언어 지원 — Python → C++

두 언어는 계획만 있으며 실제 지원 구현은 아직 시작하지 않았다. C#에서 검증한 준비/검사/저장/게임/자원 계약을 재사용하되 중단·동일 인스턴스 재사용은 각 런타임에서 별도로 입증한다.

| 순서   | 후보와 실제 작업                                                                                                                                                                                                                            |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Python | AST 규약 검사·승인 API, 제한된 CPython 호스트·자동 예산 검사, native 연산/큰 정수/GC 경계 검증. 격리 준비·지속 인스턴스·preflight·계정/게임 어댑터·진단/자원 제한을 연결한다. sys.settrace만으로 중단 보장을 완료한 것으로 취급하지 않는다. |
| C++    | Clang 규약 검사·격리 컴파일과 WASI/Wasmtime 후보 검증. 예외·RAII 정리 및 중단 후 상태 재사용을 확인하고 공통 어댑터에 연결한다. 원시 Wasm trap만으로 안전한 인스턴스 재사용을 보장하지 않는다.                                              |

공통 작성 규약은 단일 파일·허용 built-in·사용자 정적 상태/비동기·병렬·sleep·네트워크·try/catch 금지 등을 기준으로 한다. 정적 검사와 여러 실제 테스트 호출은 규약 준수의 일부를 검증하며, 모든 입력의 종료나 500ms 이내 실행을 증명하는 검사가 아니다.

## 4. JavaScript 후속 보완

- alias/간접 호출과 승인 API 프로필의 미완료 분석 범위 보완.
- 깊은 재귀 등 낮은 수준 오류의 진단 분류 보완.
- 레거시 다중 프로세스 계정 파일 잠금 EPERM의 간헐 실패 원인과 유지/이관 범위 정리. 이전 300건 회귀에서 EPERM 1건이 재현됐고 해당 파일 독립 재검사는 9건 통과했다. 최신 회귀는 301건 모두 통과했지만 이번 C# 작업에서 잠금 문제를 수정하지 않았으므로 해결 완료로 표시하지 않는다.

저장/검사 상태 연결(J2), 검사 포화·복구·동시 게임(J3)은 완료했다. [JS 검사](javascript-preflight-v2.md), [저장/실행 허가](algorithm-validation-storage.md), [J3 결과](validation-lifecycle-j3-results.md)를 참고한다.

## 7. 보류·제거 상태 유지

프롬프트 분량 축소 1~4단계와 현재 생성/복사·검사 진단은 마감했다. 아래는 미완료인 채 보류하며 일반적인 계속 진행 요청으로 자동 재개하지 않는다.

- 5단계의 실제 외부 AI 출력·대화 문맥 유지 비교 평가.
- 검사 오류/원문을 묶는 수정 프롬프트와 테스트 결과 기반 전략 개선 프롬프트.
- 기타 프롬프트 UI·전략 템플릿·출력 품질 고도화.

직접 AI API 연결, 별도 AI 응답 가져오기 모달, 로컬 템플릿 코드 생성은 제거 상태를 유지한다. 외부 AI 응답은 편집기에 직접 붙여 넣어 검사·테스트·저장한다. .NET 운영 BE 전환과 별개로 게임 엔진은 Node.js를 유지하며 엔진의 .NET 재작성은 현재 범위에 넣지 않는다.
