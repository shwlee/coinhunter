# BE 분리 구현 단계별 작업 계획

- 작성일: 2026-11-15
- 상태: 작업 계획 생성. 단계 1~9의 구현은 아직 시작하지 않았다.
- 최신 순서: 사용자 결정에 따라 **BE 분리를 먼저** 진행한다. FE의 독립 제공/배포 작업은 후속이며 기존 화면 연결에 필요한 최소 중계만 이번 통합 단계에 포함한다.
- 기준: [책임 경계](game-backend-boundaries.md), [전체 흐름·차트](game-execution-rendering-flow.md), [실행기 독립성](algorithm-runner-independence-plan.md), [저장 계약](storage-adapters.md), [로그 수집 계약](game-log-collection-modules.md).
- 우선 적용: 이 문서의 닷넷 운영/실행 관리 서비스와 BE 우선 순서를 이전 단일 Node BE/FE 우선 계획보다 우선한다. 개인정보 운영 준비는 실서비스 개시 전 마지막 필수 단계로 유지한다.

## 1. 목표 구조와 이번 범위

```text
기존 브라우저 화면 / 후속 FE 웹서버
  → 게임 운영 서비스: C# / ASP.NET Core
      ├─ 인증·계정·권한·알고리즘·맵·관리자·경기 조회
      ├─ 운영 저장 인터페이스 → 첫 단계 파일 어댑터
      ├─ 알고리즘 원문·경기 사본 파일
      └─ 게임 실행 관리 서비스: C# / 독립 상주 프로세스
          ├─ 수락·준비·생성·감시·중단·정리·상태/결과 전달
          └─ 게임별 Node.js 엔진 프로세스
              └─ 플레이어별 추상 실행 계약 → 기존 JS/QuickJS 구현

게임 엔진 → 독립 로그 수집 모듈/저장 어댑터 → 실행 저널·실행 기록 목록
```

- 운영 서비스와 실행 관리 서비스는 독립 진입점/프로세스로 구현한다. 호스트/컨테이너 수와 실제 네트워크 배치는 이 문서에서 고정하지 않는다.
- 게임별 엔진 프로세스로 격리하되 첫 구현은 기존 Node 게임 규칙과 JS 실행기를 재사용한다. 참가자별 프로세스 방식은 첫 호환 구현이며 향후 직접 호스팅/IPC의 최종 선택과 구분한다.
- 실질적인 다국어 구현, 게임 엔진의 C# 포팅, DB 제품 채택/전환, 신규 대회/공유 기능, 프롬프트 고도화는 이번 분리 범위에 넣지 않는다.
- 전량 실행 로그는 독립 모듈로 연결한다. 별도 네트워크 수집 서버가 필수는 아니며 저장 구현과 실행 배치는 수집 계약 뒤에서 선택한다.
- 공개 API 경로·화면 기능·기존 사용자/알고리즘/맵 ID·원문 파일 보관을 유지한다. 초기 관리자 개인 정보나 비밀 설정을 소스에 추가하지 않는다.

## 2. 반드시 유지할 실행/데이터 계약

1. **독립 턴:** 계산 완료 즉시 해당 액션 시작, 액션 완료 즉시 같은 인스턴스의 다음 판단. 다른 참가자 결과를 기다리거나 공통 판단 지연·논리 시간 보정으로 성능 차이를 없애지 않는다.
2. **호출 제어:** 플레이어별 호출 비중첩, 턴별 500ms 실제 중단, 해당 턴 -1 패널티, 경기 동안 같은 인스턴스/실행 호스트 유지. 정상 timeout 때 프로세스를 재생성하지 않는다.
3. **호출 경로:** 게임 중 알고리즘 호출은 엔진과 실행기 사이에서 완결한다. 운영 API·실행 관리자·운영 DB와 매 턴 왕복하도록 결합하지 않는다. 화면 중계 지연이 게임 판정 시계를 결정하지 않는다.
4. **업무 데이터:** 운영 서비스만 운영 저장소를 수정한다. 기존 Node 운영 코드/유지보수 명령과 새 C# 코드가 같은 파일에 동시에 쓰지 않는다.
5. **원문:** 파일로 보관하고 준비된 경기에는 불변 사본/참조를 전달한다. 운영 메타데이터·실행 요청·로그 본문에 원문 전체를 중복 영구 저장하지 않는다.
6. **인증/권한:** 사용자/게스트 식별과 최종 인가는 운영 BE가 담당한다. 실행 호스트가 브라우저 쿠키를 검증하거나 이메일로 계정을 자동 병합하지 않는다.
7. **결과:** 엔진 판정 결과·로그 완결·운영 요약 반영은 별도 상태다. 완료 전달은 중복/재시도를 허용하는 멱등 계약으로 만든다.
8. **설정/자원:** FE에는 공개/연결 설정만, 운영 BE에는 OAuth/저장 비밀, 실행 영역에는 필요한 실행/기록 권한만 전달한다. 실제 데이터/키로 자동 검사를 수행하지 않는다.

## 3. 프로젝트·계약 배치 초안

```text
backend/
  CoinHunter.sln
  src/
    CoinHunter.Operations.Api/     Controllers·업무 서비스·인증
    CoinHunter.Execution.Host/     내부 API·프로세스 수명·상태 중계
    CoinHunter.Contracts/          공개/내부 DTO·상태·오류·버전
    CoinHunter.Infrastructure/     운영 파일 저장·원문·프로세스/수집 어댑터
  tests/                          계약·API·프로세스·통합 검증

src/game/                          기존 Node 게임 규칙 재사용
src/runtime/                       기존 JS/QuickJS 어댑터 재사용
src/execution/                     신규 게임 호스트 진입점/메시지 어댑터 후보
```

경로/세부 클래스는 단계 1에서 확정한다. API는 Controller → 업무 서비스 → 저장/실행 인터페이스로 추적할 수 있게 하고 SDK/DB 타입을 공통 DTO에 노출하지 않는다. 공유 Contracts는 언어 중립 JSON/enum 규격과 대응시키며 Node가 .NET 어셈블리를 직접 참조해야 한다는 의미가 아니다.

신규 닷넷은 .NET 10 LTS를 기준으로 설치된 SDK와 패키지 호환성을 확인해 버전을 고정한다. 기존 Node의 배포용 지원 버전/QuickJS 호환성도 확인하되 전역 런타임이나 사용자 설정을 계획 단계에서 변경하지 않는다.

## 4. 단계 요약과 의존성

| 단계 | 작업                                | 선행       | 종료 시 확인 가능한 결과                                     |
| ---- | ----------------------------------- | ---------- | ------------------------------------------------------------ |
| 1    | API/메시지 계약·닷넷 솔루션 뼈대    | 없음       | 두 호스트가 독립 기동, 설정/상태 점검·계약 목록 확인         |
| 2    | 운영 파일 저장·원문 어댑터          | 1          | 격리된 시험 데이터로 기존 ID/소유권/수정 충돌·파일 참조 검증 |
| 3    | 인증·세션·관리자 사용자 이전        | 2          | 새 API의 로그인·권한·차단·관리자 유지보수 검증               |
| 4    | 실행 관리 서비스·게임별 Node 호스트 | 1          | 내부 요청으로 엔진 생성/준비/실행/중단·JS 검사 가능          |
| 5    | 알고리즘·맵·기록·규약 운영 API 이전 | 2, 3, 4    | 작업실/관리자 데이터 API를 새 운영 서비스로 검증             |
| 6    | 경기 API·SSE·결과 요약 통합         | 4, 5       | 새 운영 API를 통해 게스트/계정 경기 생성·구독·종료·기록 확인 |
| 7    | 독립 전량 로그 수집 연결            | 4, 6       | 원본 턴/기믹/종료 기록·완결/복구·조회 권한 검증              |
| 8    | 기존 화면 연결·호환 중계            | 3, 5, 6, 7 | 기존 화면을 단일 공개 주소에서 새 BE로 사용                  |
| 9    | 통합/장애/부하 리뷰·안전한 전환     | 1~8        | 실행/검증/백업/복귀 문서와 새 기본 BE 경로                   |

설명/검토 순서는 1→2→3→4→5→6→7→8→9다. 4단계는 계약이 고정되면 저장/인증과 독립적으로 개발할 수 있지만 사용자 검토를 위한 단계 순서는 유지한다. 각 단계는 완료 범위·검증·한계·리뷰 결과를 보고할 수 있는 단위로 나눈다. 문서 생성만으로 단계 완료나 기능 검증을 표시하지 않는다.

## 5. 단계별 상세 작업

### 단계 1 — 계약 확정과 닷넷 솔루션 뼈대

- 현재 경로·메서드·JSON 필드/날짜/enum·HTTP 상태·쿠키·SSE 이벤트·다운로드·업로드를 목록화한다. 작업실의 코드 검사와 prompt contract도 포함하고 제거된 `/api/ai`는 410 동작을 유지한다.
- 운영/실행 관리의 프로젝트·진입점·DI·설정 검사·정상 종료·자체 health/readiness를 구성한다. 기존 서버와 충돌하지 않는 로컬 포트에서 기동한다.
- 실행 요청·준비/실행 상태·화면 snapshot·최종 결과·기록 참조·오류의 버전 있는 DTO와 중복 요청 ID를 정의한다.
- 운영 BE↔관리자 내부 API, 관리자↔Node 엔진의 프로세스 메시지 계약을 고정한다. 1차 엔진 채널은 표준 입출력의 프레임 있는 JSON 메시지를 후보로 검증하며 이것을 플레이어별 알고리즘 IPC의 최종 선택과 혼동하지 않는다.
- 요청/결과 ID·프레임 경계/크기·취소/종료·느린 수신자·프로토콜 버전 거부를 명시한다. 코드 원문은 메시지에 통째로 넣지 않고 신뢰된 불변 파일 참조로 전달한다.
- 공개 URL·내부 수신 주소·신뢰 프록시·내부 서비스 인증·게스트/사용자 범위 전달 계약을 정한다. 브라우저가 직접 내부 실행 API를 호출할 수 없도록 구성한다.
- **완료 기준:** 새 솔루션 빌드/테스트·두 호스트 기동/종료·설정 실패 검증, API/메시지 계약 문서와 다음 단계 구현 경계. 기존 기본 실행·실제 데이터는 변경하지 않는다.

### 단계 2 — 운영 파일 저장과 코드 원문 보관

- 계정/신원·알고리즘·경기 요약·맵 저장 인터페이스와 C# 파일 구현을 추가한다. 기존 메타데이터/맵 버전/registry·UUID·sourceKey의 호환 범위와 필요한 이전 버전을 명시한다.
- 소유권·원자적 갱신·revision 409·Google 신원 유일성·마지막 관리자 보호를 기존 계약과 대조한다.
- 원문 스트리밍·불변 새 파일 저장·참조 갱신·활성 읽기 lease·경기 사본·실패 정리/미참조 대조를 구현한다. 제품 코드 크기 제한 없음과 디스크/동시 업로드 보호를 유지한다.
- 새 C# 유지보수 명령도 같은 저장 계약을 사용한다. Node와 C#을 동시에 운영 데이터 작성자로 사용하지 않는다. 초기에는 서로 다른 시험 디렉터리만 사용한다.
- 맵 파일 유지와 DB 후보 검토는 분리한다. DB 어댑터를 이번 단계에 필수로 설치하지 않는다.
- **완료 기준:** 임시 데이터의 교차 조회·동시 수정/권한·원문 참조/복사·중단 후 대조 계약 검사. 실제 사용자 파일을 자동 이전하지 않는다.

### 단계 3 — 인증·세션·관리자 사용자 관리

- Google 로그인 시작/콜백·로그아웃·현재 세션·역할/활성 상태와 관리자 사용자 API를 이전한다. 표준 .NET 인증 구성요소를 검토하되 기존 외부 API·내부 사용자 ID와 신원 연결 규칙을 유지한다.
- state·브라우저 결합·nonce/PKCE 등 현재 인증 검증·콜백 오류·중복/만료 요청·계정 차단을 동등하게 확인한다. 이메일 자동 병합과 개인 관리자 하드코딩을 추가하지 않는다.
- 세션 발급자는 운영 BE 하나로 정하고 Node/FE와 메모리 세션을 공유한다고 가정하지 않는다. 서버 재시작 후 재로그인 정책과 포팅 전 세션의 재로그인 필요성을 명시한다.
- 공개 URL 기준 Host/Origin·쿠키 Secure/SameSite·신뢰 프록시/클라이언트 주소·요청 제한을 구현한다.
- 부트스트랩/승격 명령을 새 운영 저장 계약에 연결하고 기존 Node 명령과의 전환법을 문서화한다. 이 경로를 비인증 HTTP 관리 기능으로 노출하지 않는다.
- **완료 기준:** 격리된 테스트 OAuth 응답으로 성공/실패/차단/권한 회귀 검증. 실제 Google 왕복은 설정 후 최종 배포 확인 항목으로 남기며 자동 검증에서 실제 키/계정을 읽지 않는다.

### 단계 4 — 실행 관리와 게임별 Node 엔진 호스트

- 기존 Match/GameState를 HTTP 서버에서 독립 실행할 수 있는 Node 호스트 진입점으로 감싼다. 엔진은 운영 저장소를 열거나 계정/권한을 재판정하지 않는다.
- C# 실행 관리 서비스에 수락 한도·엔진 생성·초기 설정·ready·시작·중단·상태 전달·종료 감시를 구현한다. 명령 인자는 셸 문자열 조립 없이 전달하고 프로토콜/진단 출력을 구분한다.
- 게임별 불변 맵/옵션·참가자 코드 사본/읽기 권한·시작 위치/캐릭터를 전달하고 수명 동안 유지한다.
- [실행기 계획](algorithm-runner-independence-plan.md)의 현재 JS 인터페이스/생성 주입을 적용한다. 독립 판단·같은 객체 재사용·500ms 동작을 유지하고 초기화 실패 때 생성한 모든 실행기를 정리한다.
- 코드 검사는 기존 preflight를 별도 요청/세션으로 연결한다. 준비/검사 동시 한도와 취소를 경기 실행 수명과 구분한다.
- 운영자가 게임을 종료하거나 엔진이 실패한 경우의 자식 프로세스 트리·미응답·임시 파일 정리와 종료 기한을 구현한다. 게임 전체 종료/장애 정리를 정상 턴 timeout 처리로 사용하지 않는다.
- **완료 기준:** 내부 API로 실제 JS 게임을 생성/준비/실행/중단 가능. 복수 게임 엔진 PID 분리, 느린 참가자 독립 진행, 정상→timeout→정상 같은 인스턴스, 엔진 장애 후 잔류 자원 정리 검증.

### 단계 5 — 알고리즘·맵·기록·규약 운영 API

- 알고리즘 목록/저장/덮어쓰기/새 이름·원문 스트리밍·코드 검사·검사 진단을 이전한다. 원문 파일과 HTTP 상태/응답 호환을 유지한다.
- 관리자 맵 제작·버전 저장·게시/숨김·옵션·표시 순서·복제/이름 중복·JSON/int[] 전송·대칭 랜덤 생성의 API를 이전한다. 공통 타일/방향/아이템 규약과 기존 JS의 검사/생성 결과를 대조한다.
- 경기 기록 목록/원문 사본 접근·재대결 선택과 작업실의 prompt contract·규약 해시를 유지한다. 규약 데이터를 두 언어에 수동 복제해 어긋나게 하지 않고 단일 원본/생성 또는 일치 검사를 둔다.
- 검사 요청은 인가 후 실행 관리 서비스에 전달하고 결과만 반환한다. 사용자가 임의 내부 경로/실행 명령을 지정하지 못하게 한다.
- **완료 기준:** 격리 데이터로 기존 API 계약·동시 저장 충돌·계정/관리자 격리·맵 가져오기/내보내기·실제 JS 검사 진단 검증. 기존 UI의 대응 API와 비교 가능한 상태.

### 단계 6 — 경기 생성·SSE·최종 결과 통합

- 운영 BE가 알고리즘/맵/옵션/계정 권한을 확인하고 경기 ID·불변 실행 요청을 만든다. 동일 요청 재전송에 중복 게임이 생성되지 않게 한다.
- 관리자 ready 이후 카운트다운/시작을 연결한다. 공개 경기 API와 SSE는 운영 BE의 권한 확인 아래 기존 snapshot 의미/순번을 유지한다.
- 화면 상태는 관리자→운영 BE 경유로 중계하며 버퍼·취소·재구독·느린 수신자를 처리한다. SSE 단절만으로 게임을 중단하지 않는다. 게임 엔진은 브라우저/운영 API 처리 속도에 맞춰 턴을 기다리지 않는다.
- 최종 결과와 경기 코드 사본을 연결하고 기록 목록을 갱신한다. 관리자에 미반영 완료 정보를 남겨 운영 BE 장애 뒤 재전달/대조가 가능하게 한다. 중복 반영·동일 ID의 상충 결과를 검증한다.
- 관리자 차단/로그아웃 등 기존 경기 중단 정책이 있으면 운영 BE의 권한 변경을 해당 실행에 전달한다. 게스트/테스트/이전 경기 대결의 접근·정리 범위를 유지한다.
- **완료 기준:** 게스트·계정·테스트·본인 이전 기록 대결의 생성/실행/중단/완료·구독 권한·목록 반영을 새 운영 API에서 검증. 이 단계만으로 전량 저널 구현 완료라고 표시하지 않는다.

### 단계 7 — 전량 로그 수집과 독립 저장 연결

- [수집 모듈 계약](game-log-collection-modules.md)에 따라 수집 인터페이스·collector·저장 어댑터·실행 기록 목록을 분리한다. 현재 최근 40건 화면 로그는 원본 기록으로 사용하지 않는다.
- 구현 전 내구성 수준·큐 포화/저장 실패 시 경기 처리·게스트/테스트 수집/조회 범위를 확정한다. 정상 종료 전량 보존과 호스트 장애 보존을 구분하고 비동기 버퍼만으로 후자를 약속하지 않는다.
- 1차 로컬 JSONL/writer 후보를 검증해 준비/초기화·모든 판단 결과·액션 시작/완료·기믹·실제 랜덤 결과·취소/늦은 응답·종료를 기록한다. 운영 DB는 원본 저널을 대신하지 않는다.
- 큐 접수/내구 seq/완결 receipt·부분 파일 복구·파일/기록 목록 불일치·조회 스트리밍/인가·소유자별 삭제 연결을 구현한다. 실패를 조용한 드롭·언어별 고정 대기·무제한 큐로 감추지 않는다.
- 결과 확정·로그 완결·운영 반영 상태를 구분하고 정상 종료와 실패 기한에서 엔진 프로세스를 정리한다.
- **완료 기준:** 원본 이벤트 수/순서·완료/취소·최종 상태 대조, disk full/느린 writer/중간 종료·복구/중복 결과 검증. 수집 프로세스/호스트 배치 미확정 사항은 명시한다.

### 단계 8 — 기존 화면 연결과 최소 호환 중계

- 기존 HTML/JS/CSS/자산은 유지하고 `/api/*`를 새 운영 BE로 연결한다. 첫 단계는 기존 정적 제공 계층에 최소 중계/세션 조회를 적용해 공개 주소를 하나로 유지한다.
- Node/화면 계층이 더 이상 자체 세션/계정/맵/경기 원본을 소유하지 않게 한다. 페이지 접근 UX는 새 운영 BE 세션으로 판단하고 최종 API 인가는 운영 BE에서 수행한다.
- 쿠키·OAuth 리다이렉트·요청/응답·파일 스트림·SSE·취소·에디터 CSP nonce·테스트 iframe을 실제 중계 경로에서 확인한다. 작은 코드 파일 상한이나 SSE 버퍼링 지연을 새로 만들지 않는다.
- 후속 FE 독립 빌드/배포와 구분해 이번 중계의 범위·제한을 문서화한다. 제거된 AI 연결을 복원하지 않는다.
- **완료 기준:** 기존 UI에서 로그인→작성/검사/저장→게임/기록/재대결→관리자 맵 편집/게시를 새 BE로 수행. 보호 페이지/API 오류·모바일/레이아웃 회귀 확인.

### 단계 9 — 통합·장애·부하 리뷰와 전환

- 실제 호출 총시간·실행기 시간·입력/출력·IPC·tick 지연을 구분하고 빠른/느린 참가자의 독립 진행을 확인한다. 호스트/중계 변경이 계산 성능의 시간상 이점을 없애지 않게 한다.
- 동시 게임·정적 자산/SSE·업로드·검사/저장·전량 기록이 겹치는 조건에서 CPU/메모리/프로세스·큐/연결·종료 시간을 측정하고 수락/자원 기준을 정한다.
- 운영 BE/관리자/엔진/수집 장애를 각각 주입한다. 재연결·미반영 결과·부분 기록과 진행 중 게임 처리 정책을 명시하며 자동 무손실 재개를 가정하지 않는다.
- 이전 도구의 dry-run과 ID/소스/맵 참조 검증을 마친 뒤 쓰기 중지→함께 백업→필요한 이전→구 BE 쓰기 차단→설정 전환→점검→쓰기 재개 순서를 제공한다. 실제 사용자 데이터 전환은 해당 운영 작업으로 명시해 수행한다.
- 전환 전과 새 BE 쓰기 발생 이후의 복귀 절차를 구분한다. 새 쓰기가 생긴 뒤 설정만 되돌려 데이터가 사라진 것처럼 보이게 하지 않는다.
- 독립 실행 명령·설정 예제·관리자 명령·디버깅·health/readiness·종료·검증·복구 문서를 갱신하고 적대적 리뷰에서 발견한 결함을 수정한다.
- **완료 기준:** 실제 새 경로의 통합/계약/브라우저 검사·자원/장애 보고·리뷰 결과·전환/복귀 절차. 외부 Google/사내 배포 테스트와 개인정보 마지막 준비의 남은 항목은 완료로 오인하지 않게 별도 표시.
