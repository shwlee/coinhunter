# 게임 운영 DB 선정과 개발·전환 계획

- 정리일: 2026-11-15
- 상태: 추천안과 개발 순서. DB 제품 채택·설치·어댑터 구현·배포는 아직 하지 않았다.
- 최신 실행 순서: [BE 분리 계획](backend-separation-implementation-plan.md)을 먼저 진행한다. C# 운영 서비스에는 처음에 파일 저장 어댑터를 구현하고 DB 제품 채택/전환은 후속으로 분리한다. 아래 Node 드라이버 예시는 분석 당시 후보이며 C# 전환 뒤 실제 드라이버/제품은 그 환경에서 선정한다.
- 기준: [백엔드 책임 경계](game-backend-boundaries.md), [현재 저장 어댑터](storage-adapters.md), [실행 로그 수집 모듈](game-log-collection-modules.md).

## 1. 범위와 추천

게임 운영 DB는 계정·권한·알고리즘 메타데이터·맵·경기 목록 등 서비스 업무 데이터를 관리한다. 매 턴 원본 로그와 엔진 진행 상태는 실행 영역의 독립 계약으로 관리한다. 운영 DB 선택이 실행 로그 저장소 선택을 결정하지 않는다.

데이터 모델과 향후 운영 BE 분리를 기준으로 **MongoDB를 우선 후보로 추천**한다. 맵/옵션·알고리즘 메타데이터·경기 요약을 버전 있는 문서로 다룰 수 있고, 기존 Node 서비스에는 공식 드라이버를 사용하는 어댑터를 추가할 수 있다. 이는 설계상 적합성 판단이며 실제 처리량 우위나 제품 채택 확정을 뜻하지 않는다. [공식 Node 드라이버](https://www.mongodb.com/docs/drivers/node/current/).

| 후보       | 이 프로젝트에서의 판단                                                                                          | 배포와 개발 부담                                                                             |
| ---------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| MongoDB    | 문서 중심 운영 데이터의 우선 후보                                                                               | 별도 DB 프로세스·인덱스·스키마 검사·트랜잭션 환경·백업 필요                                  |
| PostgreSQL | 관계·제약·대회 통계/집계 요구가 커질 경우 비교할 대안. JSONB도 제공하므로 JSON 데이터 때문에 배제할 이유는 없음 | 별도 DB 서비스와 관계형 스키마/마이그레이션 운영                                             |
| SQLite     | 하나의 앱 컨테이너와 영구 볼륨으로 끝내는 조건이 최우선일 때 단순한 대안                                        | 별도 DB 서버 불필요. 단일 호스트/쓰기 동시성 요구를 검증하고 향후 서버형 DB 전환은 별도 작업 |

[PostgreSQL JSON 형식](https://www.postgresql.org/docs/current/datatype-json.html), [SQLite 적용 범위](https://www.sqlite.org/whentouse.html).

NoSQL을 쓴다고 모든 정보를 한 사용자 문서에 넣지는 않는다. 계정별 무한 성장 배열 대신 알고리즘·경기 등을 독립 문서로 두고 소유자 ID로 조회한다. NoSQL도 타입·필수 필드·버전·유일성·일관성 설계가 필요하다. MongoDB에는 스키마 검사 기능이 있으므로 서비스 검증과 함께 적용한다. [스키마 검사](https://www.mongodb.com/docs/manual/core/schema-validation/).

## 2. 무엇을 어디에 저장하는가

| 데이터      | 운영 DB                                                                              | 다른 저장 영역                                                                              |
| ----------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 사용자      | 내부 ID·표시 이메일·역할·활성 상태·수정 정보                                         | 초기 관리자 지정은 유지보수 명령으로 등록하며 저장소에 개인 계정을 하드코딩하지 않음        |
| Google 신원 | provider·subject·userId·연결 정보                                                    | 인증 중 일시 데이터와 세션은 현재 메모리 정책 유지. Google 토큰 영구 저장을 추가하지 않음   |
| 알고리즘    | ID·소유자·이름·언어·revision·sourceKey·해시/크기·시각                                | 코드 원문은 별도 파일. 코드가 커져도 DB 문서로 이동하지 않음                                |
| 경기 기록   | 경기 ID·참가자·점수·종료 사유·고정된 코드/맵 참조·결과 버전·실행 기록 참조/완결 상태 | 기존 재대결용 코드 사본은 파일, 모든 턴/액션·진단·랜덤 결과의 원본은 실행 기록 저장소       |
| 맵          | ID·이름·버전·크기·타일 배열·옵션·초안/게시 포인터·노출·표시 순서                     | JSON/int[] 가져오기·내보내기는 교환 형식으로 유지. 샘플 파일은 초기 등록 입력으로 사용 가능 |
| 향후 기능   | 전역 정책·대회/참가/제출·매칭 등 확정된 업무 데이터                                  | 지금 만들지 않은 기능의 DB/API를 함께 구현하지 않음                                         |

맵은 크기와 스키마가 제한된 구조 데이터이므로 운영 DB에 본문까지 넣는 것을 추천한다. 알고리즘 원문 파일 유지 요구와 다르다. 다만 현재 맵은 별도 파일 저장소이므로 계정 DB 전환과 단계를 분리한다. 맵까지 이전한 뒤에는 같은 맵을 파일 registry와 DB에서 동시에 수정하는 이중 원본을 만들지 않는다.

진행 중 경기와 로그인 세션은 현재 서버 메모리에 있다. 이번 DB 전환으로 재시작 시 자동 경기 재개나 세션 유지까지 구현됐다고 간주하지 않는다. 이 기능은 별도 범위다.

## 3. 개발 구조

```text
HTTP API / 업무 서비스 / 관리자 유지보수 명령
  → 기존 AccountRepository 공개 계약 유지
      → FileAccountRepository      현재/기존 데이터
      → MongoAccountRepository     신규 메타데이터 구현
          → MongoDB
      → SourceStore                공통 코드 파일 저장 계약

맵 API / 맵 업무 서비스
  → MapRepository 계약 정리
      → 파일 구현 / 향후 Mongo 구현

기동 구성부
  → 어댑터·접속 정보·저장 경로 주입
```

현재 `ACCOUNT_STORE_ADAPTER`는 `file`만 지원한다. Mongo 구현 이후에만 `mongodb` 선택을 추가한다. `SourceStore`의 파일 쓰기/열기/사본/정리 수명도 두 메타데이터 어댑터가 공유하도록 정리한다. 기존 코드 파일 구현이 있다는 것과 DB용 조합이 이미 완료됐다는 것은 다르다.

API가 DB 컬렉션을 직접 다루지 않게 하고 기존 소유권·403/404/409·응답 형식·원문 스트리밍을 유지한다. 내부에서는 사용자/신원·알고리즘·경기 저장 책임을 나눌 수 있지만 프런트엔드나 엔진에 MongoDB 전용 타입을 노출하지 않는다. 기존 UUID를 보존하고 DB의 ObjectId로 바꿀 것을 API에 요구하지 않는다.

공식 `mongodb` 드라이버를 우선 검토하고 ODM은 필수로 추가하지 않는다. DB 클라이언트는 운영 프로세스에서 공유하고 요청/턴마다 새 접속을 만들지 않는다. 실제 서버/드라이버 버전은 구현 시 지원되는 Node 런타임과 함께 호환성을 검증해 고정한다.

## 4. 문서 모델과 일관성

첫 모델 후보는 `users`, `identities`, `algorithms`, `matches`다. 맵 전환 시 `maps`, `mapRevisions`, `mapDisplayOrder`를 추가한다. 스키마/이전 버전과 서비스 공통 제약을 조정하는 문서도 별도로 둔다. 실행 기록 원본의 catalog는 실행 영역 책임이며 이 운영 DB 모델과 혼동하지 않는다.

다음 계약을 DB에서 실제로 보장해야 한다.

- 신원: `(provider, subject)`, `(userId, provider)` 각각 고유 인덱스. Google 이메일로 자동 계정 병합하지 않는다. 신규 사용자와 신원 연결은 함께 완료되도록 처리한다.
- 알고리즘: `id + ownerId + expectedRevision` 조건으로 갱신하고 충돌은 409로 반환한다. 목록은 코드/물리 경로 없이 소유자별 페이지 조회한다.
- 관리자: 마지막 활성 관리자 보호를 유지한다. 서로 다른 두 관리자를 동시에 강등하는 경우는 각 사용자 문서의 트랜잭션만으로 안전하다고 가정하지 않는다. 관리자 집합 변경이 공통 guard 문서를 갱신하도록 직렬화하고 트랜잭션/충돌 재시도로 검증한다. 모든 승격·활성/비활성·부트스트랩 경로가 같은 규칙을 사용한다.
- 경기: 경기/사용자 기록의 고유 키와 결과 버전으로 재전달을 멱등 처리한다. 사용자별 시간순 조회와 참가 범위 검사를 지원한다. 실행 영역의 원본 점수/기록을 운영 요약으로 임의 변경하지 않는다.
- 맵: 불변 버전 문서를 먼저 만들고 draft/published 포인터는 예상 버전 조건으로 갱신한다. 동시 저장·게시 충돌, 초안 비노출, 전체 표시 순서 변경의 충돌을 검증한다.

MongoDB 단일 문서 갱신은 원자적이지만 여러 문서의 원자적 처리는 별도 트랜잭션이 필요하다. standalone 서버는 다중 문서 트랜잭션을 지원하지 않으므로 위 모델을 채택하면 replica set 환경으로 개발/검증한다. 트랜잭션을 쓴다는 이유만으로 모든 업무 제약과 동시성 문제가 해결되지는 않는다. [원자성](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/), [트랜잭션 배포 조건](https://www.mongodb.com/docs/manual/data-modeling/enforce-consistency/transactions/).

## 5. 코드 파일과 DB의 정합성

DB 트랜잭션으로 코드 파일까지 함께 롤백할 수는 없다. 다음 수명으로 처리한다.

1. 새 코드를 새 불변 파일 키에 기록하고 필요한 쓰기 완료를 확인한다. 덮어쓰기 저장도 기존 파일 내용을 직접 바꾸지 않는다.
2. 소유권/예상 revision을 검사해 DB의 파일 참조를 원자적으로 갱신한다.
3. DB 갱신 실패 시 새 파일을 정리 대상으로 남기거나 안전하게 삭제한다. 응답 유실 시 성공 여부를 대조하기 전 참조될 수 있는 파일을 삭제하지 않는다.
4. DB 갱신 성공 후 이전 파일은 활성 읽기·경기 사본 생성·보관 참조가 해제된 뒤 정리한다. 현재 프로세스 내부 lease만으로 여러 서버의 안전한 삭제를 보장하지 않는다.
5. 재기동 후 DB 참조·파일 존재·크기/해시·미참조 파일을 대조한다. 유예 기간과 작업 중 참조를 고려하고 경기 사본을 일반 낡은 파일로 삭제하지 않는다.

원문 보관량·파일 정리 실패도 운영 지표에 포함한다. 세부 개인정보 보관 기간은 마지막 필수 준비에서 확정하되 소유자별 열거/삭제와 보관 분류는 모델에 반영한다.

## 6. 단계별 구현과 완료 기준

| ----------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 1           | 제품/배포 조건·데이터 모델 확정    | Mongo 우선안과 한 컨테이너 제약을 대조하고 스키마·인덱스·원자 작업·참조/삭제 수명을 문서화                |
| 2           | 공통 저장 계약 검증                | 파일 구현의 현재 동작을 계약 테스트로 고정. DB 연결 설정·기동/종료·준비 확인·스키마/인덱스 이전 절차 준비 |
| 3           | 계정/Google 신원/관리자 Mongo 구현 | 중복/동시 로그인·차단 계정·마지막 관리자 경합·부트스트랩 검증. 사용자 ID 보존                             |
| 4           | 알고리즘/경기 요약 Mongo 구현      | 코드 파일 유지·revision 충돌·사본 일관성·중복 결과·계정 격리와 파일/DB 중간 실패 검증                     |
| 5           | 맵 저장 계약과 Mongo 구현          | 샘플/사용자 맵 이전·버전·게시/숨김·순서·옵션·복제/가져오기/내보내기 회귀 검증                             |
| 6           | 데이터 이전 도구                   | dry-run·백업·검증 보고·재실행 가능한 이전·잘못된 신원/참조 거부. 원본 파일 보존                           |
| 7           | 컨테이너/복구/부하 검증            | 영구 저장·비밀 설정 주입·DB 불통·재기동·동시 작업·백업 복원·이전 버전 복귀 검증                           |
| 마지막 필수 | 개인정보 운영 준비                 | 실제 서비스 개시 전 계정/신원/원문/경기/로그의 안내·보관/삭제·백업 만료·권리 요청을 구현/검증             |

개발 DB는 테스트 전용 데이터와 replica set으로 운영 조건을 재현한다. 인메모리 가짜 저장소만으로 DB 트랜잭션/유일성 검증을 대신하지 않는다. 기존 사용자 데이터·키를 시험 데이터로 복제하지 않는다. 파일 어댑터와 DB 어댑터에 같은 계약 테스트를 적용한다.

이전 시에는 쓰기 중지 → 메타데이터/코드/맵 함께 백업 → 검증·이전 → 개수/ID/참조/권한 확인 → 어댑터 전환 → 실제 흐름 확인 순서로 진행한다. 실시간 이중 쓰기는 첫 전환 범위에 넣지 않는다. DB에 새 쓰기가 발생한 이후 단순히 설정만 파일로 되돌리면 새 데이터가 사라진 것처럼 보이므로 쓰기 재개 전 복귀와 재개 후 복귀 절차를 구분한다.

## 7. 한 컨테이너 배포 조건

MongoDB는 별도 DB 프로세스가 필요하다. 추천 배치는 앱 컨테이너 하나와 별도 MongoDB 서비스다. 같은 호스트의 별도 DB 컨테이너도 가능하지만 전체 컨테이너 수는 둘이므로 기존 한 컨테이너 조건과 동일하다고 표현하지 않는다.

전체를 반드시 컨테이너 하나로 배포한다면 선택지는 앱과 MongoDB를 같은 컨테이너에서 관리하거나 SQLite를 채택하는 것이다. 전자는 기동 순서·DB 준비·장애 감지·모든 자식 프로세스의 종료와 각각의 영구 저장을 직접 관리해야 하므로 1차 기본안으로 추천하지 않는다. 이 경우에는 SQLite 어댑터를 우선하는 쪽이 단순하다. Docker도 책임별 서비스 분리를 권장한다. [다중 프로세스 컨테이너](https://docs.docker.com/engine/containers/multi-service_container/).

MongoDB의 개발용 단일 멤버 replica set은 트랜잭션 검증에 사용할 수 있지만 복제본/호스트 장애의 고가용성을 제공하지 않는다. 실제 배포의 DB 위치·가용성·볼륨/백업은 배포 테스트에서 확정한다. [테스트용 replica set](https://www.mongodb.com/docs/manual/tutorial/deploy-replica-set-for-testing/).

어떤 배치에서도 브라우저나 알고리즘 프로세스가 운영 DB에 직접 접속하지 않는다. 접속 비밀은 런타임 설정으로 주입하고 DB 오류 때 파일 저장소로 자동 전환해 두 원본을 만들지 않는다. DB·코드·맵·실행 기록을 함께 복원 가능한 백업 체계를 검증한다.
