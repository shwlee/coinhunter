## H1 — 기존 경기 복구와 신규 수락 정책 분리

- Execution은 같은 경기 ID의 기존 요청부터 찾고 전체 요청 fingerprint를 대조한다. 정확히 같은 요청의 결과/취소 상태는 언어가 비활성화된 뒤에도 반환하지만 다른 내용의 재사용은 409로 거절한다. 새 C# 실행은 계속 베타 정책을 검사한다.
- Operations의 복구는 기존 실행을 GET으로 조회하고 없는 경우에만 수락을 시도한다. 경기 하나의 서비스/데이터 오류는 그 항목에 남겨 재시도하고, 이후 다른 사용자의 결과 적용은 계속한다.
- 실제 C# 사용자와 다른 JS 사용자의 경기를 실행하고 Operations→Execution 순으로 종료한 뒤 베타 비활성 상태로 재시작했다. 두 경기의 `completed/applied`가 true로 복구됐고 두 사용자 모두 다음 JS 생성이 201이었다. 수정 전에는 각각 false와 409였다.

## M1 — 확정 거절과 응답 불명을 구분하고 미생성 경기 취소 보장

- `ServiceFault.Code`를 내부 HTTP 오류까지 유지한다. Execution의 등록 이전 확정 거절에만 `execution_admission_rejected`를 부여한다. 언어/할당량 거절은 이 코드로 판정하고, 준비 실패·일반 서비스 장애·응답 유실을 같은 것으로 취급하지 않는다.
- Operations는 확정 거절인 경우만 새 운영 경기와 준비한 원문 사본을 되돌린다. 수락 여부가 불명확한 실패의 운영 항목/원문은 보존해 복구하거나 안전하게 중지할 수 있게 한다.
- 중지 계약에 선택적인 원래 `execution` 요청을 추가했다. 아직 실행이 없으면 Execution은 수락과 같은 lock 안에서 원본 요청에 바인딩된 종료 상태를 먼저 영구 보관한다. 그 뒤 늦게 도착한 같은 수락은 종료 상태만 반환한다. 요청이 이미 수락됐다면 기존 실행을 중지하며, 다른 fingerprint의 취소/수락은 거절한다.
- 종료 상태는 재시작 후에도 유지하며 런타임/알고리즘을 생성하거나 메모리를 예약하지 않는다. 실제 실행이 없었던 경우 recording은 `failed`, 결과는 `aborted`로 남겨 게임/로그가 있었던 것처럼 표시하지 않는다.
- 기존 미생성 운영 항목도 전체 요청을 사용해 중지할 수 있다. 복구 과정에서 비활성/정책 거절로 더 이상 시작할 수 없는 항목도 같은 절차로 완결한다.
- 실제 정책 불일치 환경에서 생성은 503과 확정 거절 코드였고 미완료 항목은 남지 않았으며, 다음 JS 생성은 201이었다. 실제 내부 HTTP로 미생성 요청을 중지한 뒤 재전송해 `closed/aborted`, `enginePid=null`을 확인했고 다른 요청 내용의 재전송은 409였다.

내부 stop 계약은 원래 `{requestId, reason}`도 계속 받는다. 미생성/불명확 요청의 안전한 취소에는 `{requestId, reason, execution}`을 사용하므로 Operations와 Execution을 같은 수정 버전으로 갱신해야 한다. 불명확한 실패를 무조건 삭제하거나 GET 404만으로 취소가 끝났다고 처리하지 않는다.

## M2 — PC 파일 읽기 완료 시 문서 변경 보호

- PC 파일 선택에 문서/읽기 버전을 할당하고 읽기 시작 전 내용을 보관한다. 완료 시 같은 버전·본문·불러오기 창 상태인지 다시 확인한다.
- 창을 닫거나 새 문서를 만들면 이전 읽기를 무효화한다. 새 파일을 선택하면 오래된 완료가 최신 선택을 덮지 않으며 오래된 `finally`도 최신 input 상태를 지우지 않는다.
- 읽는 중 편집 내용이 바뀐 경우 기존 내용을 보존하고 안내한다. 미저장 여부 확인과 정상 파일 불러오기는 유지한다.
- 실제 브라우저에서 창 닫기→새 C# 문서 편집, 느린 파일→최신 파일 선택, 읽기 중 코드 변경을 각각 재현해 현재 내용이 유지되는 것을 확인했다.
