# C# 긴 기본 연산 측정·제한 프로필 v2

작성: 2026-11-19. C2의 긴 기본 연산 관문 중 컬렉션 검색/확장·배열 할당/GC를 측정하고 호스트 검사 함수와 객체별 한도를 구현했다. C# 정식 지원은 비활성이다. 기계 판독 요약은 [프로필 v2](../backend/contracts/csharp-bounded-profile-v2.json), 원본은 [실측 JSON](benchmarks/csharp-builtins-2026-11-19.json)에 보관한다.

## 실측 방법과 결과

Windows 전용 자식 프로세스에 메모리 768 MiB·프로세스 2개·CPU rate 10000의 R0 그룹을 적용했다. 입력 컬렉션 준비는 측정 밖에서 수행했다. 각 연산은 5회, 경계 시험은 499ms 부근까지 신뢰된 host fixture에서 기다린 다음 연산을 한 번 수행한다. user 코드에 Thread/Sleep/임의 BCL을 허용한 시험이 아니다. 샘플은 합성 데이터이며 사용자 계정/코드/실행 중인 서버는 변경하지 않았다.

아래는 해당 PC에서의 최종 관측값으로 운영 지연 상한이 아니다. 경계 측정은 한 표본이므로 percentile이나 언어 간 공정성 수치로 사용하지 않는다. 각 size는 준비 시 요청 크기이며 Dictionary/HashSet의 실제 내부 prime capacity는 다를 수 있다.

| 연산                     |                  크기 | 독립 5회 중 최대 | 499ms 부근 시작 시 최종 경과 |
| ------------------------ | --------------------: | ---------------: | ---------------------------: |
| 원본 List 확장           |             8,388,608 |          15.56ms |                     525.87ms |
| 원본 Queue 확장          |             8,388,608 |          19.29ms |                     512.30ms |
| 원본 Dictionary 재해시   |             1,048,576 |           9.14ms |                     504.64ms |
| 원본 HashSet 재해시      |             1,048,576 |           7.66ms |                     503.91ms |
| 원본 배열 할당/접촉      |             8,388,608 |           7.69ms |                     500.17ms |
| 원본 반복 배열 할당/GC   |      1,048,576 × 64회 |          32.06ms |                     534.45ms |
| 검사형 List 검색         |                65,536 |           0.84ms |                     499.46ms |
| 제한형 List 확장         |       32,768 → 65,536 |           0.21ms |                     499.06ms |
| 제한형 Dictionary 확장   |      요청 크기 32,768 |           0.45ms |                     499.60ms |
| 검사형 반복 배열 할당/GC | 1,048,576 × 최대 64회 |          10.69ms |            500.85ms에서 중단 |

같은 1M 요소 반복 할당도 GC 상태에 따라 측정값이 달라진다. 검사형이 본질적으로 할당을 더 빠르게 만든다는 뜻이 아니다. 핵심 차이는 각 할당 사이에서 마감을 확인하여 남은 작업을 계속 수행하지 않는다는 점이다.

## 적용한 후보 프로필

프로필을 `csharp-restricted-c1-v2`, 분석기를 `c1-2`, guard를 `c2-poll-bounded-v2`로 변경했다. 이전 v1 산출물/검사 결과와 같은 것으로 취급하지 않는다. 현재는 제품 cache 연결 전이므로 실제 캐시 이전은 없다.

| 영역                         | 적용                                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| List.Contains/IndexOf/Remove | host가 검색을 수행하며 최대 256요소마다 마감/중단 확인                                               |
| Queue.Contains               | host 순회에서 최대 256요소마다 마감/중단 확인                                                        |
| 컬렉션 확장                  | List/Queue/HashSet/Dictionary/PriorityQueue의 추가를 host 함수로 변환하고 Count ≤ 65,536 적용        |
| 컬렉션 생성                  | 요청 capacity ≤ 65,536. 기본/용량 생성자를 호스트 factory로 변환                                     |
| 배열 생성                    | 단일 배열 ≤ 1,048,576요소. 지원 타입의 요소 크기 기준 최대 약 8 MiB. 동적 길이는 할당 전 확인        |
| List.RemoveAt                | 최대 크기가 제한된 상태로 native 이동 전후 검사. 이동 도중 예외로 중단해 내부 상태를 손상시키지 않음 |
| 사전 인덱서 쓰기             | 새로운 키 삽입으로 Count 한도를 우회할 수 있어 AP001 거절. 읽기는 유지하고 추가는 Add 사용           |
| 콜백/Sort/LINQ/Dispose       | 기존 미승인 유지                                                                                     |

65,536개 컬렉션에서는 측정한 기본 연산이 1ms 안쪽이었다. 큰 연산의 실측 증가와 OS 그룹 여유를 고려해 이 값을 **검증용 초기 프로필**로 선택했다. 수학적인 500ms 보장으로부터 도출한 값은 아니다. 정교한 알고리즘의 코드 파일 크기를 제한하지 않으며, 코드 양과 런타임 객체 크기를 구분한다. 실제 운영 사양이 정해지면 프로필 버전을 바꿔 조정할 수 있다.

HashSet에서 이미 있는 값을 다시 Add하는 것은 Count 한도에 도달해도 정상 false 반환을 유지한다. 명시적 comparer를 허용하지 않고 int 타입으로 한정한다. 실제 내부 버킷/배열 capacity는 BCL 구현상 요청/Count 한도를 넘을 수 있으므로 최대 내부 capacity와 같다고 표시하지 않는다.

원본의 명명된 인자 순서와 receiver/인자 평가 순서를 유지한다. 별칭·완전 수식 호출은 Roslyn의 실제 심볼을 통해 같은 변환을 적용한다. 정수 크기의 배열 initializer는 정적으로 한도를 확인하고 C# 상수 초기화 규칙을 보존한다. int/long/uint/ulong 크기 표현의 동적 검사도 지원한다.

## 실패 분류

상수로 확인되는 과대 배열/용량은 AP001로 거절한다. 동적 초과는 할당/확장 전에 host가 확인하여 `operation-limit`과 `array-elements` / `collection-capacity` / `collection-count`, 원본 행/열을 반환한다. timeout·원인 불명 OOM·OS 메모리 초과와 다른 분류다. 마감도 이미 지났다면 host 소유 timeout 판정이 우선한다. 한도를 초과한 후보는 이후 재호출을 거절한다.

입력 배열의 복사, 누적 메모리·소스 분석/컴파일, 문자열/그 밖의 암묵적 연산은 이번 객체별 한도의 대상과 구분한다. OS 그룹 메모리 한도와 부모 감시는 계속 필요하다.

## 검증·재현

기존 C2 149개 확인에 정책 확인 62개를 추가했다. 실제 후보 소스를 컴파일/실행하여 다음을 검사한다.

최종 전체 검증에서 C1 52건·C2/정책 211개 확인·C3 30개 확인·기존 .NET 59건, BE 통합 13그룹·프로토콜 5건이 통과했다. 빌드 경고/오류는 0개다. [최종 정책 검증 원본](benchmarks/csharp-bounded-validation-2026-11-19.json)을 별도로 보관한다. Node 코드는 변경하지 않았으며 기존 legacy 파일 잠금 EPERM의 미해결 상태도 유지한다.

- 크기 상수/동적 길이·생성 용량·5개 컬렉션의 Count 한도와 오류 분류/위치.
- Dictionary 인덱서 변경·증감·괄호를 이용한 한도 우회 거절.
- 명명된 인자/overload·배열 initializer·int/long/uint/ulong 크기·호출 평가 순서 보존.
- 기존 BFS, 기본 컬렉션 동작, 한도에서의 중복 HashSet.Add 및 검색 범위 처리.
- 신뢰된 큰 검색 fixture에서 검색 중 timeout 후 컬렉션 크기/구조 유지. 이 fixture만 guest 한도를 넘겨 host 검사 루틴의 중간 중단을 재현한다.
- 일반 컬렉션 timeout 재사용 시험은 Clear를 함께 사용해 새 Count 한도 안에서 반복하도록 수정했다. 한도를 넘긴 실행을 정상 timeout이라고 처리하지 않는다.

측정은 수동 명령으로 제공한다. 정책 검증은 C2 전용 자식과 일반 BE 회귀에 포함된다. 과거 v1/C2/C3 측정 자료는 덮어쓰지 않는다.

## 남는 한계와 다음 단계

**할당·GC·bounded native 복사/재해시를 정확히 500ms 시점에 선점하는 구현은 아니다.** 객체별 크기를 줄이고 검색/반복 할당 사이에 체크를 넣어 긴 구간을 줄였지만 운영체제 스케줄링·GC·메모리 압박에 대한 절대 시간 보장은 생기지 않는다. 작은 배열도 임계 시점의 GC를 유발할 수 있다. 이번 26개 측정만으로 모든 허용 API의 중단 안전성이 증명되지 않는다.

따라서 C2 전체 관문을 닫거나 C#을 활성화하지 않는다. 문자열 등 나머지 암묵적 연산의 프로필 검토, Linux/메모리 압박 검증, 운영용 부모의 독립 감시와 실제 미종료 복구 정책을 먼저 진행해야 한다. C4 산출물 관리·서비스 연결은 이 제한과 버전을 전제로 설계한다.
