## 실행 흐름과 계획 조정

공개 주소는 Node 정적 웹/중계 → C# 운영 → C# 실행 관리 → 경기별 Node다. 플레이어 판단/이동은 엔진 안에서만 진행한다. 운영/화면 중계가 느려져도 엔진 턴을 기다리게 하지 않는다. 운영 API가 중지돼도 실행 관리/엔진은 계속 진행할 수 있다.

기존 공개 POST `{id}`와 카운트다운 동작을 유지하기 위해 공개 요청 내부에서 prepare→start를 수행한다. 초기 계획의 “ready 이후 카운트다운”을 별도 공개 준비 UI로 확대하지 않았다. 내부 준비/시작 경계는 실제로 분리됐고, 브라우저 카운트다운은 기존 FE의 순서를 유지한다.

상태 어휘도 실제 구현에 맞춰 accepted/prepared/running/closed/failed와 recording complete/partial/failed로 고정했다. 종료의 outcome(finished/aborted/failed), 수집 완결, 운영 반영/ack는 별개다. 1단계 초안의 임시 상태 이름을 구현됐다고 남기지 않았다.

기존 맵의 JSON/int[] 교환과 대칭 랜덤 생성은 브라우저 모듈을 유지한다. C#은 실제 API 저장/검사/게시를 담당한다. 기본 설정·제한·샘플·프롬프트 규약/해시는 기존 JS/문서에서 빌드 생성하므로 두 언어에 수작업 복제하지 않는다.

## 검증

- .NET 솔루션 빌드: 경고 0, 오류 0. 외부 NuGet 설치 없음.
- C# 기존 계약 31건 + 저장/인증/복구/이전 13건.
- Node/C# 실제 프레임·환경 경계 5그룹 + 두 서비스/중계 업무·유지보수 통합 13그룹.
- 기존 Node 회귀: **232 통과, 실패 0**, 직렬 실행 약 32초.
- collector 4건 포함: 500건 전량/seq, 느린 writer와 포화, disk-full/flush 실패 주입, 연속 배치 재개.
- 실제 브라우저: Edge headless, 1440/768/390 너비, 작업실 저장/검사·테스트 iframe·관리자 제작/게시·게임 결과, pageerror/5xx 없음.
- 동시 부하: 4경기×4플레이어 + 4 SSE + 실제 코드 검사 + 원문 업로드/저장 + 정적 에셋 + 맵 조회 20회. 5번째 경기 429, 거부된 경기를 뒤늦게 자동 실행하지 않음.
- 장애: 테스트 소유 엔진 PID 종료→실패/부분 로그, 실행 관리 종료→ready 503/receipt·partial 회수, 운영 API 재시작→게임 계속/세션 재로그인/최종 요약 1회 반영.
- 실행 도구: 자체 임시 포트에서 build/ready/UI/API·stdin 정상 종료, 웹/운영/실행 listener 모두 닫힘.
- CI: Node 22와 .NET 10.0.401의 Windows/Ubuntu BE 검사 job을 추가했다. 이번 결과는 로컬 Windows 검사이며 원격 CI 실행/Ubuntu 통과를 주장하지 않는다.

재현 명령은 [backend README](../backend/README.md)에 있다. 검사 중 실제 `.env`, 사용자 계정/코드·맵, Google 키를 읽거나 실제 외부 인증 요청을 보내지 않았다. 테스트용 호스트/브라우저만 생성/종료했다.

## 자원 측정과 한계

2026-11-15 Windows/Node 18.20.2/.NET 10.0.12의 합성 10×10 맵에서 측정했다. 측정 대상은 C# 2개 + 엔진 4개 + 플레이어 16개, 합계 22개 프로세스다. 원시 보고서는 무시된 `artifacts/backend-load-report.json`에 저장한다.

해당 실행의 후반 working set 합계는 약 **1,154MiB**, 두 C# 서비스는 약 **85/100MiB**였다. 프로세스별 working set에는 공유 페이지가 중복되므로 실제 고유 물리 메모리나 컨테이너 한도로 해석하면 안 된다. 웹/측정 프로세스와 순간적인 검사 프로세스의 최대치는 이 합계에 포함하지 않았다.

해당 검증들의 알고리즘 계산 시간과 IPC 포함 roundTripMs의 평균 차이는 약 **0.6~0.8ms**였다. 강제로 주입한 500ms 무한 루프도 포함된 표본이며 언어간 비교나 보장 수치가 아니다. 실제 운영 CPU/메모리·코드 크기·맵/브라우저 조건으로 동시 실행 한도를 다시 정해야 한다. 이번 수락 한도는 기존과 같은 4경기다.

## 검증 중 수정한 결함

- Windows EventLog 기본 provider가 제한 환경에서 예외를 재발생시킴: 콘솔 logger와 본문/URL을 남기지 않는 예외 응답으로 교체.
- 결과 저장 뒤 ack 실패 시 재전달 누락: completed와 acknowledged를 분리해 미확인 결과 재시도.
- 엔진 실패에서 같은 snapshot 순번으로 최종 화면을 놓침: 운영의 합성 종료 snapshot은 순번을 증가시켜 최종 상태 전달.
- 호스트 장애 시 결과가 메모리에만 남을 수 있음: 엔진의 fsync된 receipt를 먼저 쓰고 IPC 전달, 재시작에서 회수.
- 포화로 거부한 게임이 운영 pending에 남아 나중에 시작될 수 있음: 생성/대조 경합을 막고 명시적 수락 거부를 제거·원문 정리.
- 공개 요청 키의 사용자간 충돌: 공개 키는 소유자 범위, 내부 requestId는 별도 생성.
- 실패한 새 원문/중복 생성 요청의 staging 파일: 미확정 파일만 정리하고 완료 경기의 참조는 유지.
- 수집 writer 재개·원본/화면 큐·최종 결과 DTO 어긋남: 배치 재개와 바이트 상한, typed 최종 결과 검증, manifest/문서를 실제 구현으로 정리.

## 리뷰 시 확인할 제한

로컬 파일 어댑터는 단일 운영 writer/단일 실행 관리 writer 모델이다. 독립 네트워크 배치에서는 exchange 볼륨/파일 전달 어댑터와 서비스 인증/TLS를 확정해야 한다. 현재 loopback 제한을 다중 호스트 지원으로 표시하지 않는다.

원문 구버전은 활성 읽기와 경쟁하지 않도록 유지하고 오프라인 reconcile로 회수한다. 완료 게임/저널/exchange 자동 TTL과 계정 전체 삭제는 아직 운영 정책을 정하지 않았다. JSON 메타데이터 어댑터는 데이터가 커질수록 전체 문서 읽기/교체 비용이 커지므로 운영 DB 전환에서 대체한다.

실행 관리 재시작 후 중간 경기를 재개하지 않는다. 완결 결과를 회수하거나 실패/부분 기록으로 확정한다. 호스트 장애로 메모리 큐에만 있던 로그까지 보존한다고 약속하지 않는다. 물리 디스크를 가득 채우는 대신 저장 어댑터 실패를 주입해 검증했다.

Google OIDC는 합성 서명/가짜 제공자로 검증했다. 실제 Google 계정 왕복·등록된 callback·사내 outbound 경로는 배포 테스트에서 확인해야 한다. 실제 사용자 이전/운영 부하/컨테이너·개인정보 마지막 준비도 완료로 표시하지 않는다.
