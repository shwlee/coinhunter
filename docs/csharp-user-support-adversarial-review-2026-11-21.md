## H1 — 베타 비활성화 후 완료 경기 복구가 막히고 다른 사용자까지 정체됨

- 우선순위: 높음 / P1.
- 위치: [ExecutionManager.cs:145](../backend/src/CoinHunter.Execution.Host/Services/ExecutionManager.cs#L145), [MatchService.cs:238](../backend/src/CoinHunter.Operations.Api/Services/MatchService.cs#L238).
- 신규 언어 허용 검사가 기존 경기 조회보다 앞에 있다. 복구 루프는 미완료 항목을 GET으로 조회하는 대신 POST로 재수락하는데, C# 베타가 꺼져 있으면 같은 요청/경기의 이미 보존된 결과도 503으로 거절한다.
- 해당 항목의 예외를 경기 단위로 처리하지 않아 `Refresh()`의 나머지 항목도 중단된다. 결과가 이미 완결된 다른 사용자의 JavaScript 경기까지 운영 상태에 반영하지 못한다.

실제 두 서비스에서 C# 사용자 A와 JS 사용자 B의 경기를 시작했다. Operations를 먼저 중지해 결과 적용을 막고, Execution을 정상 종료한 뒤 베타를 끈 상태로 두 서비스를 재시작했다. Execution에는 두 경기 모두 `closed`와 최종 결과가 있었지만 Operations는 두 경기의 `completed=false`를 유지했다. 두 사용자 모두 새 JS 게임 생성이 409로 거절됐다. 기존 경기 ID를 아는 상태에서 개별 중지 API를 호출하면 운영 반영은 가능했지만 자동 복구는 계속 막혔다.

수정 방향:

1. 기존 요청의 동일성/소유 범위를 확인한 조회·완결 복구를 신규 언어 활성화 정책과 분리한다. 신규 C# 수락은 계속 차단해야 한다.
2. 복구에서는 기존 실행을 먼저 조회하고 필요한 경우에만 신규 수락을 시도한다.
3. 경기 하나의 실패가 다른 경기의 결과 적용까지 막지 않도록 복구 오류를 항목 단위로 처리한다.

## M1 — 정책 불일치로 거절된 요청이 취소할 수 없는 미완료 경기로 남음

- 우선순위: 중간 / P2.
- 위치: [MatchService.cs:99](../backend/src/CoinHunter.Operations.Api/Services/MatchService.cs#L99), [MatchService.cs:101](../backend/src/CoinHunter.Operations.Api/Services/MatchService.cs#L101), [MatchService.cs:157](../backend/src/CoinHunter.Operations.Api/Services/MatchService.cs#L157).
- 재현 조건: Operations 베타는 켜져 있고 Execution 베타는 꺼져 있으며, Execution의 기존 후보 검사는 켜져 있다. 후보 검사와 공개 게임 허용을 따로 설정할 수 있는 실제 구성이다. 이때 오래 열린 화면/직접 API 요청을 검증했다.
- C# 원문 검사까지는 통과하지만 일반 게임 수락은 503으로 거절된다. Operations는 수락 전에 이미 `completed=false` 경기와 원문 사본을 보관하며, 실패 시 409/429만 되돌리므로 이 확정 거절을 정리하지 않는다.

실제 응답은 `C# 베타 지원이 활성화되지 않았습니다.`(503)였다. Execution에는 그 경기 자체가 없어 중지 요청이 404를 반환했고, 이어서 같은 사용자의 JS 생성은 409였다. `/api/languages`가 C# 비활성을 표시하는 것은 확인했지만, 이것만으로 오래 열린 화면과 API 요청의 서버 측 상태 누수를 막지는 못한다. 생성 응답에 ID도 없으므로 일반 화면에서는 이 항목을 중지할 경로가 없다.

수정 방향:

1. 확정적인 정책/계약 거절과 수락 여부가 불명확한 네트워크 실패를 구분한다. 모든 503을 무조건 삭제하면 이미 수락한 실행과 정합성이 깨질 수 있다.
2. 확정 미수락 요청은 실패로 완결하거나 운영 등록/사본을 안전하게 되돌려 다음 게임을 허용한다.
3. 실행이 없는 미완료 운영 항목도 중지·복구로 종결할 수 있어야 한다.

## M2 — 느린 PC 파일 불러오기가 새 문서의 미저장 코드를 덮어씀

- 우선순위: 중간 / P2.
- 위치: [editor.js:697](../frontend/public/editor.js#L697), [editor.js:707](../frontend/public/editor.js#L707).
- 저장 코드 불러오기는 문서 버전과 본문을 비교하지만, PC 파일 분기는 `await file.text()` 후 현재 문서가 바뀌었는지 확인하지 않고 `reset()`한다. 기존 PC 파일 경로에 남은 결함으로, 이번 C# 전환에서도 재현되며 새로 도입된 회귀라고 단정하지 않는다.

실제 편집기와 테스트용 API를 사용했다. `slow.cs` 읽기를 보류한 상태에서 불러오기 창을 닫고 새 C# 문서에 `USER_UNSAVED_EDIT`를 작성했다. 읽기를 완료시키자 본문이 `SLOW_IMPORT`로 교체되고 출처도 `slow.cs`로 바뀌었다. 편집기 상태를 새로 만들기 때문에 앞의 편집 내용을 undo로 회복하는 경로도 유지되지 않는다. 큰 파일/느린 파일 읽기의 순서를 통제한 재현이며 실제 사용자 파일은 사용하지 않았다.

수정 방향: 파일 읽기 전 문서 버전·내용을 보관하고 완료 시 대조한다. 문서 전환/편집 또는 불러오기 취소 후에는 이전 읽기 결과를 적용하지 않는다. 새 파일 읽기가 시작된 경우에도 오래된 완료가 최신 선택을 덮지 않도록 한다.

## 확인 범위와 남은 관문

- 격리된 실제 Operations/Execution/FE에서 C# 저장 → 실제 준비/preflight → 일반 게임 시작은 성공했고 `playing`을 확인했다.
- 동일 격리 환경에서 설정 비활성화·재시작과 서로 다른 사용자의 경기 복구, 정책 불일치 시 거절/중지/후속 생성 응답을 확인했다.
- UI 재현은 실제 브라우저 편집기와 테스트용 API, 완료 시점을 통제한 `File.text()`로 수행했다.
- 사용자 `.env`·실제 계정/코드/맵·기존 서비스는 변경하지 않았다. 테스트 서비스는 종료했고 제품 코드 수정은 하지 않았다. 별도 실험의 package.json/probe 변경은 코드 커밋에서도 제외했다.
- 위 검증은 결함을 재현하기 위한 집중 리뷰다. 전체 사용자 흐름의 최종 인수, 교차 언어 대결 전체 조합, 이번 연결을 포함한 장시간 재검증, 엄격한 500ms 물리적 정지·Linux 격리·운영 용량 판정의 완료를 뜻하지 않는다.
