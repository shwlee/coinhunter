- 기준 커밋: `1acb5207940b5693adcc56201c0bbf1a2a0981be` — `feat: harden persistent C# runners and recover GC reservations`.
- 범위: 커밋의 직접 Node↔C# 채널, 할당/시간 제한, v2 진입 복구, 오류 판정·종료, 게임 자원 admission, 캐시 수명과 JS 입력 준비 변경. [구현·실측](csharp-gc-entry-recovery-2026-11-20.md).
- 방식: 커밋 후 정적 추적·추가 공격 입력·실제 호스트/캐시 재검사. 리뷰에서 제품 코드를 수정하지 않았다. [원시 검증](benchmarks/csharp-gc-entry-review-2026-11-20.json).

## 지적 사항

이번 범위에서 새로 재현해 보고할 **높음·중간·낮음 결함은 확인하지 못했다.** 아래 시험과 정적 검토 범위에 대한 결과이며 모든 입력/환경에서 결함이 없다는 증명은 아니다.

추가로 다음 경계를 코드에서 추적했다.

- GC 진입 재시도는 예약 단계에 한정된다. 사용자 호출 이전에 최대 두 번 예약하며 두 번째 실패 뒤에는 객체를 폐기한다. 정상 timeout만 같은 객체로 이어진다.
- 진입 비용은 `entryMs`와 실제 왕복/진행 시간에 남고, 사용자 구간의 GC 차이는 별도로 0을 검증한다. 호스트 정지/시작 감시는 사용자 500ms 판정과 분리된다.
- 실패한 GC 관측은 부모 소유자의 인증된 수명 채널에서 복구하며 정책과 관측 형태를 검사한다. 직접 채널/일반 데이터 채널 종료 경합에서 실제 자원 회수를 생략하지 않는다.
- 게임 전체 예약은 엔진·JS 자식·C# 실행기 한도를 포함하며 같은 참여자의 재시작 ticket을 재사용하지 않는다. 캐시 정리는 acquisition/publication gate와 활성 lease를 함께 확인한다.
- JS 입력 준비는 사용자 로드 전에 잡아둔 JSON 파서를 사용한다. 사용자 메서드/출력 변환은 계속 interrupt 가능한 호출 안에서 실행하며 외부 호스트 객체를 제공하지 않는다.

## 계속 남는 채택 조건

다음은 새로 발견한 회귀가 아니라 이미 명시한 미완료 관문이다.

- 정확한 500ms 선점은 입증되지 않았다. 현재 timeout 실측에도 소량의 실제 완료 초과가 있다. native/JIT/OS 스케줄링과 GC 진입의 별도 지연이 남는다.
- Linux cgroup·파일/네트워크 격리·외부 감독과 실제 배포 사양/장시간 다중 사용자 부하는 검증하지 않았다. 로컬 3분 통과만으로 운영 용량을 승인하지 않는다.
- C# 공개 지원과 GC/진입 복구 기본값은 계속 비활성이다. 공개 계정·경기/기록·UI 연결 전에 채택 관문을 통과해야 한다.
- 기존 레거시 다중 프로세스 계정 파일 잠금 EPERM은 이번 수정 대상이 아니다. 현재 Node 301건 통과를 해당 간헐 문제의 원인 수정으로 해석하지 않는다.

코드 커밋은 완료했으며 푸시는 수행하지 않았다. 이 리뷰 보고서와 증거는 커밋 후 별도로 작성했다.
