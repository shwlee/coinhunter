이는 **실험한 호스팅 방식의 판정**이다. C#/Python 언어 자체가 불가능하다는 결론이 아니다. 제한된 VM/Wasm·검증된 계측 등 다른 후보는 아직 검증하지 않았다. C++도 일반적인 네이티브 C++ 전체 호환을 의미하지 않는다.

제품 registry와 업로드/코드 검사/UI의 지원 언어는 JavaScript 하나를 유지했다. 실험용 호스트는 게임에 연결하지 않았다. 프로세스 재생성, 늦은 결과 무시, 턴 장벽, 계산 시간 보정으로 미통과 결과를 숨기지 않는다.

## 2. 실행 구조와 준비 범위

```text
실험 제어기(Node)
  ├─ JSONL IPC → .NET 10 호스트 → 준비된 DLL의 Player 1개
  ├─ JSONL IPC → CPython 호스트 → 최초 compile/exec한 Player 1개
  ├─ JSONL IPC → Python/Wasmtime 호스트 → 사전 컴파일 C++ Wasm Player 1개
  └─ 기존 JS 어댑터 → PlayerProcess/QuickJS Player 1개
```

각 호스트 안에서는 같은 객체의 메서드/함수를 직접 호출한다. 엔진과 호스트 사이의 비동기 IPC와 객체 메서드 호출을 구분한다. 제품용 `AlgorithmRunner`/`AlgorithmPreparer` 구현·산출물 캐시를 추가한 것은 아니다.

| 후보   | 준비/실행 형태                                                                                    | 의존성과 제약                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| C#     | 준비 시 DLL 빌드, 객체 생성·initialize/getName 1회. CLR JIT는 최초 경로에서 지연 발생 가능        | .NET 10.0.12, SDK 10.0.401. 무제한 일반 CLR 호스트를 샌드박스로 간주하지 않음                 |
| Python | 시작 시 소스 compile/exec·객체 생성/초기화, 이후 같은 메서드를 인터프리터로 실행                  | CPython 3.12.7, trace는 제한 장치 실험이며 보안 경계 아님                                     |
| C++    | WASI reactor로 사전 컴파일, Wasmtime 모듈 JIT·인스턴스 생성·초기화는 ready 전, 턴마다 export 호출 | WASI SDK 34.0, 포함 clang 23.1.0-rc3, Wasmtime Python 50.0.1. Linux/다른 CPU/상용 배포 미검증 |
| JS     | 기존 제품의 산출물 준비와 QuickJS 인스턴스 유지 경로 사용                                         | Node 18.20.2, quickjs-emscripten 0.32.0                                                       |

모든 후보에 대해 매 턴 원문 재로드/재컴파일/객체 재생성을 하지 않는다. 인터프리터 실행과 런타임 JIT까지 제거했다고 주장하지 않는다. C++ 호스트를 Python으로 만든 것은 기술 검증 편의이며 최종 어댑터 언어/배포 구조를 확정한 것이 아니다.

도구는 공식 배포 파일을 SHA-256으로 고정해 ignored `artifacts/runner-stage4-tools/`에만 내려받았다. 글로벌 SDK/Python 패키지/PATH를 변경하지 않았다. 약 590MB SDK 압축 파일과 8MB wheel, 압축 해제 공간이 필요하다. 제품 패키지 의존성은 추가하지 않았다. LLVM/WASI·Wasmtime 및 포함 라이브러리의 라이선스/고지는 실제 배포 산출물 선정 때 확인해야 한다.

## 3. 판정 방법

- 합성 Player만 사용했다. 실제 사용자 코드·계정·키·외부 AI·실제 데이터 파일에 접근하지 않았다. 파일 접근 검사는 실험이 만든 `probe-sentinel.txt`만 사용했다. 소켓은 생성/폐기만 하며 외부 접속하지 않았다.
- 정상 호출 → 필드 `saved=3` 변경 후 문제 연산 → 실제 500ms 중단 → 정상 호출의 방향 `3`과 호출 횟수/동일 PID·인스턴스 ID·생성/초기화 횟수를 확인했다. JS는 제품의 run/instance ID와 debug 필드 기록을 이용한다. ID가 같아도 다음 호출이 실패하면 유효한 재사용 통과가 아니다.
- 제품과 구분된 부모 watchdog 1500ms를 두었다. 미복귀 호스트를 종료한 결과는 **실패한 실험의 정리**이며 정상 턴 timeout 성공이 아니다. Task 대기만 만료된 경우는 재호출하지 않고 inspect로 계속 실행 중임을 확인했다.
- 500ms는 실제 경과 시간 기준이다. 타이머/OS 스케줄링으로 응답이 조금 늦게 관측될 수 있으며 정확히 500.000ms에 반환한다는 보장이 아니다. fuel/명령 수를 500ms로 환산하지 않았다.
- 상태 변경 자동 롤백을 요구하거나 수행하지 않는다. C++ ABI 스택 복원은 호스트 호출 프레임을 정리하는 제한된 실험이며 Player/힙 재생성과 다르다.

총 **56개 사례, 2개 독립 진행 사례, 4개 컴파일/준비 사례**를 기록했다. `runner:gate:check`는 실패가 성공으로 둔갑하지 않았는지 포함해 실측 자료의 불변 조건을 검사한다. 이 검사 통과는 새 언어 채택 통과를 의미하지 않는다.

## 4. 중단·상태·격리 결과

### C#

`Task.WhenAny`에서 대기를 만료시키고 CancellationToken을 취소해도 무한 루프의 `active=1`과 heartbeat 증가가 계속된다. 취소를 관찰하지 않는 코드는 멈추지 않는다.

현대 .NET에는 비협조적 중단을 시도하는 `ControlledExecution.Run`도 있다. 따라서 단순히 “Task 취소만 가능하다”라고 설명하면 부정확하다. 다만 이 API는 폐기 예정 경고 대상이며 프로세스 손상과 중단 지연 가능성이 공식적으로 명시돼 있다. 실험에서 단순 루프는 중단됐지만 catch/finally 내부 루프와 `Thread.Sleep(2000)`은 watchdog까지 돌아오지 않았다. 깊은 재귀에서도 stack overflow 진단 후 정상 응답을 얻지 못했다. [공식 API 경고와 제한](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.controlledexecution.run?view=net-10.0).

40MiB 배열 할당·소유한 sentinel 읽기·스레드·소켓 생성이 허용됐다. 이는 호스트 프로세스 분리만으로 알고리즘별 API/메모리 격리가 확보되지 않음을 보여준다. 실험용 경고 억제는 독립 probe 프로젝트에만 한정했다.

### Python

trace 예외로 단순 루프를 중단한 뒤 같은 객체를 재호출할 수 있었다. 그러나 사용자 `except BaseException`/finally 안에서 계속 실행하거나 긴 정규식 표준 라이브러리 연산에 들어가면 watchdog까지 복귀하지 않았다. 추적 함수에서 오류가 나면 추적이 해제될 수 있는 동작과 일치한다. [sys.settrace 문서](https://docs.python.org/3.12/library/sys.html#sys.settrace).

재귀는 `RecursionError` 후 정상 호출로 복귀했다. 40MiB 할당·sentinel·스레드·소켓은 허용됐다. `sys.settrace`·일부 builtins 제거만으로 임의 Python을 안전하게 호스팅한다고 판단하지 않는다.

### C++ / Wasm

epoch 중단은 일반 루프·try/catch 루프·RAII 범위 내부 루프·긴 **Wasm 내부** 연산에서 발동했다. 마지막 사례를 네이티브 호스트 함수까지 중단한 것으로 해석하면 안 된다. 별도 WAT에서 의도적으로 추가한 2초 blocking host import는 epoch가 지나도 돌아오지 않아 watchdog 실패였다. 제품에서는 이런 import를 허용할 수 없다. [Wasmtime 중단 모델](https://docs.wasmtime.dev/examples-interrupting-wasm.html).

스택 복원이 없는 프로필은 재귀 트랩 뒤 `__stack_pointer`가 262144에서 음수가 됐고 다음 정상 호출도 out-of-bounds로 실패했다. 스택 복원 프로필은 정상 재호출이 가능했지만, 다음 문제가 남는다.

- RAII 1MiB 할당 중 중단을 6회 반복하면 소멸자가 호출되지 않았다. 미정리 자원 6개·6MiB를 기록했고 실제 선형 메모리도 약 0.31MiB에서 **6.31MiB**까지 증가했다. 단순 카운터가 아니라 메모리 증가와 escaped buffer 주소를 함께 확인했다.
- 스택만 복구해도 힙/컨테이너/정적 초기화/라이브러리 내부 상태가 임의 중단에 항상 유효해지는 것은 아니다. 영속 필드와 임시 할당을 구분한 allocator/허용 API 규약 등 추가 후보가 필요하다. 아직 구현·검증하지 않았다.
- 32MiB 선형 메모리 한도에서 40MiB 할당은 실패해 `bad_alloc` 경로로 -1을 반환했고 재호출은 성공했다. 이는 호스트 프로세스 RSS 전체의 32MiB 제한을 의미하지 않는다.
- WASI에 환경/표준입출력/디렉터리 preopen을 상속하지 않아 sentinel 파일 열기는 거부됐다. threads feature는 껐고 외부 소켓을 넘기지 않았다. `std::thread` 코드는 컴파일·링크됐으므로 구문 차단이나 실제 스레드 성공을 의미하지 않는다. 실행 시 거부·오류 분류는 후속 검증 대상이다.
- `--stack-first` 명시 여부 두 바이너리를 별도 실행했다. 두 프로필 모두 같은 초기 스택 값과 재귀 트랩을 보였으므로 이 옵션만으로 안전성이 확보됐다고 해석하지 않는다.

WASI API 전체를 곧바로 허용하지 않고, 메모리 외 host import·테이블/스택·출력·초기화·컴파일 자원 한도를 함께 정해야 한다. 참고: [WASI SDK](https://github.com/WebAssembly/wasi-sdk), [C++ 예외 빌드 옵션](https://github.com/WebAssembly/wasi-sdk/blob/main/CppExceptions.md), [Wasmtime Python 바인딩](https://github.com/bytecodealliance/wasmtime-py).

### 컴파일과 기존 JS에서 발견한 문제

잘못된 C++ 구문은 거부됐다. 하지만 준비 호스트를 별도 샌드박스로 감싸지 않은 상태에서는 전처리기가 절대 경로로 **실험 소유 sentinel**을 읽을 수 있었다. 실행 시 WASI 파일 제한과 컴파일 시 파일 제한은 별개다. 이 상태로 사용자 업로드를 컴파일하지 않는다. 컴파일 시간/메모리/출력/임시 디스크·악성 입력 전체 검증은 미완료다.

기존 JS는 네 가지 중단·상태 유지 사례와 메모리 예외 후 재호출이 통과했다. 다만 깊은 재귀 입력은 현재 어댑터에서 `protocol-error`가 발생했다. 일반 사용자 예외와 런타임/프로토콜 장애의 분류·호스트 상태 확인이 필요하다. 이번 연구 변경에서 제품 코드를 임의 수정하지 않았으며 후속 수정 항목으로 남긴다.

## 5. 호출 비용과 독립 진행

12×10·20×16·40×30 각각 무연산/전체 배열 읽기를 30회 예열 후 150회 측정했다. 4개 프로필 × 3개 크기 × 2개 연산 = **24개 셀·3600회 측정**이며 p50/p95/p99/max를 원본에 보관했다.

**이 자료로 언어별 순위를 매기거나 공정성 검증 완료를 선언하지 않는다.** JS는 제품 어댑터/입력 검증을 사용하지만 다른 호스트는 최소 실험이다. JS의 execution에는 guest JSON.parse가 포함되며 C#/Python JSON parse와 C++ 입력 packing은 해당 실행 타이머 밖이다. Wasmtime Python FFI/타이머 비용도 섞여 있다. CLR JIT는 지연 발생 가능성이 있고 예열은 모든 사용자 코드 경로를 보장하지 않는다. roundTrip 역시 OS 스케줄링·호스트 구현의 영향을 포함한다.

20×16 입력의 실험용 end-to-end roundTrip 참고값(ms):

| 프로필                        | 무연산 p50 / p95 | 배열 읽기 p50 / p95 |
| ----------------------------- | ---------------- | ------------------- |
| 제품 JS / QuickJS             | 0.324 / 0.614    | 0.465 / 0.764       |
| C# / ControlledExecution 실험 | 0.148 / 0.251    | 0.139 / 0.182       |
| CPython trace 실험            | 0.129 / 0.213    | 0.133 / 0.202       |
| C++ / Wasmtime Python 실험    | 0.541 / 0.712    | 0.529 / 0.600       |

무연산과 읽기 결과의 일부 역전도 이 작은 표본/호스트 잡음의 영향이다. 보류된 호스트가 짧은 호출에서 빠르더라도 중단/격리 관문 통과를 대신할 수 없다.

공정성 후속은 정식 어댑터의 동일 직렬화/입력 검증·계측 경계를 정리한 뒤 입력 준비/IPC/guest 실행/응답을 비교하는 것이다. 인프라 편차를 줄이되 계산이 빠른 플레이어를 기다리게 하거나 논리 시간으로 보정하지 않는다.

별도 프로세스의 C# 느린 루프/Python 빠른 응답, C++ 느린 루프/JS 빠른 응답을 동시에 요청한 두 사례 모두 빠른 결과가 먼저 반환됐고 느린 호출은 timeout 후 동일 객체로 재호출됐다. 제품 엔진의 독립 진행 회귀는 [3단계](runner-stage3-results.md)를 기준으로 유지한다. 이것이 임의 과부하에서도 CPU 경쟁이 없다는 보장은 아니다.

## 6. 다음 관문과 완료 범위

1. **기존 JS 재귀 오류 분류 보완**: 사용자 예외인지 치명적 VM 장애인지 구분하고 동일 객체 재사용 가능성을 시험한다. 실제 작업은 별도 변경으로 진행한다.
2. **C# 우선 후보 재선정**: 제한 VM/계측 또는 Wasm 호스팅의 문법·라이브러리·중단·필드 일관성 검증. 일반 CLR + Task/ControlledExecution을 제품으로 올리지 않는다.
3. **C++ 추가 검증**: 자원 누적과 힙 일관성, 허용 라이브러리·blocking import, 런타임 스레드 거부, 샌드박스 컴파일과 반복 실패를 검증한다.
4. **Python 대체 VM 검증**: CPython trace 외의 중단/격리 방법을 선정해야 한다.
5. 채택 관문을 통과한 언어만 5단계 준비/산출물 캐시와 6단계 정식 실행기로 진행한다.

이번 단계의 결과는 재현 가능한 실험·원본·보류/조건부 판정이다. 제품 다국어 지원, 배포 가능 샌드박스, 컴파일 보안 전체 검증은 완료하지 않았다. 사용자 서버/계정 데이터와 기존 게임 규칙을 변경하지 않았다.

검증: 실제 실험 실행 완료, 원본 불변 조건 11개 검사 통과, 기존 runtime/runner-contract/javascript-runner 37건 통과. 신규 스크립트/문서 형식, Python 구문, 원본/소스 해시 일치도 확인했다. 제품 코드 변경이 없으므로 전체 웹/OAuth/운영 BE 회귀를 다시 실행한 것으로 표시하지 않는다.
