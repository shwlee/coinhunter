## 1. 실제 게임 연결

[실행 관리자](../backend/src/CoinHunter.Execution.Host/Services/ExecutionManager.cs)가 내부 후보 요청을 수락할 때 GC 설정과 자원 계획을 고정한다. 합산 예산이 부족하면 소스 복사·컴파일·게임 프로세스 시작 전에 거절한다. 이후 설정을 바꿔도 이미 수락한 게임의 launch는 바뀌지 않는다.

GC 게임은 엔진 자식 scope와 C# 참여자별 자식 scope를 사용한다. JavaScript 실행기는 별도 Node 자식 프로세스이므로 엔진 scope의 프로세스 한도에 `1 + JavaScript 참여자 수`를 포함한다. 이 부분은 실제 혼합 게임의 초기 검증에서 발견해 수정했다. 전역 회계는 부모 게임 예약 한 번만 반영하며 참여자 launch를 재사용하지 않는다.

정상 호출은 기존 Node→C# 직접 채널을 유지한다. 검증한 GC 관측은 `runtime-observation` 이벤트에 플레이어·턴·호출·인스턴스 식별자와 함께 기록한다. GC 예약/구간/호스트 할당 실패로 직접 연결이 끊기면 별도 lifecycle 소유자가 확인한 종료 사유를 조회한다. 조회는 실패 경로에만 추가하며 정상 호출의 왕복 횟수는 늘리지 않는다.

GC 실패는 JSONL의 `runtime-failure.infrastructureFailure`, 최종 경기 결과와 fsync receipt의 `reason`에 같은 허용된 코드를 사용한다. 사용자 `timeout`이나 제자리 패널티 결과를 만들어내지 않는다. 실제 종료와 자원/lease 회수를 확인한 뒤 게임을 닫는다.

## 2. 실행·재사용 정책

| 결과                            | 현재 턴/게임 처리                       | 객체 재사용                 |
| ------------------------------- | --------------------------------------- | --------------------------- |
| 정상 방향 / `-1`                | 반환 방향 / 제자리 액션                 | 유지                        |
| 500ms 시간 초과                 | 실제 중단 완료 후 해당 턴의 제자리 액션 | 같은 PID·인스턴스·필드 유지 |
| 잘못된 방향                     | 해당 턴의 제자리 액션                   | 유지                        |
| 사용자 예외·연산/할당 한도 초과 | 진단을 기록하고 게임 실패 종료          | 금지, 자동 재시작 없음      |
| GC 예약·구간·호스트 환경 실패   | 인프라 사유로 게임 실패 종료            | 금지, 사용자 패널티 아님    |

치명적 오류가 발생한 뒤 정리 시각이 500ms를 넘으면 기존 판정이 이를 정상 timeout처럼 보고할 수 있는 경계를 보완했다. `exception`/`operation-limit`을 유지하고 부모도 `failed` 상태로 전환해 다음 호출을 받지 않는다. 실제 별도 호스트에 501ms 이후 오류를 발생시켜 IPC 판정과 회수를 검증한다. 이것은 사용자 코드가 시계/예외 처리를 쓰도록 허용한 기능이 아니라 내부 시험 주입이다.

500ms는 여전히 호출별 판정 기준이다. 실제 정지가 정확히 500ms에 이루어진다는 보장은 성립하지 않는다. 측정한 정상 timeout의 작은 초과와 native/JIT/스케줄링 경계는 남겨 둔다. 제한을 완화하거나 고정 라운드·공통 대기·시간 보정으로 숨기지 않는다.

## 3. 실제 동시 게임과 부하

- 허용 최대 맵 40×30, 게임 2개. 각 게임 C# 2명과 JavaScript 1명으로 실제 엔진·알고리즘 프로세스를 사용한다.
- C# 객체당 128MiB 상태를 초기화 때 보유하고 매 턴 64KiB 배열을 추가 할당한다. 50ms 액션, 4번째 잘못된 방향, 6번째 500ms timeout, 7번째 필드 유지 결과를 확인한다.
- GC 호스트 한도 768MiB, 엔진 그룹 512MiB, 부모 게임 예약 2,304MiB, 시험 전체 예산 8,192MiB다. 배포 권장 사양이나 새 서비스 기본값이 아니다.
- 매초 부모 OS 관측·턴 수·전역 예약을 수집하고 DLL 파일이 턴 중 다시 컴파일되지 않는지 확인한다. 종료 시 완결 JSONL·결과 receipt·자원 예약 0을 대조한다.

첫 180초 목표 시험은 합계 8,714턴을 처리한 뒤 약 97초에 `gc-reservation-unavailable`로 종료됐다. C# 4개 객체에서 합계 5,798개의 정상 GC 구간 관측을 남겼으며 정상 timeout 뒤 동일 객체의 필드가 유지됐다. 게임별 관측 peak는 약 1,310/1,312MiB였다. 실제 게임 전체 예약을 모두 소모하기 전에도 CLR의 NoGC 예약은 실패할 수 있다. 이 결과를 성공한 3분 부하 시험으로 표시하지 않는다.

추가 CPU 상한 조건과 최종 결과/회귀 수는 검증 JSON에 별도로 보관한다. Windows CPU rate 2500/10000은 OS 상한 설정이지 전용 코어 예약이 아니다. 로컬의 분 단위 시험은 운영 장시간·다중 사용자 용량 검증을 대체하지 않는다.

| 시험                          | 목표/실행 시간          | 알고리즘 결과 / GC 관측 | 판정                     |
| ----------------------------- | ----------------------- | ----------------------- | ------------------------ |
| 첫 실제 2게임 부하, CPU 10000 | 180초 목표 / 약 97.12초 | 8,714 / 5,798           | GC 예약 실패로 조기 종료 |
| CPU 상한 2500의 별도 2게임    | 60초 목표 / 약 61.52초  | 5,522 / 3,670           | 제한된 60초 조건 통과    |
| 최종 재검증, CPU 10000        | 180초 목표 / 약 96.14초 | 8,711 / 5,797           | 같은 GC 예약 실패 재현   |

두 180초 목표 시험 모두 참여 객체의 timeout 뒤 필드 유지와 완결 JSONL/결과를 확인했다. 최종 timeout의 실제 완료는 약 500.20~500.25ms였으며 정확한 500ms 선점 보장을 주장하지 않는다. 각각의 검증 종료 후 전역 예약 메모리/프로세스는 0이다.

## 회귀와 최종 확인

- 전체 BE 회귀: 통과. C# budget 293건·추가 settlement 정책 7건·기존 실제 게임 39건·직접 채널 10,022건·운영/실행 통합 13그룹·프로토콜 통합 5건 포함.
- 새 실제 GC 게임 기능 검사: 최종 36건 통과. 부하 관문 실패와 구분한다.
- Node 전체: 300건 중 299건 통과·1건 실패. 기존 레거시 계정 파일 잠금의 다중 프로세스 `EPERM` 간헐 실패다. 해당 파일 독립 재검사 9건은 통과했으며 잠금 코드 자체는 수정하지 않았다. 전체 통과로 표시하지 않는다.
- C# Node 어댑터 집중 검사: 8건 통과. 정상 경로 추가 왕복 없음, 누락/유실/잘못된 GC 관측 거절, 허용된 종료 사유만 복구하는 동작을 확인한다.
- 종료 직전의 유효한 실패 프레임을 일반 process-exit 사유가 먼저 덮지 않도록 부모의 stdout 처리를 제한 시간 안에서 기다린다. 전체 회귀 뒤 추가한 이 경로와 수락 거절 시 timer 정리는 마지막 parent manager·실제 게임 smoke로 재확인한다. 마지막 smoke는 부하 판정용이 아니다.
- 마지막 빌드 경고·오류 0개. 원시 관측과 회귀·마지막 재확인의 실제 수는 검증 JSON에 보관한다.

## 다음 판정

실제 연결·실행 정책 구현과 로컬 부하 측정은 수행했다. GC 정책은 장시간 채택 조건을 통과하지 못했다. 반복 예약의 heap/단편화/구간 진입 정책을 추가 분석해야 하며, 예약량을 무조건 늘리거나 실패 때 프로세스를 재시작하지 않는다. 강제 GC나 별도 대기를 추가해 계산/진행 비용을 측정에서 숨기지도 않는다. 정책을 변경한다면 그 비용을 전체 왕복/진행 속도에 반영해 다시 비교해야 한다.

Linux 격리, 실제 배포 자원 정책·운영 부하와 C# 공개 계정/기록/UI 연결은 후속이다. 사용자 서버·계정·파일과 환경 설정은 변경하지 않았다. 커밋/푸시는 수행하지 않았다.

부하 명령은 기능 검증 통과와 별개로 목표 시간 전에 종료되면 exit 2다. `completed`는 검증 절차 완료, `soakPassed`는 부하 조건 통과를 의미한다. 예외/검증 실패는 exit 1이며 원시 결과는 격리된 `artifacts`에 남는다.
