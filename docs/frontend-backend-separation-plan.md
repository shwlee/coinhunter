실행 영역 분리 시 [실행기 추상화·독립 실행 계획](algorithm-runner-independence-plan.md)을 함께 적용한다. 플레이어별 준비된 인스턴스·비동기 실행 계약·실제 완료에 따른 즉시 액션/다음 턴·500ms 중단 후 재사용을 유지하고, 호스팅/IPC 선택과 별개로 호출 비용을 분해·최적화한다. 공통 판단 지연과 논리 시간 스케줄러는 구현 항목에서 제외한다.

## 1. 범위와 기본 결정

사용자는 하나의 서비스 주소에 접속한다. FE 웹서버는 HTML·JS·CSS·이미지·영상을 제공하고 `/api/*`를 내부 BE로 전달한다. BE는 인증·권한·데이터·경기·알고리즘 실행·외부 AI 연결을 담당한다. 브라우저의 `/api/...` 상대 경로와 기존 페이지 주소를 유지한다.

첫 구현은 기존 Node.js 실행 환경을 활용한 얇은 FE 웹서버를 기준으로 한다. 정적 파일 제공, 페이지 진입 제어, CSP nonce 삽입, 고정 BE로의 프록시만 담당한다. FE가 별도 계정 저장소나 게임 로직을 갖지 않게 한다. 이후 배포 환경에 따라 전용 웹서버를 앞에 둘 수 있도록 외부 주소와 내부 연결 설정을 분리한다.

저장소는 하나로 유지한다. FE·BE는 별도 진입점과 배포 산출물을 가지며, 공통 코드는 빌드 시 포함한다. 첫 단계에서 별도 저장소·프런트엔드 프레임워크·CORS 기반 별도 도메인·DB 교체·BE 다중화·게임 실행 서비스 분리는 도입하지 않는다.

기존 **사내 단일 호스트·단일 컨테이너 운영 목표**와 양립하도록 설계한다. 로컬에서는 FE/BE 두 프로세스로 검증하고, 한 컨테이너에서도 프로세스 관리자 아래 함께 실행할 수 있는 진입점을 준비한다. 컨테이너 이미지·프로세스 관리자 선정과 실제 패키징은 배포 단계에서 수행한다. 이후 두 컨테이너나 다른 호스트에 배치해도 브라우저 주소와 API 경로를 바꾸지 않는 것이 목표다.

## 2. 목표 구조와 책임

```text
사용자 브라우저
      │ 단일 서비스 주소 (개발 HTTP / 운영 HTTPS)
      ▼
FE 웹서버
 ├─ /, /signin, /signup, /game, /editor, /admin, /admin/maps, /admin/maps/editor
 ├─ 공개 정적 파일·에디터 빌드 결과·게임 에셋
 ├─ 페이지 진입 제어 / 보안 헤더 / 편집기 nonce 삽입
 └─ /api/* → 설정된 내부 BE로 전달
                    ▼
BE Node.js 서버 (첫 구성은 인스턴스 하나)
 ├─ 로그인·Google OAuth·세션·권한·소유권 검사
 ├─ 알고리즘·맵·경기 기록·AI API
 ├─ 경기 상태와 SSE
 ├─ 플레이어별 알고리즘 실행 프로세스
 └─ 기존 저장 어댑터·코드 파일·임시 업로드·자격 증명 저장소
```

| 영역          | FE                                          | BE                                |
| ------------- | ------------------------------------------- | --------------------------------- |
| 화면과 자산   | 제공·표현                                   | 일반 정적 파일 제공 종료          |
| 페이지 진입   | BE 세션을 조회해 로그인 이동·접근 거부 표시 | 사용자·역할·이용 상태의 최종 판단 |
| API           | 고정 내부 주소로 전달                       | 입력·권한 검사와 처리             |
| 경기·알고리즘 | 화면 표시와 요청                            | 현재 엔진·프로세스 수명 유지      |
| 데이터·비밀   | 영구 저장하지 않음                          | 기존 위치·소유권·수명 유지        |
| 공통 규약     | 빌드된 공개 모듈 사용                       | 같은 원본의 순수 모듈 사용        |

## 3. 현재 코드에서 변경할 지점

- `src/server.js`: 정적 파일 경로 표, HTML 제공·nonce 삽입, 페이지 접근 제어를 FE로 분리한다. BE의 API·경기 관리와 종료 처리는 유지한다.
- `scripts/start.js`: FE·BE 개별 실행과 함께 실행하는 로컬 진입점을 구성한다. 편집기 빌드와 실행 순서를 명확히 한다.
- `src/auth/*`, `src/ai/routes.js`: localhost·HTTP·현재 수신 포트에 묶인 Host/Origin 검사를 공통 요청 주소 정책으로 정리한다. OAuth 콜백 Host 검사와 쿠키 설정도 같은 공개 주소를 기준으로 처리한다.
- `public/editor.html`, `src/web/code-editor.js`: FE에서 응답별 nonce를 HTML·CSP 헤더·CodeMirror 스타일에 일치시킨다. 보안을 느슨하게 만드는 `unsafe-inline` 추가로 해결하지 않는다.
- `public/account.js`, `public/app.js`, `public/ai-scripting.js` 등: API 상대 경로를 유지하고 프록시 경유 쿠키·업로드·SSE가 동작하는지 검증한다.
- BE가 `public`에서 가져오는 캐릭터 정의, 전략 템플릿·입력 규칙, 맵 배열 파서·관련 타일 상수를 공통 영역으로 옮긴다. 공통 모듈의 의존성도 함께 점검한다.
- 기존 파일 저장 어댑터·코드 파일 위치는 변경하지 않는다. FE에는 `.env`, `data`, 코드 원문 저장 디렉터리, Google secret, AI 키·암호화 키를 배포하지 않는다.

## 4. 외부 주소·신뢰 경계 계약

외부 공개 주소, FE 수신 주소, 내부 BE 주소, BE 수신 주소, 신뢰할 프록시 범위를 각각 설정한다. 변수명은 2단계 구현에서 확정하고 비밀 없는 설정 예제와 시작 시 검증을 함께 제공한다. 현재 `.env`를 임의로 수정하거나 실제 운영 도메인을 미리 정하지 않는다.

1. **단일 공개 주소:** 브라우저 Origin·로그인 콜백·복귀 주소·쿠키 보안 옵션이 같은 설정을 사용한다. 개발용 localhost HTTP와 운영용 HTTPS를 명시적으로 구분한다.
2. **프록시 신뢰:** BE는 허용된 FE 연결에서만 전달 주소를 사용한다. FE는 클라이언트가 보낸 `Forwarded`·`X-Forwarded-*`를 그대로 신뢰하지 않고 필요한 값을 재설정한다. 임의 Host·외부 목적지·절대 URL로 프록시하지 않는다. 운영 BE 포트는 브라우저에 직접 공개하지 않는다.
3. **요청 보호:** Host 허용 목록과 변경 요청의 Origin 정책을 공통화한다. Origin 누락·`null`·잘못된 스킴·다른 출처를 명시적으로 처리한다. Google 콜백의 외부 이동 GET은 별도 OAuth state·브라우저 결합 검증을 유지한다. CORS 전체 허용으로 우회하지 않는다.
4. **쿠키:** 인증·OAuth·게스트 쿠키의 `Set-Cookie`를 여러 헤더로 보존하고 경로·HttpOnly·SameSite를 유지한다. 운영 HTTPS의 Secure를 로그인 방식과 독립적으로 적용한다. 현재 세션 종류별 SameSite 차이를 하나로 뭉개지 않는다.
5. **주소·제한:** 로그인 등의 요청 제한에서 모든 사용자가 FE 한 명으로 집계되지 않도록 신뢰 경계 안에서 클라이언트 주소를 전달한다. 외부 헤더로 제한을 우회할 수 없도록 검증한다.
6. **로그:** 프록시는 요청/응답 본문, 쿠키·인증 헤더, OAuth 쿼리의 code/state, 코드·AI 입력·키를 로그에 남기지 않는다. 관측 항목은 상태·지연·연결 수 등 필요한 값으로 제한한다.

## 5. 단계별 작업 순서

### 1단계 — 공통 코드와 제공 경로 분리

- `src/shared` 등 공통 영역에 브라우저·서버 모두 사용할 순수 코드를 정리한다. Node 전용 API와 DOM 의존성을 넣지 않는다.
- 브라우저의 기존 모듈 URL을 유지할 매핑 또는 빌드 산출물을 구성한다. 소스 폴더 전체를 공개하지 않는다.
- 정적 파일·페이지 경로를 명시적인 목록으로 분리하고 FE로 이전할 대상을 확정한다. 테스트의 기존 import 경로도 갱신한다.
- **완료 기준:** 기존 통합 실행이 정상이며 BE의 공통 규칙 코드가 `public` 소스 배치에 의존하지 않는다. 맵 배열·캐릭터·전략 규약 검사 통과.

### 2단계 — 공개 주소와 요청 검증 통합

- 개발 직접 접속과 FE 경유 접속의 요청 컨텍스트를 정의한다. 인증·AI·일반 API가 같은 Host/Origin·HTTPS 판단을 사용하게 한다.
- OAuth callback과 공개 주소 일치를 시작 시 검사한다. 잘못된 신뢰 프록시·내부 주소·운영 HTTP 설정은 시작 전에 거부한다.
- 쿠키의 Secure·프록시 신뢰·클라이언트 주소와 요청 제한 처리를 연결한다.
- **완료 기준:** 기존 로컬 인증과 API를 유지하면서 외부 Host·전달 헤더 위조·잘못된 Origin을 거부한다. HTTP 개발·HTTPS 프록시 시나리오의 자동 검사 통과.

### 3단계 — FE 웹서버와 API 프록시 구현

- 별도 FE 진입점을 추가하고 허용된 정적 파일·페이지 경로만 제공한다. FE가 사용자 입력 경로로 저장 파일을 읽지 않게 한다.
- `/api/*`를 고정 BE 주소로 전달한다. 본문·응답을 스트리밍하고 메서드·쿼리·콘텐츠 유형·상태·다운로드 헤더·복수 쿠키를 보존한다. 연결 전용 헤더는 전달 규칙에 맞게 처리한다.
- API 오류를 HTML로 바꾸거나 API 404를 홈 화면으로 대체하지 않는다. BE 미접속·시간 초과는 비밀 없는 오류로 구분한다.
- **완료 기준:** 별도 포트의 FE/BE로 맵 조회·세션·코드 검사·맵 배열 전송·알고리즘 업로드가 동작한다. 파일 경로 조작과 임의 대상 프록시가 차단된다.

### 4단계 — 페이지 접근과 편집기 보안 이전

- FE가 BE의 기존 세션 API를 조회해 홈·편집기·관리자 페이지의 로그인 이동, next 경로, 403 동작을 유지한다. 사용자·역할을 FE 저장소에 복제하지 않는다.
- BE 장애 시 보호 페이지는 오류를 표시하며 미인증·관리자로 임의 간주하지 않는다. API의 권한 검사는 BE에서 항상 독립적으로 수행한다.
- nonce 생성·보안 헤더·편집기 HTML 삽입을 FE로 옮긴다. API 응답의 BE 보안 헤더와 FE 페이지 헤더 책임을 구분한다.
- 로그인·계정·보호 HTML·API는 no-store를 유지한다. 정적 자산 캐시 정책은 코드/에셋 버전 일치와 함께 정의한다.
- **완료 기준:** Google 로그인 왕복, 로그아웃·관리자 이용 중지·비관리자 차단, 편집기 스타일과 테스트 iframe의 같은 Origin 통신이 동작한다. 키·데이터 디렉터리·BE 소스가 FE로 노출되지 않는다.

### 5단계 — SSE·취소·장시간 전송 검증

- 경기와 AI SSE를 즉시 전달하고 프록시 버퍼링·압축 지연을 피한다. heartbeat, 재연결, 오류·종료와 느린 수신자 처리를 유지한다.
- 일반 API·업로드·SSE의 시간 제한을 분리한다. 알고리즘 파일에 임의의 작은 크기 상한을 추가하지 않고 기존 디스크·동시 업로드 보호를 유지한다.
- 브라우저 연결 중단을 BE 요청에 전달해 코드 검사·업로드·AI 스트림 자원이 정리되게 한다. 경기 SSE 단절만으로 경기를 종료하지 않는다. 단순 SSE 재연결로 새 유료 AI 요청을 만들지 않는다.
- **완료 기준:** 실제 경기의 점수·아이템·결과·기록 갱신과 AI 진행 이벤트가 지연 누적 없이 표시된다. 연결 단절·재연결·취소 후 불필요한 연결·파일·프로세스가 남지 않는다.

### 6단계 — 실행·빌드·배포 경계 정리

- 개별 FE/BE 실행 명령과 로컬 동시 실행 명령을 제공한다. 기존 `npm start`의 최종 동작을 명시하고 포트 충돌·BE 준비 실패·종료 신호를 처리한다.
- FE와 BE 산출물에 필요한 파일만 포함한다. FE 빌드와 실행 환경에는 허용한 공개/연결 설정만 전달하고 Google·AI 비밀을 상속하지 않는다. BE는 공통 모듈·샘플·규약·런타임 의존성을 빠뜨리지 않는다.
- FE만 재시작할 때 BE 세션·경기가 유지되는 것을 검증한다. BE 재시작 시 현재 메모리 세션·진행 경기가 유지되지 않는 한계는 문서화한다.
- 한 컨테이너의 두 서버와 플레이어 자식 프로세스를 추후 프로세스 관리자로 관리할 수 있도록 종료·준비 상태 계약을 문서화한다. 실제 Docker 구성은 별도 배포 작업으로 남긴다.
- **완료 기준:** 비밀 없는 설정 예제로 기존 Windows 개발 환경에서 실행·종료 가능하고, 한쪽 서버 실패가 조용히 방치되지 않는다. 다른 호스트의 BE를 설정할 수 있는 배포 계약을 갖춘다.

### 7단계 — 통합 검증·리뷰·전환

- 기존 통합 서버 경로의 검증과 새 FE 경유 검증을 비교하고 필수 브라우저 검사를 FE 주소로 실행한다. 검증 스크립트가 BE에 직접 접속해 분리 문제를 놓치지 않게 한다.
- 게스트 경기, 로그인·알고리즘 저장, 프롬프트·코드 가져오기, 테스트 플레이, AI 연결, 관리자 맵 작성·옵션·배열/JSON 전송·게시 전체 흐름을 확인한다.
- 외부 OAuth/AI는 우선 대체 응답으로 검증한다. 실제 Google·기등록 AI의 최종 확인은 사용자가 할 수 있도록 절차를 제공한다. 자동 검사에서 기존 키를 읽거나 유료 호출하지 않는다.
- 로컬에서 동시 경기·정적 자산 전송·SSE가 겹칠 때 지연·연결 수·메모리를 측정하고 기존 결과와 비교한다. 분리만으로 BE 경기 수용량이 증가했다고 간주하지 않는다.
- 높은/중간 결함을 검토·수정하고 실행법·설정·아키텍처·API·검증 결과를 갱신한다. 새 경로 검증 전에는 기존 실행 경로로 복구할 수 있게 유지한다.
- **완료 기준:** 아래 완료 조건을 충족하고 FE/BE 분리가 기본 실행에 반영된다. 통합 제공 코드의 임시 호환 경로 정리 여부와 남은 배포 한계를 기록한다.

## 6. 최종 완료 조건

- [ ] 단일 FE 주소에서 기존 화면·API·로그인·경기·관리 기능을 사용할 수 있다.
- [ ] FE/BE를 독립 포트와 프로세스로 실행하고 각각 종료·재시작할 수 있다.
- [ ] BE는 일반 화면·이미지·스크립트를 제공하지 않고 FE는 사용자 데이터·비밀을 보관하지 않는다.
- [ ] API 권한·소유권 검사는 BE에서 유지되며 프록시 헤더·Host·Origin 위조가 거부된다.
- [ ] OAuth 왕복·복수 Set-Cookie·HTTPS Secure·관리자 접근·로그아웃이 일관되게 동작한다.
- [ ] 편집기 CSP nonce와 iframe 통신을 유지하며 보안 정책을 느슨하게 하지 않는다.
- [ ] 코드 업로드·검사·SSE·취소·재연결이 프록시 경유로 검증된다.
- [ ] FE만 재시작해도 BE 경기와 인증 상태가 유지되고 재접속할 수 있다.
- [ ] 기존 코드·맵·옵션·기록 저장 형식과 사용자 데이터에 마이그레이션이 필요하지 않는다.
- [ ] 새 실행 명령·설정 예제·검증 절차·복구 방법이 문서화된다.

## 7. 후속 작업과 제약

BE는 하나의 인스턴스를 유지한다. 로그인 세션, OAuth 진행 상태, 경기와 일부 AI 요청 상태가 메모리에 있으므로 FE 분리만으로 BE 다중화를 제공하지 않는다. 여러 BE 인스턴스 운영은 공유 세션·경기 배치·저장소 동시성 등의 별도 작업이다.

실제 운영 도메인, VPN·TLS 종료 위치, 방화벽·허용 포트, Google/AI 외부 통신, 컨테이너 이미지와 운영 프로세스 관리자는 배포 검증에서 확정한다. 로컬 분리 검증은 실제 사내 배포 검증을 대신하지 않는다.

개인정보 운영 준비는 기존 합의대로 실제 서비스 개시 전 마지막 필수 단계다. 이번에는 새 저장소를 추가하지 않고 로그 최소화·비밀 분리·사용자 데이터의 BE 보관 경계를 적용한다. 정책·사용자 안내·삭제 요청 전체 기능의 본격 구현을 앞당기지 않는다.
