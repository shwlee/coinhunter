# AI 연결·자격 증명 저장 — 2단계

- 상태: 저장 어댑터·조율 서비스·인증 세션 정리 구현. 연결 등록 HTTP API, 제공자 확인·모델 조회, 사용자 모달은 아직 없다.
- 기준: [공통 계약](ai-contracts.md), [AI 작업 계획](ai-scripting-plan.md), [개인정보 운영 준비](privacy-operations-plan.md).

## 저장 위치와 구성

`AI_DATA_DIR`의 기본값은 `data/ai`다. 기본 경로는 Git에서 제외했다. 운영에서 다른 경로를 사용하면 실제 데이터도 저장소 밖에 두어야 한다.

| 위치 | 내용 |
| --- | --- |
| `connections.json` | 영구 연결 메타데이터와 마지막 영구 연결·모델 선택 |
| `credentials/<UUID>.json` | API 키의 암호문, 임의 IV, 인증 태그, 내부 소유자·참조·암호화 키 식별자 |
| `credentials.key-check.json` | 설정한 마스터 키의 일치 여부를 확인하는 인증된 암호화 자료 |
| 서버 메모리 | 임시 연결·키·해당 로그인 세션의 선택 |

코드 원문과 경기 기록의 저장 위치는 변경하지 않았다. `FileAiConnectionRepository`와 `FileCredentialStore`를 분리하고 `createAiStorage`가 비밀 생성 → 연결 참조 갱신 → 이전 비밀 정리를 조율한다. 메타데이터 저장소는 향후 DB 어댑터로 교체할 수 있다. 비밀 원문은 일반 메타데이터·공개 연결 응답에 포함하지 않는다.

메타데이터는 기존 로컬 파일 잠금을 재사용해 읽기·수정·원자적 교체 전체를 직렬화한다. 독립 어댑터 인스턴스도 같은 파일 잠금을 사용한다. 임시 상태와 조율 서비스는 단일 서버 프로세스용이며 여러 컨테이너 공유 운영은 지원하지 않는다.

## 설정

`AI_ENABLED=true`이면 작성 서비스의 내부 AI 저장 계층을 준비한다. 이 설정만으로 AI를 호출하거나 UI가 바뀌지는 않는다. 기본은 false다.

영구 키 저장을 사용하려면 다음이 필요하다.

- `AI_ALLOW_STORED_CREDENTIALS=true`
- `AI_CREDENTIAL_KEY`: 무작위 32바이트를 표현한 64자리 16진수. 암호화 키이며 제공자의 API 키가 아니다.
- `AI_CREDENTIAL_KEY_ID`: 해당 암호화 키를 식별하는 이름. 영문·숫자·밑줄·하이픈 1~64자.

키를 설정하지 않아도 임시 연결은 사용할 수 있다. 키 또는 ID만 입력하거나 잘못된 형식을 입력하면 설정 오류로 중단한다. `storedAvailable`은 설정 준비 여부이며 기존 파일에 대한 마스터 키 일치 검증 성공을 의미하지 않는다. 실제 저장·조회 전에 키 확인 자료를 검증한다.

AES-256-GCM, 임의 12바이트 IV, 16바이트 인증 태그를 사용한다. 형식 버전·참조 ID·내부 사용자 ID·키 ID를 인증 데이터로 묶어 소유자 변경이나 다른 참조로의 파일 복사를 감지한다. 구현은 [Node 18 crypto API](https://nodejs.org/docs/latest-v18.x/api/crypto.html#ciphersetaadbuffer-options)를 사용한다.

마스터 키는 로컬 `.env` 또는 별도 배포 비밀 주입으로 관리하고 데이터 디렉터리·Git·일반 로그·데이터 백업에 포함하지 않는다. 프로세스 재시작 때 새 키를 자동 생성하지 않는다. 파일 mode 0600은 POSIX 환경의 방어이며 Windows에서는 저장 위치의 ACL을 운영 단계에서 별도로 확인한다.

## 보존·복구·키 교체

서버와 유지보수 쓰기 작업을 중지한 뒤 `AI_DATA_DIR` 전체를 백업한다. 메타데이터·비밀 파일·키 확인 자료를 같은 시점으로 복원하고 원래 마스터 키/ID를 별도 비밀 설정으로 주입한다. 틀린 키·다른 ID·변조된 파일은 실패 처리하고 덮어쓰지 않는다. 비밀 파일이 있는데 키 확인 자료만 없으면 새 저장소로 초기화하지 않고 복구가 필요하다고 처리한다.

마스터 키 자동 회전·기존 자료 재암호화 도구는 이번 단계에 포함하지 않았다. 운영 전 별도 절차가 필요하며, 기존 자료가 있는 상태에서 환경변수의 키·ID만 바꾸거나 키 확인 파일을 삭제해 재초기화하지 않는다. 키를 잃어버리면 암호문만으로 원문을 복원할 수 없다. 사용자의 제공자 API 키 교체는 별개이며 새로운 키를 새 비밀 파일에 기록한 뒤 연결 리비전을 갱신한다.

API 키 확인은 다음 단계의 제공자 검사 콜백을 연결할 지점을 제공한다. 현재 기본 콜백은 외부 검사를 하지 않으므로 교체 결과는 `unchecked`이며 API 인증 성공으로 표시하지 않는다. 확인 실패·리비전 충돌·메타데이터 쓰기 실패는 새 비밀을 정리하고 이전 연결을 유지한다. 커밋 후 이전 비밀 정리 실패는 성공한 교체를 실패로 돌리지 않고 비밀 없는 운영 오류를 기록한다.

메타데이터와 비밀 파일은 서로 다른 저장 영역이다. 중간에 프로세스가 강제 종료되거나 파일 삭제가 실패하면 미참조 암호문이 남을 수 있다. 자동 미참조 파일 수집은 아직 구현하지 않았다. 운영 전 정리 절차를 마련하고 잘못된 키의 자료를 임의 삭제하지 않는다. 계정별 `deleteOwner`는 메타데이터·선택·해당 계정의 암호문을 정리할 수 있지만 최종 계정 삭제 UI와 백업 삭제 정책은 마지막 개인정보 운영 준비 단계다.

## 세션 격리와 종료

로그인 쿠키 원문과 별개의 내부 세션 ID를 추가했다. `authentication.scope()`가 현재 계정 상태와 유효한 세션을 확인해 AI 소유권 범위를 반환한다. 이 ID는 `/api/session` 응답이나 저장 키 메타데이터에 포함하지 않는다.

- 임시 연결은 같은 사용자의 다른 로그인 세션에서도 보이지 않는다.
- 로그아웃·재로그인으로 세션이 교체되면 해당 세션의 임시 연결·키·선택을 즉시 제거한다.
- 세션 만료는 접근 시 및 1분 간격 정리에서 제거한다. 만료 후 접근은 즉시 거부한다.
- 이용 중지/세션 전체 폐기는 해당 사용자의 모든 임시 연결을 제거한다.
- 서버 종료는 세션·임시 저장·대기 중 저장 작업을 정리하며 종료된 세션 저장소는 늦은 로그인 응답으로 새 세션을 발급하지 않는다.
- 영구 연결·키는 일반 로그아웃으로 삭제하지 않으며 다음 로그인에서 다시 사용한다.

늦은 키 확인 결과가 로그아웃 뒤 임시 연결을 다시 등록하지 못하게 저장 전 유효 세션과 리비전을 검사한다. 계정 전체 삭제 호출자는 먼저 해당 계정 세션과 새 작업을 차단해야 한다. 메모리 정리는 참조 제거이며 JavaScript 런타임·OS 덤프에서 모든 바이트가 즉시 소거된다는 보장은 아니다.

## 리뷰·검증과 후속 범위

리뷰에서 마스터 키 불일치 상태의 새 쓰기 차단, 실패한 임시 메타데이터 쓰기의 메모리 변경 보류, 다른 소유자의 연결 취소 훅 실행 차단, 서버 종료 뒤 늦은 세션 발급 차단을 보완했다. 새 기능은 테스트용 자격 증명만 사용하며 실제 사용자 키나 로컬 계정 자료를 수정하지 않았다.

`test/ai-storage.test.js`는 임시 키 디스크 비저장·세션 격리, 재시작 복호화, 잘못된 키/ID·소유자/참조 변조, 리비전 경합, 키 교체 실패 보존, 로그아웃/만료/이용 중지/종료, 지연 검사 경합, 저장 실패 롤백, 소유자별 정리, 실제 HTTP 로그아웃 연결을 검사한다. 제공자 확인·모델 목록·HTTP 연결 관리·암호화 키 회전·강제 종료 후 미참조 자료 수집은 후속 범위다.
