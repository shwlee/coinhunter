# BE 분리 1단계 구현·검증 기록

- 작성일: 2026-11-15
- 구현: .NET 10 운영 API·실행 관리 호스트의 독립 뼈대, typed 실행 DTO·공개 API 목록 36개, 설정/내부 인증·상태 확인, C#/Node 엔진 프레임 규약 v1.
- 범위 밖: 계정/파일 저장·Google 실제 로그인·게임 엔진 생성/상태 전이·경기/SSE·전량 수집·FE 연결. 업무 경로 501과 businessReady=false로 구분한다.
- 환경: Windows, .NET SDK 10.0.401, .NET/ASP.NET Core 10.0.12, Node 18.20.2. 로컬 검증이며 배포용 버전/네트워크 확인을 대신하지 않는다.

## 실행 명령

```sh
node scripts/backend.js test
```

`npm run backend:test`의 동일한 진입점이다. 현재 도구 sandbox에서는 사용자 프로필 아래 npm 진입 파일의 lstat가 거부되어 직접 Node 진입점을 사용했다. 전역 npm/권한/사용자 설정을 변경하지 않았다.

검사는 로컬 빈 NuGet feed에서 복원/빌드한 뒤 SDK만 사용하는 C# 계약 검사를 실행하고 실제 호스트를 각각 임의 loopback 포트로 기동해 HTTP/프로세스 검사를 수행한다. 내부 키는 시험마다 새로 생성하고 출력하지 않는다. 검사가 만든 프로세스는 정상 종료하고 두 서비스의 포트가 닫히는 것까지 확인한다. 사용자 서버·.env·계정/원문 파일·실제 Google/API는 사용하지 않는다.

## 확인한 내용

- 솔루션 5프로젝트 빌드: 경고 0·오류 0.
- C# 계약 검사 31개: fixture·버전·필수/알 수 없는 필드·참가자/맵/언어/source 구조·guest duel·원문 metadata 계약·프레임 분할/병합/EOF/손상/길이·설정 검증.
- Node/HTTP/프로세스 검사 19개: 호스트 환경의 불필요한 자격 증명 제외, protocol manifest 일치, UTF-8·분할/병합/종료·bad frame, C#→Node/Node→C# 실제 바이트 상호운용.
- 두 호스트 live/ready·bootstrap 범위·업무 준비 false, 내부 키 없음/불일치, 유효 키라도 브라우저 Origin 거부.
- 공개 계약 목록 36개·이전 단계별 501·쿠키 미발급·제거 AI 410·알 수 없는 API/파일 JSON 404.
- Host/Origin/전달 헤더 위조 거부, 명시된 proxy의 공개 authority 재검사, Production의 공개 HTTPS 요구와 개발 계약 목록 비노출.
- OAuth code/state와 내부 키가 응답/기본 요청 로그에 남지 않음.
- 실행 서비스 키/버전 불일치·종료·redirect·과대 응답·헤더 후 본문 정지 시 운영 readiness 503, 자체 live 유지. status body 전체 deadline 검증.
- 잘못된 설정이 포트 수신 전에 실패하며 입력 비밀을 오류에 포함하지 않음.
- 두 서비스 동시 실행 도구의 별도 포트 시작과 stdin 종료 후 두 호스트/실행 도구 정상 종료·포트 정리.
- 기존 JS 실행기/preflight 회귀 21개 통과. 실제 500ms 중단·같은 PID/객체 재호출·참가자 독립 진행·검사 진단 등 기존 실행 계약을 유지한다.

## 자체 후속 리뷰

status probe가 응답 헤더를 받은 후에도 본문에서 무기한 기다리지 않도록 전체 deadline을 적용하고 stalled body 시험을 통과했다. 신뢰 proxy라도 일부 전달 헤더가 누락되거나 다중 hop/잘못된 IP이면 거부하도록 보강했다. 404 fallback의 파일 확장자 경로, 개발 실행 도구의 모듈 순환 참조도 검사 중 수정하고 전체 backend 검증을 다시 통과했다. 추가 높음/중간 결함은 확인하지 못했으며 아직 미구현인 업무/실행 기능은 별도 한계로 남긴다.

## 검증의 한계

실제 Google 왕복과 회사 네트워크/TLS, 원본 데이터 이전, 사용자 코드 실행/지속 게임, idempotency ledger·원본 이벤트 수집·리플레이는 아직 검증하지 않았다. DTO 검증/프레임 상호운용이 해당 기능을 대신하지 않는다. 실제 계정/업무 readiness는 단계 2 이후에 구현한다.

다음 단계는 C# 파일/원문/맵 저장 어댑터다. 새 BE가 기본 서비스나 데이터 작성자가 된 상태는 아니다.
