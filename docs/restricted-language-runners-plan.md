## 1. 목적과 기존 결과의 해석

기존 Unity 작성 규칙과 추가 금지 규칙을 먼저 검사하고, 통과한 코드의 실제 호출 종료·객체 재사용을 검증한다. sleep/스레드/소켓이 허용된 일반 호스트 실험은 규약 검사 완료를 의미하지 않는다. 해당 코드는 정적 검사에서 거부하는 부정 테스트로 옮기고, 허용된 유한 장시간 계산·할당·내장 함수에 대해서는 실행 중 제한도 시험한다.

이 문서는 사용자 요청에 따른 후속 작업 계획이다. 4단계 원본 실측을 수정하거나 보류 후보를 지원 완료로 바꾸지 않는다. 프로토타입은 4단계 추가 검증으로 진행하고, 채택한 후보만 상위 계획 5단계 준비/캐시·6단계 정식 어댑터로 연결한다.

| 재귀 금지                  | 직접·상호 재귀 모두 거부. 프로퍼티/연산자/콜백 등 숨은 호출 경로 포함. 분석할 수 없는 동적 호출은 별도 지원하지 않음                                   |

| 사용자 try/catch 금지      | 사용자 try문 전체를 금지: C#/C++ try/catch, Python try/except/except*/finally. 사용자 try/finally 우회도 거부. 호스트가 생성·관리하는 예외 처리와 구분 |

정규식/키워드 검색만으로 검사하지 않는다. 구문·심볼·참조 대상을 분석하며 별칭, 완전 수식 이름, 간접 호출을 포함한다. 파일 단일성은 소스 형식과 참조 로더 양쪽에서 제한한다. Python 표준 모듈과 C++ 표준 헤더를 모두 외부 라이브러리로 간주하지 않고, 허용 API를 명시한다. 정적 메서드 호출을 전부 금지하면 Math 등 기본 API까지 막히므로 사용자 static 선언과 승인된 표준 메서드 참조를 구분한다.

사용자 catch 금지는 중단 예외 삼키기를 줄이지만, using/with/소멸자 등 암묵적 정리와 긴 내장 호출은 남는다. 이 기능들은 기존 규약에서 자동 금지됐다고 간주하지 않고 각 언어 계획에서 허용/제한 후보를 검증한다. 기존 저장 코드에 새 규칙이 적용되는 시점과 재검사 안내도 정의한다. 자동 삭제·변환하지 않는다.

## 3. 중단·복구 정책 후보와 결정 항목

공통 후보는 **500ms 결과 마감 → 협조적 중단·제한된 정리 유예 → 미종료 시 프로세스 종료·교체**다. 정상 timeout으로 호출이 끝나면 같은 Player를 유지한다. 강제 종료하면 객체가 소멸하므로 다음 정책을 선정해야 한다.

| 항목        | 계획상 처리                                                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 500ms       | 결과 마감 기준은 유지. 시작 경계는 입력 변환/dispatch를 포함하는 기존 JS 계약과 대조해 명문화. IPC 지연을 순수 알고리즘 시간으로 혼동하지 않음    |
| 정리 유예   | 후보 설정 `cleanupGraceMs`; 수치는 실측 후 결정. 500ms 이후 CPU 실행을 허용하므로 현재의 실제 중단 계약과 다르며 제품 적용 전 계약/정책 확정 필요 |
| 늦은 반환   | 방향을 적용하지 않음. 같은 callId는 결과 확정 1회만 허용. 유예 중 계산이 필드를 변경할 수 있다는 의미도 규약에 명시                               |
| 제자리 액션 | 마감 시 현재 턴 -1 액션. 액션과 정리는 병행 가능하지만 액션 완료와 실제 호출 정리 완료를 모두 확인한 뒤 다음 판단                                 |
| 강제 종료   | 감시자가 해당 플레이어 프로세스만 종료하고 종료 완료를 확인. 이전 generation의 응답은 거부. 다른 플레이어는 독립 진행                             |
| 객체 상태   | 초기화 재시작 / 마지막 정상 턴의 명시적 상태 복원 후보 비교. 기본값 미확정. 임의 CLR/Python/C++ 객체 자동 복제는 약속하지 않음                    |
| 반복 실패   | 게임 전체/플레이어별 재시작 횟수·자원 한도와 한도 초과 처리 결정. 무제한 재시작 금지, 임의 실격 규칙을 먼저 적용하지 않음                         |
| 예비 호스트 | cold start 측정 후 제한된 대기 풀 적용 여부 결정. 다른 사용자 상태를 재사용하지 않음. 예비 Player가 최신 상태라고 간주하지 않음                   |

500ms 초과 판정, 정리 성공, 프로세스 장애를 별도 이벤트로 기록한다. 실제 중단·강제 종료 정책 확정 전에는 기존 `RunnerResult.completion`을 거짓으로 반환하지 않는다. 이 정책을 적용하려면 `deadline-reached`와 `execution-settled`를 분리하는 버전 계약이 **필수**다. 종료 대기 중 busy 상태를 유지하고, stop/disconnect/서버 종료 시에도 자원을 회수한다.

명시적 상태 복원 후보는 사용자 스키마/버전·바이트 한도·저장 호출 예산·소유권·검증·복원 실패 정책을 포함한다. 마지막 성공 상태만 게시하고 실패 턴의 상태를 승격하지 않는다. 상태 저장을 매 턴 DB 동기 쓰기로 붙이지 않는다. 상태 API 추가는 별도 결정이며 원문 코드 파일 보관과 분리한다.

### 실제 게임 실행 자원 제한 — 사용자 코드 로딩 전 필수

- 프로세스/컨테이너 수명 관리자가 OS 수준 메모리·CPU 사용률/할당·프로세스 수 제한을 설정한 뒤 사용자 코드 로드·생성자·initialize를 허용한다. 제한 설정 실패 시 실행을 허용하지 않는다. CPU 자원 제한과 500ms 경과 시간 예산은 별개다.
- Windows 개발 환경과 Linux 배포 환경 각각의 적용 어댑터를 정의한다. Windows Job Object 및 Linux cgroup 등은 검증 후보이며 지원 OS에서 실제 강제 제한·자식 포함 회수가 확인돼야 채택한다. 공유 서비스 전체를 죽이는 방식으로 플레이어 한도를 대신하지 않는다.
- C# GC heap·Python 객체 할당·Wasm 선형 메모리 외에 native allocation, 스택, JIT/VM, IPC 버퍼를 포함한 호스트 메모리 한도를 따로 둔다. 하나의 32MiB 값을 모든 런타임 RSS에 그대로 적용하지 않고 시작 비용/guest 예산을 측정해 설정한다.
- 게임 실행, 검사, 컴파일, 예비 프로세스에 대한 전체 예약 예산과 admission 한도를 관리한다. 한도 부족은 대기/거부로 처리하고 무제한 프로세스 생성·교체를 허용하지 않는다. 예비 호스트에도 같은 제한을 먼저 적용한다.
- 한도 초과로 종료된 경우 신뢰된 OS/호스트 증거가 있을 때 `resource-limit`으로 분류한다. 원인 불명 exit를 사용자 timeout/OOM으로 추정하지 않는다. 프로세스 트리 종료·종료 확인 후에만 슬롯을 반환한다.
- 완료 시험: 500ms 이전 대량 할당, native 메모리 증가, 자식 생성 시도, 여러 게임+검사+교체 동시 부하, 제한 설정 실패, 서버 종료 시 고아 프로세스 회수. 다른 참가자·운영 API의 가용성을 함께 측정한다. RSS 관찰만으로 강제 제한 통과를 선언하지 않는다.

### 시간·이벤트 계약과 판정 우선순위

1. 요청의 대기/IPC 기한, 사용자 호출 실행 예산, 결과 전송 기한, 정리 유예 기한, 강제 종료/교체 기한을 각각 둔다. 요청 전송 시각부터의 500ms를 알고리즘 실행 시간으로 사용하지 않는다.
2. 신뢰된 host wrapper가 승인된 실행 예산 구간 진입 직전 `execution-started`와 호출 식별자(generation/run/instance/call)를 기록한다. 이 구간은 승인된 입력 변환/dispatch와 사용자 호출을 포함하며 경계를 명시한다. 생성자/초기화/이름 조회에도 별도 기한과 자원 한도를 적용한다.
3. 시작 통보와 완료 기록의 duration은 host의 같은 단조 시계로 잰다. 부모가 마감/정리 watchdog을 독립 집행하기 위해서는 검증된 공통 단조 시계 또는 오차 범위를 가진 시간 매핑을 먼저 구현한다. 자식 timestamp와 부모 timestamp를 직접 빼거나 통보 도착 시간을 실제 시작으로 취급하지 않는다. 매핑 불가 환경에서는 일반 미응답 감시만 수행하고 정확한 마감 알림 지원을 완료 처리하지 않는다.
4. 부모 관리자는 사용자 코드와 독립적으로 기한을 감시한다. 시작 통보 누락·비정상 지연은 `start-unconfirmed` 인프라 실패, 완료 기록/전송 누락은 `unresponsive`로 분류한다. 경과 시간 증거 없이 timeout으로 바꾸지 않는다. 이 상태에서는 다음 호출을 금지하고 정리한다.
5. host의 호출별 `deadlineExceeded`는 한 번 설정되면 해제되지 않는다. 최종 판정은 신뢰된 기한 상태·종료 duration·실제 정리 여부를 조합하며 예외 타입이나 문자열만으로 timeout을 결정하지 않는다. 마감 전 종료 기록이 증명되면 IPC가 늦었다는 이유만으로 timeout을 만들지 않는다. 결과 수신 기한 초과로 이미 인프라 실패가 확정된 호출은 늦게 성공으로 되돌리지 않는다.
6. 마감 확정 후 예외가 다른 타입으로 감싸지거나 정상 값이 반환돼도 방향을 수락하지 않는다. 프로세스/자원 장애가 겹치면 이번 턴 마감 판정과 호스트 실패 원인을 각각 보관한다. timeout 확정이 인스턴스 재사용 허가를 의미하지 않으며 정리 실패·치명적 오류·상태 유효성 미확인은 폐기/복구 경로다.
7. 정리 유예는 확인된 실행 마감 시점에 연결한다. 늦은 통보 수신이나 재전송으로 유예를 연장하지 않는다. 마감과 완료의 동시 도착·메시지 역전/중복·오래된 generation을 시험하고 결과/액션 확정은 1회만 허용한다.

부모에서 시간이 지났다는 사실과 “기한 내 완료 메시지가 아직 도착하지 않았다”는 사실만으로 턴 timeout을 확정하지 않는다. 마감 전에 완료됐으나 전달이 늦은 경우를 구분하기 위해 신뢰된 완료/마감 원자 기록 또는 이에 준하는 경합 조정 프로토콜을 검증한다. 그 증거가 불명확하면 실행 결과를 미확정으로 유지하다 별도 응답 기한에서 인프라 실패로 정리한다. 이미 timeout 액션을 적용한 후 뒤늦게 정상 방향으로 바꾸는 설계는 허용하지 않는다. 제자리 액션을 500ms에 바로 시작하는 기능도 이 판정 경로가 검증된 환경에서만 활성화한다.

필수 시험은 빠른 계산+늦은 IPC, 요청 대기 지연, 시작 통보 미수신, 자식 관리 스레드 정지, 시계 매핑 오차, 500ms 경계에서 완료/마감 경합, 중단 예외 변형/억제, 유예 만료와 프로세스 종료 경합이다. 정책 수치 확정 전부터 이 계약의 실험을 수행하며 기존 v1 경로와 섞어 지원하지 않는다.

## 4. 코드 검사·저장 시 테스트 호출 루틴

### 공통 경로

```text
검사 버튼 / 저장 요청
  → 서버 소유권·언어 확인
  → 소스의 불변 임시 파일·hash 확보
  → 저장 요청이면 파일·revision·검사 pending 상태를 먼저 원자적으로 보관
  → 규약/구문/참조 검사
  → 준비·컴파일
  → 격리된 검사 세션에서 테스트 호출
  → 호출별 진단 + 소스/규약/실행기/테스트 버전에 묶인 결과
  → 동일 저장 revision/hash의 검사 상태 갱신 (코드 보관 성공과 실행 허용을 구분)
```

- 기존 `backend/node/src/runtime/preflight.js`와 worker, `AlgorithmsController`의 검사/저장 및 소스 저장 서비스 경로를 조사하고 공통 검사 서비스로 연결한다. 실제 게임과 동일한 준비/실행 어댑터를 사용한다.
- 코드 검사와 저장 모두 서버가 수행한다. 클라이언트의 통과 플래그를 신뢰하지 않는다. 저장마다 검사 실행을 요청하며, 이후 최적화 시 같은 소스 hash·언어/규약/런타임/테스트 버전·허용 프로필/자원 설정·소유자에 묶인 서버 결과만 짧게 재사용한다. 코드 편집 시 UI의 통과 상태를 무효화한다.
- **원문 보관과 실행 허용을 분리한다.** 문법/규약/실행 검사 실패·500ms 초과가 있어도 사용자 요청에 따라 코드와 revision을 저장한다. UI는 “저장됨 · 검사 실패”처럼 두 결과를 독립적으로 표시한다. 검사 실패로 이미 보관한 원문을 삭제하거나 이전 revision으로 되돌리지 않는다.
- 저장의 인증·소유권·revision 충돌·파일/메타데이터 쓰기 실패는 저장 실패이며 기존 데이터를 보존한다. 검사 서비스 오류·포화·취소는 저장 성공과 별개로 `unverified`/재검사 필요를 표시한다. 사용자가 저장 자체를 취소한 경우 commit 전후를 구분하며 commit 후 검사 취소가 저장 취소로 표시되지 않게 한다.
- 검사 결과 상태는 `pending / passed / failed / unverified / stale`로 정의한다. pending 작업 유실/서버 재시작 후 영구 진행 중 상태가 남지 않도록 작업 receipt와 복구 또는 재검사 경로를 둔다. 검사 용량이 없으면 원문은 저장하고 무제한 큐 대신 재검사 필요를 표시한다.
- 게임/작업실 테스트/업로드/이전 경기 대결의 실행 진입점은 동일 소스·활성 프로필에 유효한 passed 결과를 확인하거나 새로 검사한다. failed/pending/unverified/stale이면 실행 준비를 중단하고 이유를 표시한다. 저장 성공을 실행 허가로 사용하지 않는다. 이미 진행 중인 게임은 고정된 artifact/profile을 유지한다.
- 검사 결과 갱신은 소유자/source hash/저장 revision/검사 버전을 비교해 수행한다. 검사 중 새 저장·삭제·계정 중지·프로필 변경이 발생하면 늦은 통과가 현재 코드의 실행 허가를 덮어쓰지 않게 한다. 검사 세션의 source lease를 해제한 뒤 미참조 임시 파일을 정리한다.
- 기존 계정/파일 어댑터의 소유권·덮어쓰기 충돌 검사를 유지한다. 검사 도중 이름/선택/코드가 바뀌면 다른 소스를 저장하지 않도록 스냅샷을 고정한다. 원문은 파일로, 결과 요약·버전·hash 등은 메타데이터로 보관한다.

### 초기 테스트 묶음 후보

| 사례            | 입력과 목적                                                                                      |
| --------------- | ------------------------------------------------------------------------------------------------ |
| 필수 인터페이스 | initialize/getName/moveNext 형식·동기 반환·반환 방향·이름 검증                                   |
| 기본 탐색       | 유효한 작은 대칭 맵, 여러 시작 위치, 가까운/먼 코인                                              |
| 목표 없음       | 코인·아이템 없음, 빈 큐/탐색 종료 처리                                                           |
| 우회·도달 불가  | 유효한 벽 배치, 도달 불가 목표, 경계 이동 처리                                                   |
| 아이템          | 없음(-1), 각 종류 위치, 획득 전후 입력. 랜덤점프 중 알고리즘 미호출은 엔진 규칙으로 별도 회귀    |
| 큰 입력         | 게임에서 허용하는 최대 맵 크기 기준 벽/코인 밀집·희소 사례. 새 맵 크기 상한을 임의 도입하지 않음 |
| 연속 호출       | 같은 객체에 변경된 맵/현재 위치를 전달하는 짧은 실제 진행 시퀀스. 호출마다 initialize하지 않음   |

구체 입력은 고정 seed와 fixture 버전으로 재현 가능하게 만든다. 초기 예산은 6개 내외 유효 맵 시나리오, 시나리오당 3~5회 호출 후보를 측정해 결정한다. 맵 크기가 달라지면 별도 인스턴스를 초기화하고, 같은 시나리오에서는 동일 객체를 유지한다. 검사 실패 시 불필요한 후속 호출을 중단한다.

각 moveNext의 실행 예산은 독립적으로 500ms다. prepare/initialize/getName, 전체 검사 작업, 프로세스 정리에는 각각 별도 기한을 둔다. 실행기 시작/JIT 지연과 호출 실행 시간의 경계를 기록하며 예열로 실제 첫 호출 초과를 숨기지 않는다. 단일 샘플이 초과하면 재시도 평균으로 통과시키지 않는다. 호스트 과부하 등 인프라 실패는 사용자 코드 timeout과 구분해 재검사 안내한다.

테스트에서 규약 위반·사용자 예외·잘못된 반환·500ms 초과가 확인되면 검사 실패로 표시하고 실행을 허용하지 않는다. 원문 보관은 허용한다. `-1` 정상 반환은 실패가 아니다. 현재 게임에서 정상적인 벽 방향 선택은 게임 규칙으로 처리되므로 코드 오류로 오판하지 않는다. 게임 중 처음 나타나는 입력에서의 timeout은 여전히 현재 턴 패널티로 처리한다.

UI는 저장 결과와 별도로 검사 진행/취소·실패 사례·호출 번호·측정 시간·한도·가능한 코드 위치를 제공한다. 검사 실패 상태의 코드를 다시 불러와 편집할 수 있다. “모든 경우에서 안전함” 대신 “규약 검사 및 제공된 실행 테스트 통과”로 표시한다. 유한한 테스트만으로 모든 입력/턴의 종료·시간 준수를 증명할 수 없다.

### 검사 서비스 보호와 진단

- 사용자별/전체 동시 한도·bounded queue·전체 시간·출력/메모리/임시 디스크 한도 적용. 검사 부하가 게임 처리량을 잠식하지 않도록 실행 자원 할당 측정.
- 검사 세션은 실제 게임 Player를 사용하지 않음. 검사 종료 시 프로세스 종료는 검사 세션 정리이며 게임 timeout 정책과 구분.
- 취소·페이지 이탈·저장 연타·서버 재시작·실행기 미응답 시 자원 회수. 재시작 루프로 검사 시간을 무한 연장하지 않음.
- 사용자에게는 원본 파일 위치로 변환된 진단을 제공하고 생성 래퍼·서버 물리 경로·환경 값은 숨김. 로그에 코드 원문을 중복 보관하지 않음.

## 5. 공통 작업 순서와 완료 기준

### 선행 J 작업 — 현재 JavaScript에서 독립 완료

현재 JS preflight는 2개 맵 × 4개 플레이어 × 3회, 총 24회 호출을 이미 수행한다. 저장 API는 이 검사를 호출하지 않는다. 새 기능을 중복 구현하지 않고 기존 경로를 확장한다. 이 작업은 C#/Python/C++ 후보 채택이나 정리 유예 정책 확정을 기다리지 않는다. 기존 JS 실제 중단 계약 v1을 유지한다.

| 단계 | 작업                                                                               | 완료 기준                                                                                 |
| ---- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| J0   | 현재 JS 규약/검사 결과 구조와 저장·실행 경로 조사, 추가 규칙의 지원 범위/진단 명세 | 기존 24회 호출과 누락 사례 식별, 저장/검사/실행 허가 계약 확정                            |

| J2   | 원문 보관 성공과 검사 상태 분리, 저장 후 검사·실행 진입점 연결                     | 실패 코드 저장/재불러오기, 검증 전 실행 거부, stale 통과·직접 API 우회·revision 경합 방지 |
| J3   | 현재 JS 작업실/게임/히스토리 흐름과 검사 부하 검증                                 | 검사 서비스 장애에도 코드 보관 가능, 진행 중 경기 보존, 고아 검사/파일 회수               |

JS의 추가 규약 분석 범위는 J0에서 명시하고 아직 검사하지 못하는 규칙을 적용 완료로 표시하지 않는다. 기존 코드 재검사 시점과 안내를 함께 제공한다. 이후 채택 언어는 J 작업의 서비스/상태 계약을 재사용한다.

### 다국어 R 작업 — 언어별 통과 후 연결

| 단계 | 작업                                                                  | 완료 기준                                                                                          |
| ---- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| R0   | 규약/API 명세, 실제 실행 프로세스 자원 제한·감시 기반                 | 사용자 코드 로딩 전 강제 한도·admission 확인, 위반 사례 거부                                       |
| R1   | C# → Python → C++ 순서로 제한 프로필·자동 중단 후보 검증              | 정상→유한 장시간 계산→호출 종료→동일 객체 정상 호출, 우회 거부와 자원 누적 결과                    |
| R2   | 독립 시간 감시·마감/정리 이벤트 계약, 예외 판정·복구 실험과 정책 결정 | 시계/통보/예외 변형 경합 시험, 유예/복구/반복 실패 정책 및 계약 버전 확정. 조건 불충족 언어는 보류 |
| R3   | 통과 후보의 준비/정식 어댑터와 공통 preflight 구현                    | 게임·검사에서 같은 규약/어댑터, 원본 위치 진단, 격리된 컴파일·파일 기반 산출물                     |
| R4   | 채택 언어를 J 작업의 검사·저장 상태·실행 허가 경로에 연결             | 언어별 검사 fixture, 보관/실행 분리, 프로필/버전별 stale·검사 우회 방지                            |
| R5   | 통합·혼합 언어·부하·복구 회귀와 적대적 리뷰                           | 독립 진행, 비중첩, 타 사용자 격리, 늦은 응답 무효화, 반복 timeout/교체 자원 안정성                 |

기존 JS의 깊은 재귀 오류 분류는 공통 회귀 보완 대상으로 유지한다. 새 재귀 금지 정책의 정적 거부와, 실행기 내부 재귀 장애 방어를 구분한다. 언어별로 통과한 순서에 따라 채택하며 전체 언어 지원을 묶어서 완료 처리하지 않는다.

## 6. 검증 기록·공정성·작업 경계

정적 검사 부정 사례와 정상 알고리즘 사례를 분리한다. 정상 샘플은 BFS/반복형 DFS·우선순위 탐색·영속 방문 기록을 포함하고, 고의 timeout fixture는 제품 사전 검사에서 실패하는 것이 기대 결과다. 내부 중단 장치를 직접 시험할 때만 신뢰된 fixture로 호출한다.

언어별 코드 변환 전후 실행 비용, 입력 변환/IPC/검사 지점 오버헤드, 실제 중단 지연, 제자리 액션 후 다음 판단까지 지연, cold/warm 재시작, RSS·임시 할당·반복 재시작 누적을 기록한다. 동일 IPC라는 이유로 공정하다고 판정하지 않고 빠른 계산을 인위적으로 대기시키지 않는다. 유예 중의 추가 CPU 사용도 별도 기록한다.

현재 계획은 지원 규약/실행 제어/사전 검사·저장 연결에 한정한다. UI의 다국어 편집 환경·프롬프트 언어별 생성, 운영 DB 전환·외부 배포는 별도다. API/저장소에 빈 지원 언어를 등록하지 않는다. 원문 파일 보관·소유권·삭제 가능 참조와 마지막 개인정보 운영 준비를 유지한다.
