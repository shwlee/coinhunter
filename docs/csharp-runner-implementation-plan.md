# C# 제한 규약 실행기 작업 계획

- 상태: 계획 작성, 구현 미착수. [공통 규약·검사/저장·복구 계획](restricted-language-runners-plan.md)을 따른다.
- 선행 기반: [R0 자원 제한](execution-resource-limits.md)의 공통 예약/OS 그룹·로드 전 승인과 Windows 실측을 구현했다. Linux 강제 제한·부모 장애 수명 감독은 미검증이다. C1 Roslyn 분석기·C# 준비/컴파일과 개별 호스트 프로필은 아직 구현하지 않았다.
- 2026-11-16 리뷰 반영: 실제 게임 강제 자원 한도, 시간/중단 판정 계약, 실패 코드 보관과 실행 허가 분리. 기존 JS J0~J3 개선 이후 채택된 C#을 공통 경로에 연결한다.
- 목표: 단일 C# 소스를 준비 시 컴파일하고 Player를 반복 호출한다. 사용자 try/catch/finally·재귀·goto·static·비동기/병렬·대기·외부 접근을 거부한다.
- 후보: .NET 10 전용 호스트 + Roslyn 분석/변환 + 자동 예산 검사. Thread.Abort/ControlledExecution은 제품 중단 방식으로 채택하지 않는다. 메시지 루프는 호출 순서·비중첩을 관리하며 중단 수단 자체는 아니다.

## C1. 규약 분석기

실제 게임·검사 호스트 모두 공통 R0의 OS 강제 자원 제한을 사용자 코드 로딩 전에 적용한다. .NET GC heap 한도와 프로세스 전체 메모리 한도를 구분하고 native allocation·스택·JIT·동시 호스트/예비 호스트 예약을 포함한다. 제한 설정 실패 시 실행 금지, 확인된 자원 초과와 원인 불명 프로세스 장애를 구분한다. 분석기 자체의 입력/CPU/메모리 부하도 준비 한도로 관리한다.

1. 필수 메서드/서명·동기 반환·참조 assembly를 검사한다. 서버가 지정한 승인 참조만 사용하고 NuGet/사용자 DLL·컴파일 옵션 입력을 받지 않는다.
2. Roslyn 구문/의미 모델로 사용자 try문, goto, static 선언, async/await, unsafe/extern/PInvoke·Reflection/dynamic·프로세스/Thread/Task·대기·I/O 참조를 판정한다.
3. 별칭·완전 수식 참조·로컬 함수·프로퍼티/연산자 등을 포함해 호출 그래프를 만들고 순환을 거부한다. delegate/virtual 호출은 대상이 증명되는 범위만 허용하는 후보를 명시한다.
4. Math 등 승인 표준 static 메서드와 사용자 static 상태를 구분한다. 컬렉션·LINQ·사용자 comparer·iterator·using/Dispose는 잠재적 콜백/정리 경로를 분석하고 허용 범위를 정한다.

산출물: 허용 구문/API 표, 진단 코드·원본 위치, 정상 탐색과 우회 입력 테스트. 사용자에게 try/catch를 쓰도록 요구하지 않는다.

## C2. 자동 중단 검사 삽입

1. 반복 backedge·함수 진입·콜백 및 필요한 분기 경로에 호스트 소유 예산 검사를 삽입한다. continue/중첩 루프에서도 누락이 없어야 한다.
2. 기한 경과 시 host의 호출별 마감 상태를 먼저 고정하고 실행기 전용 중단 예외를 던진다. 최외곽은 예외 타입이 아니라 신뢰된 마감 상태·종료 시간·정리 결과로 판정한다. 사용자 throw로 timeout을 위조하거나 내부 예산을 변경할 수 없도록 심볼/참조를 분리한다.
3. 검사 사이의 긴 표준 함수, 할당/GC, implicit Dispose는 별도 측정한다. 사용자 catch 금지만으로 이 구간의 종료가 보장된다고 하지 않는다.
4. Player 객체와 일반 필드를 유지한다. 중단 전 부분 변경은 롤백하지 않으며 컬렉션/호스트 불변 조건이 유지되는지 반복 시험한다.

필수 부정 시험: 승인된 정렬/comparer 경로에서 중단 예외가 InvalidOperationException 등으로 감싸지는 경우, Dispose가 원래 중단 예외를 다른 예외로 바꾸는 경우, 마감 뒤 정상 값 반환, 사용자 예외로 timeout 위조 시도. 마감이 확인되면 방향은 거부하되 정리/호스트 장애 원인을 별도로 남긴다. 정리 실패·치명적 오류인 객체를 timeout이라는 이유로 재사용하지 않는다.

통과 기준: 유한 장시간 루프의 자동 중단, 동일 PID/instance·필드 유지·정상 재호출, 우회 코드 사전 거부, 반복 실패의 자원 안정성. 실패하면 허용 범위 조정/대체 VM 후보를 보고하고 정식 지원을 보류한다.

## C3. 수명·복구 실험

전용 .NET 프로세스가 요청을 직렬 처리한다. 마감 알림·정리 완료를 구분하고 실제 정리 전 다음 메시지를 실행하지 않는다. 별도 관리 채널이 계산 루프에 막히지 않는지 확인한다. 제한된 유예 후 강제 종료·종료 확인·generation 교체, 게임 종료와 교체의 경합을 시험한다.

공통 R2의 시간 계약을 필수 적용한다. 부모의 요청 전송부터 500ms를 재지 않고 host 실행 시작/종료 기록·검증된 시계 매핑을 사용한다. 시작 통보 누락/IPC 지연은 별도 인프라 실패다. 사용자 스레드가 응답하지 않아도 부모의 자원/종료 감시는 동작해야 한다.

준비된 DLL 재사용, 초기화·JIT 첫 호출 비용, 예비 호스트 비용을 측정한다. collectible AssemblyLoadContext를 보안 격리/임의 객체 스냅샷으로 취급하지 않는다. 상태 복원 여부는 공통 R2에서 결정하며 수명 교체를 동일 객체 유지로 표시하지 않는다.

## C4. 준비·검사·저장 연결

채택 후 컴파일을 별도 격리 작업으로 구현하고 파일·CPU·메모리·진단 출력 한도를 적용한다. 생성 코드/참조·compiler 버전을 artifact hash에 포함하고 원본 위치 매핑을 보관한다.

공통 preflight의 맵/아이템/연속 호출 묶음을 실제 어댑터로 실행한다. 500ms 초과·예외·규약 위반 시 검사 실패와 실행 불허를 표시하지만 원문 보관은 허용한다. 먼저 완료한 JS J 작업의 저장/검사 상태 계약에 연결하고 source hash·revision·프로필에 맞는 결과만 갱신한다. source는 파일로, 검사 요약/버전은 메타데이터로 관리한다.

## C5. 완료 판정

- 정상 BFS/반복형 DFS·컬렉션·영속 필드가 허용 프로필에서 동작.
- 직접/상호 재귀·try/catch/finally·goto·static·Task/Thread/sleep·외부 접근 및 간접 우회 거부.
- 입력 크기/콜백/Dispose/GC·반복 timeout과 인스턴스 유효성 결과 보관.
- 실제 게임의 OS 메모리/CPU/프로세스 한도·동시 부하·고아 회수 통과. 중단 예외 변형/마감 경합·시작 통보 실패와 독립 감시 확인.
- 늦은 결과 미적용, 비중첩, 독립 진행, 검사/저장 우회 방지와 복구 정책 시험.
- 승인된 규약·복구 정책에서 통과한 경우에만 C# capability 활성화. 컴파일 성공만으로 지원 완료 처리하지 않음.
