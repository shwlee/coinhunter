# 알고리즘 호출 비용과 언어 간 공정성 비교

- 측정일: 2026-11-15
- 목적: 알고리즘 계산 능력과 별개인 호출 경로 비용을 구분하고 직접 호스팅/IPC 설계의 비교 근거를 남긴다.
- 상태: 현재 JavaScript 구현의 합성 측정. 다국어 실행기 구현이나 .NET 직접 호스팅의 실측 결과가 아니다. 실행 구조 선택을 확정하지 않는다.
- 사용자 확정 기준: 플레이어별 독립 실행과 실제 계산 속도의 경쟁 이점을 유지한다. 계산 완료 즉시 액션을 시작하고 액션 완료 즉시 다음 판단을 시작한다. 공통 판단 지연·결과 적용 대기·계산 시간을 제외하는 논리 시간 스케줄러는 이번 요구에서 제외한다. 호출 인프라 편차는 실행기/입력 전달 경로의 설계·최적화로 줄인다.
- 재현: `node scripts/measure-algorithm-call-overhead.js`.
- 원시 집계 결과: [측정 JSON](benchmarks/algorithm-call-overhead-2026-11-15.json). 재실행 결과는 `artifacts/algorithm-call-overhead-results.json`에 별도 생성한다.
- 대상 구현: [PlayerProcess](../src/runtime/player-process.js), [AlgorithmSandbox](../src/runtime/sandbox.js), [게임 진행](../src/game/match.js).
- 구현 계획: [실행기 추상화·독립 실행·호출 비용 최적화](algorithm-runner-independence-plan.md). 이 측정과 요구사항을 게임 실행 분리/다국어 검증의 작업 항목으로 연결한다.

## 1. 현재 실행 경로에서 추가되는 비용

```text
엔진의 입력 배열 사본
  → Node 프로세스 IPC 직렬화·전송·수신 스케줄링·역직렬화
  → 자식 프로세스에서 QuickJS 입력용 JSON 직렬화·문자열 생성
  → QuickJS의 JSON.parse·디스패치
  → 사용자 moveNext 계산
  → 반환 검사·핸들 정리·IPC 응답·엔진 재개
```

`elapsedMs`는 QuickJS 호출을 감싼 `run()`의 시간이다. QuickJS 안의 JSON.parse/디스패치도 포함하며 순수 사용자 함수 시간은 아니다. 반면 IPC와 입력 JSON.stringify 등은 이 시간 바깥에 있다. 엔진의 호출→응답 경과 시간과 실행기 보고 시간을 같은 값으로 취급하지 않는다.

Node IPC는 객체 직렬화가 필요하다. .NET 직접 호스팅은 해당 IPC를 제거할 수 있지만 언어별 interop 마샬링·입력 복사·런타임 진입과 Task 스케줄링은 별도 비용이다. 동일한 managed 인터페이스라고 동일한 비용이 보장되지는 않는다. [Node IPC](https://nodejs.org/api/child_process.html#advanced-serialization), [.NET interop](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices).

## 2. 측정 조건

- Windows 10.0.26200, Intel Core i7-10700F, 논리 CPU 16개, Node v18.20.2. 통제된 전용 성능 시험 호스트가 아닌 현재 개발 PC다.
- 두 경로 모두 같은 `AlgorithmSandbox`/QuickJS 구현과 `return 2`만 하는 알고리즘을 사용한다. 사용자 데이터·서버·외부 서비스는 사용하지 않는다.
- 직접 호출은 부모 프로세스에서 `sandbox.invoke()`를 동기 호출한다. IPC 호출은 기존 `PlayerProcess.move()` 그대로 사용한다. **.NET + Task 직접 호스팅의 대용 측정값으로 사용하지 않는다.**
- 맵/아이템 배열 사본 생성부터 반환까지 host 경과 시간을 측정한다. 직접 호출에도 기존 QuickJS의 JSON 변환 비용이 남는다. 출력·의미 있는 알고리즘 연산은 없다.
- 초기화/프로세스 시작 제외, 120회 워밍업, 400회씩 3라운드. 직접/IPC 1명은 각 1,200개, IPC 4명 동시 호출은 4,800개 응답 지연 표본이다. 시나리오 순서는 라운드별 순환한다.
- 실제 Match/tick·화면/SSE·로그 writer·다중 경기 부하가 없는 짧은 연속 호출 측정이다. IPC 4명은 네 독립 실행기에 동시에 요청하는 조건이며 알고리즘 CPU 부하가 있는 조건은 아니다.

## 3. 관측 결과

모든 값은 ms다. 추가 지연은 서로 다른 두 구성의 평균 차이이며 순수 IPC 전용 비용이나 언어 간 차이가 아니다.

| 맵    | 입력 JSON bytes | 직접 QuickJS 평균 | IPC 1명 평균 | 평균 차이 | IPC 1명 p95 |
| ----- | --------------- | ----------------- | ------------ | --------- | ----------- |
| 12×10 | 341             | 0.0422            | 0.1580       | 0.1159    | 0.2105      |
| 20×16 | 795             | 0.0734            | 0.1907       | 0.1173    | 0.2621      |
| 40×30 | 2,777           | 0.2054            | 0.3505       | 0.1452    | 0.4366      |

| 맵    | IPC 4명 동시 평균 | p95    | p99    | 관측 최대 |
| ----- | ----------------- | ------ | ------ | --------- |
| 12×10 | 0.1709            | 0.2523 | 0.3688 | 2.4646    |
| 20×16 | 0.1991            | 0.2814 | 0.4233 | 2.4956    |
| 40×30 | 0.3603            | 0.4776 | 0.6130 | 2.1645    |

직접 호출 경로도 입력 크기에 따라 비용이 증가한다. 이 실험은 현재 QuickJS 래퍼에서 IPC를 추가했을 때 약 0.12~0.15ms의 평균 차이를 관측한 것이며, C#/C++/Python 호출 비용이나 .NET 직접 실행 시간은 아직 수치화하지 않았다. 평균/P95/관측 최대는 이번 표본의 통계이며 상한 보장이나 다른 호스트 예측이 아니다.

## 4. 게임 공정성에 미치는 영향

현재 엔진은 `await runner.move(...)`가 반환된 시점에 `beginAction`을 시작한다. 따라서 500ms 제한에서 IPC 시간을 제외했더라도 이동 시작은 전달 지연만큼 늦어진다. 빠른 알고리즘에서 호출 비용의 상대적 비중이 커질 수 있다.

액션 완료는 20ms tick에서 확인하고 다음 턴도 이 흐름에서 시작한다. 작은 지연이 같은 tick 안에 흡수될 수도 있고 경계를 넘겨 약 한 tick 늦게 처리될 수도 있다. IPC 비용을 그대로 매 턴 손실로 합산하거나 400ms 대비 비율만 보고 결과 공정성을 판정하지 않는다. 이번 측정에는 tick 경계와 코인 경합이 포함되지 않았다.

현재 모든 참가자가 같은 JS 실행 경로를 쓰지만 프로세스 스케줄링 지연까지 동일하지는 않다. 다국어 추가 시에는 공통 IPC를 쓰더라도 언어별 메시지 처리·런타임 마샬링·GC·시작 워밍업 등이 달라지고, 직접 호스팅도 P/Invoke/JS 호스트/managed 메서드 경로가 달라진다. 어느 방식도 그 자체로 언어 간 호출 비용이 같아지는 보장은 없다.

## 5. 직접 호스팅과의 비교 판단

| 항목             | 게임 엔진 내부 .NET 직접 호스팅                 | 현재와 같은 참가자별 IPC                                                   |
| ---------------- | ----------------------------------------------- | -------------------------------------------------------------------------- |
| 호출 경로        | 인터페이스 → 언어별 래퍼 → 준비된 함수/객체     | 인터페이스 → 프로세스 전송 → 언어별 래퍼 → 함수/객체                       |
| 제거 가능한 비용 | 프로세스 왕복·IPC 직렬화/역직렬화               | 공통 통신/입력 표현·버퍼 재사용 등으로 최적화 가능하나 실제 별도 구현 필요 |
| 남는 차이        | managed/native/script 변환·Task 큐·런타임 락·GC | 언어별 메시지/변환·각 프로세스 스케줄링·런타임 차이                        |
| 실제 비교 상태   | 미구현·미측정                                   | 현재 JS 경로만 측정                                                        |

사용자 제안의 직접 호스팅은 호출 경로에서 프로세스 왕복을 제거하는 방향으로 검토할 근거가 있다. 다만 지금의 Node/QuickJS 직접 측정으로 .NET + 각 언어 + Task의 총 지연을 대신하거나 직접 호스팅의 모든 언어에서 같은 지연을 보장할 수는 없다. 별도 프로세스의 장애 격리와 중단 보장도 함께 검증해야 한다.

## 6. 선택 전 필요한 후속 측정

1. 언어별 동일한 무연산 반환·입력 읽기/검증·출력 없는 호출을 준비하고 준비/컴파일은 제외한다. 결과 의미와 입력 사본/불변성 정책을 통일한다.
2. 직접 호출·실제 Task 실행·IPC 호출의 준비된 인스턴스 지연을 분리해 측정한다. JS/Python의 객체/배열 변환과 C++ ABI, .NET 스케줄링/락도 포함한다.
3. 호출 총시간·실행기 내부시간·변환시간·대기시간을 분리하고 p50/p95/p99·언어 간 편차와 워밍업/GC를 기록한다. 내부 시간의 포함 범위를 언어별로 같게 정의한다.
4. 네 플레이어의 언어/호출 순서/시작 위치를 교차하고 실제 tick·이동·코인 경합과 동시 경기 CPU 부하에서 턴 수·점수/완료 시점을 대조한다.
5. 실제 계산 시간의 경쟁 이점을 유지하면서 허용 호출 편차를 정하고 실행 방식 선택을 확정한다. 느린 실행기에 맞춘 대기·공통 판단 시간·응답 순서를 무시하는 논리 시간 보정은 적용하지 않는다. 호출·변환·불필요한 큐/락 비용을 최소화하고 플레이어별 실행이 서로를 불필요하게 직렬화하지 않는지 검증한다.

이 목록은 비교 설계이며 보류 중인 다국어 실행기 구현을 자동 착수한 것이 아니다. 이번 작업은 현재 JS 측정과 자료 보관만 수행했다.
