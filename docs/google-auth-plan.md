# Google 인증 전환 진행

## 1단계 완료 — 인증 제공자와 서비스 세션 분리

- `src/auth/mock-provider.js`: 로컬 접속·개발용 계정 선택을 검증하고 이메일 신원만 반환한다. 계정 생성이나 세션 발급을 수행하지 않는다. 운영에서 활성화할 수 없다.
- `src/auth/authentication-service.js`: 등록된 제공자로 신원을 확인한 후 내부 계정 연결 함수 `resolveAccount`를 호출한다. 저장소에서 계정 이용 상태·역할을 다시 읽어 서비스 세션을 발급한다. 신원 데이터의 역할은 사용하지 않는다.
- `src/auth/memory-session-store.js`: 8시간 메모리 세션, 재로그인 시 기존 토큰 교체, 만료·로그아웃·사용자 전체 세션 폐기를 담당한다. 서버 재시작 시 재로그인이 필요하다. 현재 쿠키의 HttpOnly·SameSite=Strict·Path 설정을 유지했다.
- `src/authoring-api.js`: 인증 HTTP 요청을 공통 서비스로 위임한다. 관리자 이용 중지 시 공통 세션 폐기와 기존 경기 정리를 수행한다.

기존 `/api/session`, `/api/auth/mock`, `/api/auth/logout` 응답과 로그인 화면은 유지한다. 실패한 로그인은 기존 세션을 폐기하지 않는다. 세션 조회에서 삭제·이용 중지 계정을 발견하면 해당 사용자 세션을 폐기한다.

목업 신원은 이메일로 개발용 계정을 찾는다. 외부 신원이 연결된 계정은 목업 이메일 로그인 대상으로 선택하지 않는다.

## 2단계 완료 — Google 신원과 내부 계정 연결

- 메타데이터 파일의 `identities`에 `{ provider, subject, userId, createdAt }`를 저장한다. Google의 `sub`는 `subject`로 전달하며 이메일은 표시 정보로만 사용한다.
- `findByIdentity(provider, subject)`로 계정을 조회한다. `loginIdentity(identity, { allowCreate })`는 이용 상태 확인과 이메일 갱신을 수행한다. 신규 생성은 `allowCreate: true`일 때만 허용하며 일반 사용자로 생성한다.
- `linkIdentity(userId, identity)`로 기존 계정에 신원을 명시적으로 연결한다. 내부 ID·역할·알고리즘·경기 기록을 유지한다. 서버 내부 메서드이며 공개 HTTP 연결 API는 없다. 운영용 이관 명령은 8단계에서 구현한다.
- 제공자·신원은 한 사용자에게만 연결하고 사용자당 제공자별 신원도 하나만 허용한다. 충돌은 409로 거부하며 생성과 연결은 직렬 쓰기 구간에서 처리한다.
- 이메일이 같아도 기존 계정이나 관리자와 자동 병합하지 않는다. 이메일 변경에도 내부 ID를 유지한다. `identities`가 없는 기존 파일은 그대로 읽는다.
- 공통 인증 서비스에 검증된 Google 신원 처리 경로를 준비했다. 등록된 제공자가 `subject`, `email`, `emailVerified: true`를 반환해야 한다. 신규 가입 승인 콜백은 기본 거부이며 회사 가입 정책은 6단계에서 연결한다.

신원 저장 메서드는 토큰을 검증하지 않으며 아래 서버 인증 제공자가 검증한 신원을 전달한다.

## 3~5단계 구현 완료 — 설정·로그인 시작·콜백 검증

`AUTH_MODE=google`일 때 필수 설정을 검사하고 Google 공식 `google-auth-library`를 사용한다. `.env`는 `npm start`에서 읽으며 비밀값을 Git·HTTP 응답에 포함하지 않는다. 로컬 콜백은 `/api/auth/google/callback`이다.

로그인 시작에서 브라우저 쿠키와 연결된 10분짜리 state·nonce·PKCE 검증자를 생성한다. 콜백은 state를 일회성으로 소비한 뒤 코드를 교환한다. SDK가 서명·발급자·대상·만료를 검증하고 서비스가 nonce·이메일 검증·추가 대상 정보를 확인한다. 내부 사용자 ID와 연결한 후 세션을 발급한다. Google 액세스·리프레시 토큰은 저장하지 않는다. 오류 원문과 인증 코드는 화면에 노출하지 않는다.

동일 브라우저의 새 로그인 시작은 대기 중이거나 코드 교환 중인 이전 시도를 대체한다. 인증 완료 후와 계정 조회 완료 후 최신 시도인지 확인하며, 마지막 확인부터 세션 발급까지는 비동기 대기를 넣지 않는다. 새 시도가 취소·실패해도 이전 시도로 되돌아가지 않는다. 다른 브라우저의 인증에는 영향을 주지 않는다. 완료된 시도의 서버 추적 정보는 정리하고, 오래 걸린 시도도 10분 만료를 확인한다.

`coinhunter-oauth` 쿠키는 콜백에서 삭제하지 않고 브라우저 식별자로 최대 10분 유지하며 새 로그인 시작에서 갱신한다. 이를 통해 코드 교환 중에도 같은 브라우저의 재시도를 구분하고 이전 콜백의 늦은 응답이 새 시도의 쿠키를 삭제하는 문제를 막는다. 쿠키 자체에는 계정 권한이 없고, 인증에는 별도의 일회성 state·nonce·PKCE와 Google 검증이 필요하다. 로그인이 끝난 뒤 동일 state의 재사용은 계속 거부한다.

로그아웃은 해당 브라우저의 최신 인증 추적 정보와 대기 state를 먼저 제거하고 세션을 폐기한다. 이미 Google 코드 교환이나 계정 조회가 진행 중이어도 마지막 최신 시도 검사에서 거부하므로 늦은 응답은 세션 쿠키를 발급하지 못한다. OAuth 쿠키 경로는 `/api/auth`로 설정해 `/api/auth/logout`에도 브라우저 식별자를 전달한다. 로그아웃 시 현재 경로와 이전 버전의 `/api/auth/google` 경로 쿠키를 함께 삭제한다. 다른 브라우저의 인증에는 영향을 주지 않으며 로그아웃 완료 후 새로 시작한 로그인은 허용한다. 이미 시작된 Google 통신의 동시 실행 수 관리는 별도 후속 수정 대상이다.

반복적인 미인증 시작 요청은 TCP 접속 IP별 1분 요청 횟수와 미완료 인증 수로 제한한다. 기본 한도는 60회/분·50개이며 환경변수로 조정한다. 전체 인증 슬롯 1000개와 주소별 요청 추적 항목 4096개의 상한도 유지한다. 주소 추적은 1분 구간 만료 시 정리한다. 새 시도의 수용 여부를 먼저 검사한 다음 기존 시도를 대체하므로 제한에 걸린 재시도가 기존 인증을 무효화하지 않는다. 같은 브라우저의 재시도는 기존 슬롯을 대체하지만 요청 횟수 제한은 적용된다. 콜백 완료·만료 시 슬롯을 회수하고 다른 접속 IP에는 독립 한도를 적용한다. [설정과 프록시 경계](google-auth-setup.md)를 참고한다.

## 6~7단계 로컬 구현 완료 — 가입 정책·로그인 화면

검증된 Workspace `hd` 허용 도메인과 개별 이메일 예외를 설정한다. 허용한 신규 계정은 일반 사용자로 자동 가입한다. 허용 목록은 관리자 승격 기능이 아니다. 계정 이용 중지와 저장된 역할 확인을 유지한다. 로컬에서 허용 목록이 없으면 모든 검증된 Google 계정을 허용하며 운영에서는 명시적 목록을 요구한다.

Google 로그인 버튼·오류 안내·기존 목적지 복원을 연결했다. OAuth용 쿠키와 Google 모드 세션은 SameSite=Lax, HttpOnly이며 HTTPS 설정 시 Secure를 추가한다. 목업은 기존 Strict 세션을 사용한다. 여러 응답 쿠키를 보존해 인증 state와 게스트·계정 세션이 덮어써지지 않게 했다.

**실제 비밀값 입력과 Google 로그인 성공 확인은 아직 진행하지 않았다.** 운영 HTTPS·프록시·도메인 연결도 후속 작업이다. 로컬 설정은 [Google OAuth 실행 안내](google-auth-setup.md)를 따른다.

9. 운영 Host·Origin·HTTPS·인증 중계 경로를 구성한다.

발급한 설정값을 로컬에 입력하고 실제 Google 로그인 확인을 진행한다. 운영 네트워크·최종 회사 가입 도메인은 배포 전에 확정한다.

## 검증

`test/authentication-service.test.js`는 세션 교체·만료·폐기, 로컬 전용 목업, 검증 실패 시 기존 세션 유지, 저장된 권한 사용, 이용 중지, 미구성 제공자의 이메일 연결 차단을 검사한다. 기존 계정 통합 테스트와 작업실 브라우저 테스트로 로그인·저장·테스트 플레이 흐름을 확인한다.

`test/account-identities.test.js`는 기존 관리자·코드 파일·경기 기록 보존, 이메일 변경·충돌, 동시 생성·연결 충돌, 잘못된 신원·이용 중지 차단, 신규 가입 승인과 저장된 권한 사용을 검사한다. Google 제공자는 테스트 대역이며 실제 Google 인증 성공을 의미하지 않는다.

`test/google-auth.test.js`와 `scripts/google-auth-smoke.js`는 실제 SDK의 로컬 서명 검증과 HTTP·브라우저 로그인을 검사한다. 외부 Google 통신만 대체하며 실제 발급된 Google 토큰을 사용하는 검증은 별도로 진행한다.
