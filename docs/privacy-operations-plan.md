# 개인정보 운영 준비 — 배포 전 마지막 필수 단계

- 작성일: 2026-10-11
- 상태: 필수 작업으로 지정. 운영 정책 확정·사용자 화면·삭제 기능의 본격 구현은 기능 개발과 배포 구성 검증 뒤, 실제 사내 서비스 개시 전에 진행한다.
- 범위: OAuth, 사용자·관리자 계정, 알고리즘·경기 기록, AI 연결·요청, 접속 정보·로그, 파일·DB·백업·외부 제공자.
- 목적: 최종 단계에서 정책·안내·삭제 실행 기능을 연결할 수 있도록 지금부터 데이터와 저장 경계를 준비한다. 법적 준수 완료를 선언하는 문서는 아니다.
- 관련 문서: [전체 계획](implementation-plan.md), [AI 계획](ai-scripting-plan.md), [저장 어댑터](storage-adapters.md), [체크리스트](work-checklist.md).

## 1. 진행 시점과 완료 조건

지금은 새 기능마다 아래 설계 조건을 적용하고 개인정보 운영 준비 전체를 먼저 구현하지 않는다. 최종 단계에서 실제 운영자·배포 지역·제공자·처리 목적에 맞는 정책과 개인정보 담당자 검토를 마무리한다. 필수 단계이므로 미완료 상태에서 사내 실서비스를 개시하지 않는다.

실제 데이터의 외부 전송 허용 여부나 API 키 처리 권한처럼 개별 기능 사용에 앞서 필요한 조건은 마지막 단계로 미루지 않는다. 개발·검증은 최소 데이터와 테스트 계정을 사용하고, 허용되지 않은 업무 자료를 외부 AI에 보내지 않는다.

## 2. 앞으로의 개발에 적용할 설계 조건

1. **최소 수집:** 기능에 필요한 항목만 처리한다. OAuth 이메일·sub 외의 이름·사진 등 새 개인정보를 편의상 추가하지 않는다. 권한 범위는 구성과 제공자 계약에서 조정할 수 있게 한다.
2. **소유권:** 계정 소유 데이터에는 내부 사용자 ID를 연결한다. 이메일을 파일 경로·삭제 기준·외부 요청 식별자로 사용하지 않는다. 게스트·임시 데이터는 별도 수명 식별자를 둔다.
3. **데이터 목록:** 새 저장 항목의 목적, 소유자, 저장 위치, 외부 전송 여부, 보유·정리 계기를 기록한다. 파일·메타데이터·캐시·로그·백업을 구분한다.
4. **정책 분리:** 보유 기간·후보 수명·로그 수명·허용 제공자·전송 범위는 서버 정책/설정에서 관리한다. UI·게임 엔진에 기간을 흩어 넣지 않는다. 정책 버전과 변경 경계를 둔다.
5. **삭제 가능한 저장 계약:** 목록·저장뿐 아니라 소유자별 조회·삭제·취소·만료 정리를 추가할 수 있는 저장소 계약으로 만든다. 임시 데이터는 생성 기능과 함께 정리를 구현한다. 최종 계정 삭제 UI·전체 삭제 조율은 마지막 단계에 구현한다.
6. **원문 분리:** 코드 원문과 AI 후보는 파일, 메타데이터는 저장 어댑터, 자격 증명은 전용 저장소로 분리한다. 코드 사본·경기 당시 코드·비밀 참조도 소유자별로 추적 가능하게 한다.
7. **외부 전송 경계:** AI 입력은 명시적인 허용 항목으로 구성한다. 이메일·Google sub·세션 토큰·연결 이름·내부 파일 경로·다른 사용자 데이터는 기본 입력에 포함하지 않는다. API 키는 인증에만 사용하며 프롬프트에는 넣지 않는다.
8. **자격 증명:** 원문 키·토큰을 일반 메타데이터·API 조회 응답·URL·로그·브라우저 영구 저장소에 기록하지 않는다. 임시 키와 저장 키의 수명을 구분하고 암호화 키는 데이터와 분리한다.
9. **로그 분리:** 운영·접근 기록은 목적에 필요한 필드만 기록한다. 코드·요청문·응답 원문을 일반 로그로 남기지 않는다. 보안상 필요한 접속기록과 디버그 출력은 별도 범위·권한·수명으로 다룬다.
10. **화면 연결 지점:** 처리방침·고지·필요한 동의 화면을 마지막에 붙일 수 있게 로그인·연결 등록·외부 전송 진입점을 유지한다. 필수 서비스 처리와 선택적인 AI 전송을 같은 동의로 암묵적으로 묶지 않는다.
11. **진행 작업과 삭제 경합:** 계정·연결 삭제 또는 이용 중지 시 새 요청을 차단하고 진행 중 경기·AI·검사·업로드·SSE·세션을 정리할 수 있게 수명 관리 서비스를 둔다. 늦은 결과가 삭제한 데이터를 다시 저장하지 못하게 상태/리비전을 확인한다.
12. **저장 구현 독립:** 파일 어댑터에서 DB로 전환해도 위 소유권·정리·비밀 경계가 유지되게 한다. UI가 실제 저장 파일을 직접 수정하거나 삭제하지 않는다.

이미 구현된 기능에서 조건이 충족되지 않는 부분은 최종 점검 대상으로 기록하고 해당 영역을 수정할 때 반영한다. 이번 문서 변경으로 기존 구현이 모두 조건을 충족했다고 간주하지 않는다. 최종 단계의 목표는 설정·안내·삭제 조율·검증으로 마무리하며 새로 개발한 기능의 저장 구조를 재설계하지 않는 것이다.

## 3. 최종 단계의 작업 순서

| 순서 | 작업 | 산출물·검증 |
| --- | --- | --- |
| 1 | 전체 데이터 처리 목록 확정 | OAuth·계정·코드·경기·AI·접속 기록의 항목·목적·소유자·저장/전송 위치 |
| 2 | 운영 조건과 처리 근거 검토 | 운영자·담당 창구, 실제 Azure/백업 지역·외부 제공자·위탁/국외 이전 조건·약관 |
| 3 | 최소 수집과 보유 정책 확정 | OAuth scope 재검토, 필수/선택 처리 구분, 보유·파기·백업 만료 설정 |
| 4 | 처리방침·안내·필요한 동의와 권리 요청 경로 구현 | 로그인·AI 연결·전송 안내, 적용 시 고지/동의 기록의 정책 버전, 열람·정정·삭제·처리정지 요청 |
| 5 | 계정/데이터 삭제와 운영 정리 구현 | 재인증·요청 확인, 세션/진행 작업 취소, 사용자 메타데이터·키·코드·경기 사본 정리 |
| 6 | 백업·보존 예외·복원 절차 조정 | 필요한 법적 보존의 별도 격리, 백업 만료, 삭제 이력 최소 보관과 복원 후 삭제 재적용 |
| 7 | 실제 환경 검증과 담당자 검토 | 프록시 로그·콜백 URL·쿠키·키 유출 검사, 타인 접근·삭제 경합·파일 정리·복원 검증 |
| 8 | 배포 전 필수 완료 확인 | 처리방침·운영 절차·검증 결과와 남은 조건 기록 후 실서비스 개시 |

삭제는 서비스 계정과 데이터에 적용하며 사용자의 Google 계정 자체를 삭제하지 않는다. 이미 외부 제공자에 전송된 입력은 로컬 파일 삭제만으로 지워졌다고 표시하지 않는다. 외부 보존·삭제 요청 가능 여부는 실제 계약에 맞게 안내한다.

## 4. 우선 점검할 기존 항목

- Google `profile` scope의 필요성 및 실제 계정 수집 정보와의 일치.
- 자동 가입 시 서비스 데이터 처리 안내와 보유 기간.
- 이용 중지와 별개인 계정 삭제, 계정에 연결된 경기 기록·코드 사본 정리.
- 관리자 계정·유지보수 CLI·데이터 파일과 백업 접근 범위.
- 로그인 세션·OAuth/IP 임시 집계와 배포 프록시 접속기록의 수명.
- Azure 호스팅·백업·Google 인증·각 AI 제공자에 대한 실제 데이터 흐름.
- 서비스 재시작·백업 복원·늦은 비동기 결과로 삭제 데이터가 재생성되는 경합.

## 5. 개발 단계에서의 완료 판단

각 새 기능은 최소 수집·소유권·저장 경계·임시 정리·늦은 결과 차단을 해당 구현 단계에서 검사한다. 운영 정책 확정·개인정보 화면·계정 전체 삭제는 이 문서의 마지막 필수 단계에서 진행한다. 동의 문구 추가나 암호화만으로 법적 의무가 모두 충족됐다고 표시하지 않는다.
