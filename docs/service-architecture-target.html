1. 전체 방향과 전제

2026-11-14 제품 변경: 직접 AI API 연결은 현재 서비스에서 제거했다. 이 문서의 직접 연결 구성은 당시 목표 기록이며, 작성 지원은 프롬프트 후속 계획을 따른다. FE·BE 분리와 다국어 구현 보류 상태는 유지한다.

하나의 서비스 주소 아래에서 FE 웹서버·BE 서버·알고리즘 실행 환경을 분리한다. 사용자는 브라우저만 사용하며 코드 저장·컴파일·실행·경기 판정은 서버에서 처리한다. 사용자 PC에 알고리즘 실행기를 설치하지 않는다.

여러 언어 지원 대상은 C#·C++·JavaScript·Python이다. 각 실행기는 공통 입력·출력과 시간 제한·인스턴스 수명 계약을 만족해야 한다. 게임 화면과 게임 엔진은 언어와 독립적으로 유지한다.

아직 해결되지 않은 전제: 경기 중 인터프리터 실행까지 배제하면서 턴별 500ms 중단과 동일 프로세스·인스턴스 유지를 보장할 언어별 실행 환경은 선정되지 않았다. 현재 QuickJS와 일반적인 Python 실행은 바이트코드 인터프리터를 사용한다. 아래 구조는 해당 요구를 통과한 실행기를 연결한다는 목표이며, 네 언어의 모든 문법·라이브러리를 지원할 수 있다고 확정한 것은 아니다.

게스트는 로컬 파일을 업로드해 게임을 실행한다. 계정 단위 알고리즘 생성·저장·불러오기와 과거 경기 알고리즘 대결은 로그인 사용자에게 제공한다. 로그인 사용자는 다른 PC에서도 본인 계정의 알고리즘과 경기 기록에 접근한다.

다른 사용자의 코드는 기본적으로 공개하지 않는다. 선택적 공유 더미나 대회는 별도 기능이며 FE·BE 분리와 언어 지원만으로 구현 완료된 것으로 간주하지 않는다.

4. FE 웹서버의 책임

FE는 단일 접속 창구다. HTML·CSS·JavaScript·이미지·영상을 제공하고 /api/*를 설정된 내부 BE 주소로 전달한다. 브라우저는 FE와 BE의 별도 주소를 관리하지 않으며 기존 API 상대 경로를 사용한다.

페이지 진입 시 BE의 인증 상태를 조회해 로그인 화면으로 이동하거나 접근 거부를 표시한다. 편집기 보안 헤더와 요청별 CSP nonce도 FE 제공 계층에서 처리한다. 작업실과 테스트 플레이 iframe은 같은 공개 Origin에서 동작한다.

FE는 점수·아이템 획득·사용자 권한을 확정하지 않는다. 화면에서 권한을 확인했어도 BE는 모든 API에서 인증·역할·소유권을 독립적으로 검사한다. FE에 원문 저장소·사용자 데이터·Google secret·AI 키·암호화 키를 배포하거나 보관하지 않는다.

운영에서는 공개 HTTPS 주소와 신뢰할 프록시를 명시적으로 설정한다. FE가 외부에서 받은 전달 헤더를 그대로 신뢰하지 않으며 BE의 Host·Origin·쿠키·OAuth 검증과 일치시킨다. 실제 도메인·TLS 종료 위치·VPN 경로는 배포 검증에서 확정한다.

처음에는 하나의 BE 인스턴스 안에서 모듈을 분리한다. 각 기능을 처음부터 별도 네트워크 서버로 만들지는 않는다. 게임 상태의 최종 권한은 서버에 있고, 브라우저는 입력·렌더링·애니메이션을 담당한다.

외부 AI 직접 연결과 복사용 프롬프트 생성은 함께 제공한다. 프롬프트 생성만 사용하는 경우 AI API 연결이나 유료 호출이 필요하지 않다. 직접 연결 시에는 BE가 제공자 인증·요청을 담당한다. 실제 외부 접속 경로와 회사 네트워크 허용 여부는 별도 배포 조건이다.

6. 코드 준비와 경기 실행 분리

경기 시작 전

원문 파일과 언어 확인
 → 문법·게임 규약 검사
 → 필요한 컴파일·실행 준비
 → 실행 전 검사
 → 준비 완료
 → 경기 생성·참가자별 로드·Player 생성·초기화
 → 모든 참가자 준비 완료 후 경기 진행

컴파일·필수 준비·실행 환경 로드는 경기가 진행되기 전에 끝낸다. 컴파일 시간과 준비 시간은 턴 실행 시간과 구분하고 별도 시간·메모리·동시 작업 제한을 적용한다. 컴파일 과정도 신뢰하지 않는 코드 처리로 격리한다.

준비된 실행 결과는 원문 내용·언어 버전·컴파일러·실행 규약·대상 환경에 따라 구분해 재사용할 수 있다. 코드나 실행 환경이 바뀌면 다시 준비한다. 결과 파일을 재사용해도 사용자 권한 검사를 생략하거나 실행 중 객체를 공유하지 않는다.

경기 진행 중

같은 Player 인스턴스의 moveNext(현재 맵, 현재 위치, 아이템)를 반복 호출한다. 원문 파일 재로딩·재파싱·컴파일을 매 턴 수행하지 않는다. 호출에는 최신 게임 입력을 전달하고 결과를 기존 게임 엔진이 판정한다.

인스턴스 유지와 인터프리터 사용 여부는 별개다. Python의 바이트코드 사전 준비나 C#의 DLL 생성만으로 경기 중 인터프리터/JIT 배제를 충족했다고 처리하지 않는다. 이 조건은 언어별 실행기 확정 전에 별도로 검증한다.

7. 공통 실행 계약과 언어별 실행기

공통 기능 역할
prepare 코드 검사·필요한 컴파일·실행 결과 준비
initialize 경기 참가자의 Player 인스턴스 생성·초기화
getName 알고리즘 이름 조회
moveNext 맵·현재 위치·아이템을 받아 이동 방향 계산
close 경기 종료 후 인스턴스·프로세스 정리

prepare는 경기 전 준비 계층에 속하며 나머지는 참가자별 실행 환경의 계약이다. 경기 중 엔진은 언어별 컴파일 방식이나 런타임 내부를 알 필요가 없다.

실행 결과는 정상·시간 초과·예외·잘못된 반환값 상태, 방향(-1 또는 0~3), 실행 시간, 제한된 디버그 출력으로 통일한다. 런타임 자체 장애는 정상적인 턴 시간 초과와 구분해 별도 장애 정책으로 처리한다.

언어 현재 상태와 목표 검토 방향
JavaScript 현재 QuickJS 실행기 보유. 인터프리터 배제 조건을 엄격히 적용하면 재검토 필요
Python 제한된 실행 환경과 허용 모듈·문법을 검토. 일반 인터프리터만으로 추가 성능 조건을 충족한다고 가정하지 않음
C++ 사전 컴파일과 제어 가능한 실행 환경 검토. Wasm 후보도 중단 후 객체·메모리 상태 보존 검증 필요
C# 제어 가능한 실행 환경 검토. DLL 생성과 JIT 없는 사전 실행 코드 생성을 구분하고 중단·동일 객체 재호출을 검증

네 언어의 실행 환경·지원 버전·문법·표준 라이브러리는 확정 전이다. 모든 외부 패키지와 일반 개발 환경 전체를 제공하는 것을 기본 범위로 삼지 않는다. Wasm 실행 중단 기능 자체가 언어 런타임 내부 상태까지 복구해 주는 것은 아니다.

8. 경기별·참가자별 인스턴스 수명

경기 A
 ├─ 참가자 1 전용 프로세스 → Player A
 └─ 참가자 2 전용 프로세스 → Player B

경기 B
 ├─ 참가자 1 전용 프로세스 → Player C
 └─ 참가자 2 전용 프로세스 → Player D

같은 알고리즘 코드가 A와 C에 사용되더라도 변수·방문 기록·턴 상태·메모리는 공유하지 않는다. 코드의 준비된 결과만 재사용할 수 있고 런타임 객체는 경기마다 새로 생성한다. 서로 다른 언어가 한 경기에 참가해도 엔진은 같은 계약으로 호출한다.

참가자들은 독립적으로 턴을 수행한다. 한 참가자가 계산 중이더라도 다른 참가자의 정상 턴을 기다리게 하지 않는다. 같은 참가자의 이전 호출이 끝나기 전에 다음 호출을 중첩하지 않는다.

각 호출은 최대 500ms를 기준으로 독립 판정한다. 실행기가 현재 계산을 실제 중단하고 이번 턴의 이동을 -1 제자리 패널티로 처리한다. 응답만 버리고 계산을 계속하거나 프로세스·인스턴스를 재생성하는 방식은 허용하지 않는다. 중단 이후 다음 턴은 같은 인스턴스로 호출하고 경기가 완전히 끝나면 정리한다. 500ms는 통신·대기·애니메이션 시간이 아니라 알고리즘 실행 구간의 기준이며 감지·스케줄링 오차를 포함한 검증이 필요하다.

지원 확정 전 필수 실험은 정상 실행 → 상태 변경 → 무한 루프 중단 → 동일 PID·인스턴스의 정상 재호출이다. 예외 포착·finally·긴 내장 연산·재귀·메모리 고갈·다른 참가자의 독립 실행도 검증한다.

알고리즘 원문을 DB의 텍스트 필드로 옮기지 않는다. 언어·버전·원문 파일 참조 등을 메타데이터로 관리하고 원문은 파일로 유지한다. 과거 경기의 코드는 이후 원본 수정과 독립된 사본을 사용한다.

현재 메타데이터는 파일 어댑터를 사용한다. FE·BE 분리와 다국어 지원만 완료했다고 DB 연결까지 완료되는 것은 아니다. 실제 DB 어댑터 연결은 별도 배포 작업으로 검증하며 원문 파일 보관 원칙은 유지한다. 기존 JS 데이터에 언어 정보가 없으면 JavaScript로 해석하는 호환 경로를 설계한다.

원문·기록·캐시·임시 파일·비밀의 소유권과 정리 경계를 유지한다. 로그에 코드·쿠키·OAuth code/state·AI 키를 남기지 않으며 FE의 공개 산출물에 사용자 데이터를 포함하지 않는다.

10. 배포와 확장

최초 운영은 한 호스트·한 컨테이너 안에서 FE·BE와 참가자별 실행 프로세스를 관리하는 구성을 지원한다. 외부에는 서비스 진입점만 노출하고 프로세스 관리자가 서버 준비·종료·실패를 관리한다. 실제 이미지·관리자·운영 OS·TLS 구성은 배포 단계에서 확정한다.

이후 FE와 BE를 다른 컨테이너나 호스트에 배치할 수 있도록 내부 연결 설정을 분리한다. 사용자 주소와 API 경로는 유지한다. 프로세스를 분리해도 같은 호스트의 CPU·메모리는 공유하므로 동시 경기·컴파일 작업·실행 메모리·출력에 한도를 적용한다. 언어별 런타임 기본 메모리와 알고리즘 메모리는 구분해 측정한다.

FE만 재시작할 때 BE의 경기·세션은 유지하고 브라우저가 재연결하도록 구성한다. BE 재시작 후 진행 경기 복구나 여러 BE의 분산 운영은 이 고도화만으로 제공되지 않는다. 현재 메모리 세션·OAuth 진행 상태·경기·일부 AI 요청 상태를 여러 서버가 공유하는 설계는 별도 확장 작업이다.

실제 사내 네트워크·VPN·Google/AI 외부 연결·브라우저·동시 경기 부하는 배포 검증에서 확인한다. 개인정보 운영 준비는 기존 합의대로 실제 서비스 개시 전 마지막 필수 단계다.

11. 적용 범위와 보관 원칙

이 문서는 최종 목표를 설명하기 위한 보관 문서다. 현재 코드·설정·서버 실행을 변경하거나 고도화 구현을 시작하지 않는다. 고도화 착수 시 보관 목록과 상세 계획을 기준으로 당시 코드와 배포 조건에 맞춰 범위를 다시 정한다.

FE·BE 분리와 다국어 지원은 독립적으로 진행할 수 있다. 다국어 지원의 첫 작업은 공통 실행 계약과 기존 JavaScript 동작의 보존, 후보 언어의 중단·상태 유지·성능 조건 검증이다. 네 언어의 지원 범위는 검증 결과를 근거로 확정한다.
