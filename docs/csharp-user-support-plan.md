# C# 사용자 지원 연결

실행기 후보를 사용자 기능에 연결한다. 기본 설정은 비활성이며 최종 통합 검증·적대적 리뷰·베타 활성화는 이번 구현 범위에서 제외한다. 단계별 빌드와 변경 경로의 집중 검사는 수행한다.

1. 공통 언어 capability와 Windows/로그인 전용 C# 베타 정책, 실행 서비스의 준비 상태, 별도 자원·GC 정책을 연결한다.
2. 파일 원문과 언어 메타데이터를 함께 보관하고 현재 코드/소유자/검사 규약을 대조한다. 저장 성공과 실행 허가는 분리하며 게임 입장 때 원문 사본을 다시 검사한다.
3. 작업실의 언어 선택·C# 편집/빈 문서·샘플·규약·컴파일 진단과 테스트 전달을 연결한다. 언어도 문서 변경 상태에 포함한다.
4. 게임의 업로드/저장 코드·혼합 언어·이전 경기 코드 사본에 언어를 유지한다. 기존 기록의 누락 언어는 JavaScript로 해석한다.
5. 후속: 최종 전체 흐름·보안/적대적 리뷰 후 베타 활성화 여부를 결정한다. 엄격한 500ms 물리적 정지·Linux 격리·운영 사양 승인은 별도 관문이다.

공통 설정은 `Backend:Languages:CSharpBetaEnabled`이며 Operations와 Execution 양쪽에 적용해야 한다. 이번 작업에서 실제 `.env`나 실행 중인 서비스 설정을 바꾸지 않는다. 일반 JavaScript 자원 정책도 그대로 유지한다.

## 1~4단계 구현 결과

### 정책·서버 계약

- 공통 `AlgorithmLanguages` 정책과 공개 `GET /api/languages`, 내부 `GET /internal/v1/languages`를 추가했다. Operations 설정과 실행 서비스의 실제 준비 상태가 모두 맞아야 화면에 C# 사용 가능으로 표시한다. C#은 Windows·로그인 전용 베타다.
- 두 서비스의 기본 `Backend:Languages:CSharpBetaEnabled`는 false다. 기존 내부 후보 검사/경기 분기는 그대로 유지한다. C# 베타의 일반 경기 요청만 기존 private player 채널에 연결한다.
- C# 베타 게임은 별도 `CSharpGameMemoryMiB=2304`, `CSharpGameCpuRate=10000`, 프로세스 5개 정책을 사용한다. 일반 JS 게임의 기본 1,024MiB/CPU 25% 정책은 바꾸지 않았다. 베타 게임당 C#은 최대 2명이다.
- 베타 실행에는 GC 구간·진입 복구 v2, C#당 768MiB와 엔진/JS 그룹 512MiB를 적용한다. 내부 실험의 메모리 override를 베타에 그대로 적용하지 않는다. 전체 예산은 게임 1개 외 준비용 1,536MiB 이상 여유를 요구한다.
- 500ms 알고리즘 판정, 정상 timeout의 동일 인스턴스 재사용, 계산 완료 후 즉시 액션 정책은 유지한다. 운영 watchdog·강제 종료는 사용자 timeout과 구분한다.

### 저장·검사

- 원문 업로드/레거시 JSON 요청에 `language`를 받는다. 생략한 기존 요청은 JavaScript이며 기존 알고리즘 수정에서 생략하면 원래 언어를 유지한다. 다른 언어로 덮어쓰기는 거절하고 새 알고리즘으로 저장하도록 한다.
- 원문은 파일, 언어·해시·revision·검사 결과는 메타데이터로 유지한다. 기존 파일 어댑터의 불투명 UUID `.js` 파일명은 이관 없이 유지하며, C# 원문도 파일로 저장한다. 실행 언어는 확장자로 추측하지 않고 메타데이터/실행 계약으로 결정한다. 사용자가 내보내거나 업로드하는 파일은 `.cs`다.
- C# 검사 결과의 owner/hash/fixture/profile/toolchain/call count를 대조한 뒤 현재 베타 정책과 함께 실행 가능 상태를 계산한다. 원래 preflight report의 `executionAllowed=false`는 유지하며 검사 결과만으로 언어를 활성화하지 않는다.
- 같은 코드의 저장 버전·검사 시도 CAS를 유지한다. 동일 정책/규약의 베타 검사 상태는 재시작 후 유지할 수 있으며 중단된 검사·후보 전용 결과·버전 변경은 재검사가 필요하다. 실제 게임 입장에서는 항상 실행용 사본을 재검사한다.

### 작업실

- 언어 선택, C# 표시 lexer, 언어별 빈 문서·샘플·확장자, C# 서명/입력/승인 API·한도 안내를 추가했다. 컴파일 진단 코드·행/열과 실행 검사 정보를 표시한다. Roslyn과 실행 검사가 판정을 담당하며 표시 lexer는 검증기가 아니다.
- 언어 변경은 새 문서로 전환하고 기존 문서에 다른 언어를 덮어쓰지 않는다. 미저장 여부와 테스트 코드 변경 상태에 언어도 포함한다.
- 저장/불러오기/파일 가져오기/내보내기와 테스트 iframe 메시지에 언어를 유지한다. 베타가 꺼진 저장 C#은 읽을 수 있지만 저장·검사·실행은 서버에서 거절한다.
- 기존 프롬프트 생성은 JavaScript 전용으로 유지한다. C# 문서에서는 해당 사이드바를 숨기고 안내한다. C# 프롬프트 고도화는 이번 작업 범위에 추가하지 않았다.

### 플레이·기록

- `.cs` 업로드와 저장 C# 선택, C# 샘플 다운로드, 선택한 언어 표시를 추가했다. 게스트는 JS만 사용한다.
- 현재 코드와 이전 경기 상대의 언어를 각각 서버에서 결정하고 해당 언어로 재검사/실행 요청한다. 더미는 기존 JS다. 경기 기록에는 주 알고리즘의 언어·원문 해시와 코드 파일 사본을 보관한다. 언어가 없는 기존 기록은 JS다.
- 비활성 언어의 저장 코드/이전 기록은 선택을 막고 이유를 표시한다. C# 테스트도 기존처럼 맵·위치만 선택하며 별도의 알고리즘 선택 단계는 표시하지 않는다.
- C# 준비/재검사를 수용하도록 FE 프록시의 수동 검사 요청은 150초, 게임 생성은 360초의 idle timeout을 사용한다. 내부 검사/준비의 별도 상한을 대체하지 않는다. C# 저장 검사 상태 조회도 더 오래 기다린 뒤 지연을 안내한다.

## 개발 중 확인

- 별도 빌드 `artifacts/csharp-user-support-build`: 경고/오류 0개.
- 서버 컴포넌트 22건: 정책·자원 설정·샘플 정적 규약·검사 결과 바인딩·혼합 실행 요청·기록/원문 사본 보존을 확인했다. 실행 서비스는 테스트 대역이며 실제 신규 베타 게임을 시작하지 않았다.
- 기존 C# 계정 검사 회귀 44건: 실제 준비/preflight·언어/hash/revision CAS·변조 보고서·기본 게임 비활성 유지 통과.
- Node 집중 검사 21건: 언어/진단과 기존 작성 규약·C# 어댑터 검사 통과.
- 작업실 브라우저 컴포넌트 7시나리오: 비활성 capability, C# 편집 모드, 오류 위치, 언어 저장/불러오기, `.cs` 내보내기, iframe 언어 전달, JS 복귀를 테스트 응답으로 확인했다. 실제 게임을 시작하지 않았다.
- [집계 기록](benchmarks/csharp-user-support-components-2026-11-20.json)을 보관한다. 변경 뒤 전체 회귀·실제 HTTP/브라우저/게임 흐름·교차 언어 대결·장시간 부하·최종 적대적 리뷰는 아직 수행하지 않았다.

## 최종 검증 대기

아래 단계가 끝나기 전에는 기본 설정을 true로 바꾸지 않는다.

1. 실제 두 서비스와 브라우저에서 JS/C#의 작성·업로드·저장·검사·테스트·플레이·결과·기록을 확인한다.
2. C#↔JS와 C#↔C# 이전 경기 대결, 원문/메타데이터 변경·소유권·재시작·비활성 설정·동시 준비/자원 포화를 확인한다.
3. 최종 적대적 리뷰와 수정 후 베타 정책을 승인한다. 필요 시 이번 연결을 포함한 장시간 시험을 다시 수행한다. 이전 30분 결과는 이번 UI/API 연결을 검증한 결과가 아니다.
4. 활성화하기로 한 경우에만 두 서비스에 `Backend__Languages__CSharpBetaEnabled=true`를 적용하고 재시작한다. `npm start`는 신뢰된 빌드 HostAssembly 경로를 주입하며 수동 실행은 해당 절대 경로를 운영 설정으로 지정해야 한다.

엄격한 물리적 500ms 정지, 모든 허용 연산의 경계, Linux 격리, 실제 배포 사양별 용량 승인은 별도 미완료 관문이다. 이번 구현/개발 중 확인을 정식 운영 승인으로 해석하지 않는다.
