## 1. 목표와 현재 상태

```text
C# 실행 관리 서비스
  → 게임별 Node 게임 엔진
      → 언어와 무관한 플레이어 실행기 계약
          → 선택한 언어의 준비된 실행 산출물
          → 게임별·플레이어별 독립 인스턴스
```

게임 엔진은 Node를 기준으로 작업한다. C#은 운영/실행 관리 서비스와 알고리즘 지원 언어라는 두 역할을 구분한다. 게임 엔진의 C# 포팅은 이번 범위에 포함하지 않는다.

| 영역        | 이미 구현된 기반                                  | 이번에 필요한 작업                                      |

## 2. 변경하지 않을 실행·데이터 조건

1. **독립 진행:** 계산 결과가 준비되면 해당 플레이어 액션을 시작하고 액션 완료 후 같은 인스턴스에 다음 판단을 요청한다. 다른 참가자의 결과를 기다리는 턴 장벽·최소 판단 시간·논리 시간 보정은 추가하지 않는다. 준비 단계의 전체 참가자 초기화 확인과 구분한다.
2. **비중첩:** 같은 플레이어는 한 번에 하나의 판단/액션만 수행한다. timeout 응답이나 취소 요청만으로 busy를 풀지 않고 실제 호출 중단을 확인한다.
3. **500ms:** 각 호출에서 독립 판정한다. 정상 timeout 때 프로세스/객체 재생성·상태 초기화·결과만 무시하고 백그라운드 계산을 계속하는 방식을 사용하지 않는다. `Task.WhenAny`/취소 토큰 발급 자체는 중단 검증을 대신하지 않는다.
4. **상태 유지:** 로드·객체 생성·initialize/getName은 게임 준비 단계에서 수행한다. 판단 중 변경된 필드의 자동 롤백을 가정하지 않는다. 중단 뒤에도 유효한 인스턴스로 다음 호출이 가능해야 한다.
5. **턴 의미:** -1/timeout 패널티는 이번 턴의 제자리 액션이다. 랜덤점프는 알고리즘 호출을 생략한다. 신발·망치·효과 교체와 이동/대체 액션의 기존 시간 규칙을 유지한다.
6. **준비 분리:** 매 턴 원문 재로드·재평가·컴파일을 하지 않는다. 사전 바이트코드/산출물 준비와 런타임 내부의 인터프리터/JIT 실행은 구분한다. 후자까지 금지하는 조건으로 단정하거나 사전 컴파일만으로 제거했다고 주장하지 않는다. 4단계에서 언어별 실제 실행 형태와 요구 충족 범위를 명시한다.
7. **호출 경로:** 엔진과 실행기 사이에서 판단을 완결한다. 운영 API·DB·화면·로그 저장 완료를 매 턴 기다리지 않는다. 공통 인터페이스나 동일 IPC만으로 호출 비용이 같다고 간주하지 않는다.
8. **보관/권한:** 원문은 파일로 유지한다. 산출물·캐시·로그·진단에도 소유권과 삭제 가능한 참조를 둔다. 사용자 요청에 임의 실행 명령/물리 경로를 허용하지 않는다. 코드 파일의 새 제품 크기 상한을 도입하지 않는다.
9. **오류 분리:** 사용자 예외/잘못된 반환/timeout과 호스트 장애·프로토콜 손상·메모리/컴파일/기록 실패를 구분한다. 전체 종료의 프로세스 정리를 정상 턴 timeout 처리로 사용하지 않는다.

500ms 예산에 포함되는 경계는 1단계에서 문서화한다. 현재 JS의 `elapsedMs`에는 QuickJS 입력 parse/dispatch가 포함되며 순수 사용자 함수 시간이라고 표시하지 않는다. 언어별로 측정하기 어렵다는 이유로 기존 JS 예산을 조용히 변경하거나 실제 경과 시간을 소급 보정하지 않는다.

## 4. 단계별 상세 계획

### 1단계 — 공통 실행 계약과 JS 기준선

- 게임 엔진용 `AlgorithmRunner` 계약과 준비/컴파일용 `AlgorithmPreparer` 계약을 분리한다. 실제 타입 표현은 현재 Node의 JSDoc/검증 모듈을 우선하며 대규모 TypeScript 전환을 요구하지 않는다.
- runner의 initialize/move/close, 이름/인스턴스 정보와 생성 factory의 입력을 정의한다. 사용자 코드의 initialize/getName/moveNext를 엔진 계약과 혼동해 변경하지 않는다.
- `gameId/playerId/runId/callId`, language, artifact 참조, runtime/adapter 버전의 위치를 정의한다. source/비밀 값은 로그나 공통 메시지에 복제하지 않는다.
- created→initializing→ready→computing→ready→closing→closed와 failed 상태, 유효한 호출 순서·중복 종료·실제 중단 확인을 명시한다. 엔진의 acting 상태와 runner의 준비 상태를 구분해 액션 중 다음 판단이 호출되지 않도록 한다.
- 정상 -1, timeout, exception, invalid-result와 infrastructure failure의 결과/예외 형식, debug 출력/생략 수를 정한다. 메모리 초과를 식별할 수 있는지와 식별할 수 없는 한계도 분리한다.
- map/myPosition/items의 값·스냅샷 시점·복사/소유권, 초기화 인자와 불변 산출물의 수명을 정의한다.
- 입력 준비/전달·실행·응답·엔진 반영 시간의 측정 경계와 500ms 예산을 정하고 무연산/입력 읽기/보통 탐색의 현 JS 기준을 남긴다.

**완료 기준:** 계약 문서·타입/결과 검증과 현 구현 대응표, 재현 가능한 JS 기준 측정. 다른 언어를 지원 목록에 등록하거나 게임 진행 방식을 변경하지 않는다.

### 2단계 — JS 정식 어댑터와 registry

- `PlayerProcess`/worker/QuickJS를 첫 정식 어댑터로 감싼다. `Match`의 기본 생성 구현과 JS 결과 형식 의존을 공통 계약 경계로 옮긴다.
- 참가자 language/산출물/실행 옵션을 전달하는 registry/factory를 만든다. 현재 활성 언어는 javascript뿐이며 알 수 없는 언어를 JS로 묵시 변환하지 않는다.
- 생성된 자원은 즉시 추적한다. factory나 일부 초기화가 실패해도 이미 만든 모든 runner를 정리하고 부분 준비 상태가 남지 않게 한다.
- 초기화/미응답/프로세스 단절·늦은 응답·중복 close·종료 기한을 정리한다. 정상 턴 timeout과 전체 프로세스 수명 실패를 구분한다.
- 기존 게임과 코드 검사 경로가 같은 JS 어댑터/정책을 사용하도록 연결하고 필요한 검사 전용 옵션을 명시한다.

**완료 기준:** 기존 JS 회귀 통과, 정상→timeout→정상의 PID/인스턴스/필드 유지, 비중첩·부분 생성 실패·정상/비정상 종료 정리 검증. 기존 공개 JS 알고리즘과 저장 데이터가 동작한다.

### 3단계 — 엔진의 독립 진행과 수명

- `GameState`의 규칙, `Match`의 진행/runner 제어, 화면 snapshot/전량 이벤트의 역할을 분리한다. 제어 가능한 clock/random·runner·기록 sink 경계를 시험에서 사용할 수 있게 한다.
- 계산 완료→액션 시작→액션 완료→다음 판단의 경로를 명확히 한다. 시작 전 준비 확인 외에 참가자 전체를 기다리는 장벽을 만들지 않는다.
- 현재 20ms tick을 먼저 기준으로 유지하고 액션 완료→다음 호출 지연을 측정한다. 스케줄링 방식 변경은 8단계의 근거와 회귀 조건에 따른다.
- start/stop·초기화 중 취소·액션 중 종료·판단 중 종료·늦은 응답의 상태 전이를 검증한다. runner/호스트 장애가 해당 참가자/전체 게임 중 어디에 적용되는지 명시하고 기존 전체 종료 정책을 임의로 바꾸지 않는다.
- 사용자 -1/timeout, 벽 충돌/망치, 신발, 아이템 효과 만료/교체, 랜덤점프 호출 생략을 대조한다.

**완료 기준:** 느린/빠른 가짜 runner 및 실제 JS runner로 독립 진행·동일 플레이어 비중첩·게임 규칙/종료 회귀 통과. 단지 취소 응답을 빨리 반환한 것을 계산 종료로 간주하지 않는다.

### 4단계 — 언어별 기술 검증과 선정 관문

- C#·C++·Python 각각의 최소 Player와 실행 호스트 후보를 만든다. JS는 같은 계약의 비교 기준으로 사용한다. 이때 필요한 최소 사전 빌드와 5단계의 제품용 준비/캐시 구현은 구분한다.
- 후보의 직접 호스팅/IPC, 런타임 내부 실행 형태, 컴파일·JIT·인터프리터 범위, 허용 문법/표준 라이브러리, 설치/배포 의존성을 기록한다. Wasm 등 특정 기술을 미리 최종 해법으로 확정하지 않는다.
- 정상→필드 변경/무한 루프→500ms 실제 중단→같은 인스턴스 정상 호출을 확인한다. PID뿐 아니라 run/instance ID·생성/초기화 횟수·변경한 필드로 판정한다.
- catch/finally 우회, 재귀, 긴 내장/네이티브 연산, 메모리 고갈, 호스트 파일/네트워크/스레드 접근, 악성 컴파일 입력과 다른 참가자의 진행 영향을 검증한다.
- 같은 입력의 무연산·배열 읽기·반복 호출을 측정한다. 같은 managed wrapper/IPC라도 변환·런타임 락·스케줄링 편차가 있는지 확인한다.
- 결과를 후보별 보고서와 실행 환경/버전으로 보관하고 **채택/조건부·추가 검증/보류**를 판정한다. 설치·조사한 상태를 실제 지원으로 표시하지 않는다.

**통과 조건:** 호출 실제 중단·동일 상태 인스턴스의 유효한 재호출·다른 참가자 독립성·격리와 자원 한도·사전 준비가 검증된 후보만 5~6단계로 진행한다. 명령 수/fuel 제한을 500ms 경과 시간 제한과 동일하게 간주하지 않는다.

**미통과 시:** 원인과 대안, 지원 가능한 제한 범위를 보고한다. 프로세스 재생성/결과 버리기/요구 완화로 통과 처리하지 않는다. 해당 언어 단계는 미완료로 남기고 검증된 JS/공통 작업은 유지한다. 게임 규칙이나 지원 조건 변경이 필요하다면 구체 검증 결과를 기준으로 별도 결정한다.

### 5단계 — 사전 준비·컴파일·불변 산출물

- 소유권이 확인된 원문 파일/언어/승인된 옵션을 받아 검사→준비/컴파일→산출물 검증→보관→ready로 진행한다. 게임 중에는 이 작업을 반복하지 않는다.
- 준비 작업은 실행과 별도의 동시 한도·시간·메모리·출력·임시 디스크 제한을 둔다. compiler 입력도 신뢰하지 않으며 임의 명령/옵션·경로·외부 패키지 다운로드를 허용하지 않는다.
- 키는 원문 hash·언어/계약·컴파일러/런타임·adapter 버전·승인 옵션·대상 OS/architecture를 포함한다. 내용이 바뀌면 이전 산출물을 재사용하지 않는다.
- 동일 준비 요청의 중복, 준비 중 취소/실패, 부분 파일, 캐시 쓰기 충돌과 손상 검사를 구현한다. 컴파일 진단은 원문 위치에 대응시키고 호스트 물리 경로/환경 비밀을 제거한다.
- 원문/산출물/진단 메타데이터와 캐시 접근 권한, 활성 게임 읽기 lease, 미참조/버전 폐기·실패 정리를 정의한다. 캐시 bytes 재사용과 플레이어 가변 상태 재사용은 구분한다.

**완료 기준:** 재컴파일 없는 산출물 재사용, 변경/버전 차이에 따른 무효화, 동시 빌드·취소·손상·디스크 부족·타인 참조 거부 검증. 원문은 파일로 유지하고 새 코드 크기 상한을 만들지 않는다.

### 6단계 — 언어별 정식 어댑터와 규약

- 4단계 채택 후보를 공통 runner/preparer 계약으로 구현한다. 기본 구현 순서는 JS 기준 확정 후 C#을 우선하고 Python/C++ 순서는 검증 결과에 따른다. 순서 때문에 기술적으로 미검증인 언어를 건너뛰어 지원 완료로 표시하지 않는다.
- 준비된 산출물에서 게임별·플레이어별 객체를 생성하고 동일 객체에 메서드를 반복 호출한다. 다른 게임/참가자에게 static/global/모듈 상태가 공유되지 않게 한다.
- initialize/getName/moveNext에 대응하는 언어별 템플릿, 정수/배열·문자열 인코딩, 반환/예외/debug.print 규약을 정의한다. JS 문법 금지를 C#/C++/Python 구문에 그대로 복사하지 않고 원래 주의사항의 목적을 유지한다.
- 초기화·이름·판단·출력·중단·종료를 정규화하고 진단을 코드 검사 경로에 연결한다. 준비 성공만으로 실제 실행 검사 통과를 반환하지 않는다.
- 언어별 최소 샘플·정상/timeout/잘못된 반환/메모리/금지 기능의 검증 자료를 보관한다.

**완료 기준:** 채택 언어 각각의 작성/검사/실행 규약과 adapter 검사 통과. 같은 계약으로 JS와 교체 가능하고 중단 후 동일 상태 재호출이 실제로 확인된다.

### 7단계 — 계측·자원·전량 로그

- 호출별 run/instance/call ID, language/runtime/artifact/adapter 식별자와 시간 측정값을 기록한다. 알고리즘 호출이 없는 점프 이벤트도 명시한다.
- 입력 준비/전달·실행·응답·액션 반영을 같은 단조 시계/측정 경계로 정리한다. 프로세스간 시계 정렬이 필요한 값과 각 프로세스 내부 duration을 구분하고 단순 차감으로 정확한 구간이라고 주장하지 않는다.
- 런타임 기본 메모리·알고리즘 한도·전체 실행 호스트 자원을 구분한다. 현재 QuickJS 32MiB를 전체 Node 프로세스 또는 모든 언어의 동일한 메모리 한도라고 설명하지 않는다.
- 출력/응답/작업 큐 한도와 host crash·미응답·프로토콜 오류·메모리/저장 실패의 식별/정리 경로를 구현한다.
- 기존 collector/storage/receipt·부분 복구와 연결한다. 로그 때문에 매 턴 저장 완료를 기다리지 않으며 드롭/누락과 수집 실패를 숨기지 않는다. 원문·인증 비밀을 추가로 기록하지 않는다.

**완료 기준:** 모든 언어의 호출/생략/실패를 전량 이벤트와 추적으로 대조할 수 있고 정상 종료·부분 기록·실제 중단 확인이 일치한다. 어댑터 교체로 로그 저장 구현을 다시 작성하지 않는다.

### 8단계 — 호출 비용과 진행 성능 최적화

- 입력 크기·플레이어 수·언어/시작 위치/호출 순서 교환·동시 게임 수를 바꿔 p50/p95/p99, 자원·큐/락·GC·tick 지연을 측정한다. 미지원 언어는 측정/완료 표에서 제외 사유를 남긴다.
- 무연산/입력 읽기/동일 탐색·빠른/느린 합성 알고리즘으로 인프라 비용과 실제 계산 성능을 구분한다. 언어 자체의 수행 속도까지 동일해진다고 약속하지 않는다.
- 중복 JSON 변환/복사, 불필요한 Task/Promise 큐, 공통 락과 응답 병목을 근거에 따라 줄인다. 버퍼 재사용/전달 방식 변경은 입력 격리와 메모리 안전 조건을 함께 검증한다.
- 20ms tick의 다음 판단 지연을 평가하고 필요할 때 액션 완료 스케줄링을 개선한다. 동일 시점 충돌·기믹·아이템 판정 순서와 수명 회귀를 함께 검사한다.
- 후보가 요구를 만족하지 못하면 4단계 선택 근거를 재검토한다. 비교 근거 없이 고정 ms 허용 편차나 보정 배율을 정하지 않는다.

**완료 기준:** 재현 가능한 원시 집계·환경/버전·개선 전후 보고서, 빠른 계산이 불필요하게 대기하지 않는 증거, 느린 참가자가 다른 참가자를 논리적으로 막지 않는 증거. 자원 경합에 의한 지연과 엔진 장벽을 구분한다.

### 9단계 — C# 실행 관리와 운영 API 통합

- C# 요청/검증·Node 초기화·registry의 지원 언어를 일치시킨다. 런타임/컴파일러가 준비된 언어만 capability에 표시하며 사용자가 내부 명령·산출물 경로를 지정하지 못하게 한다.
- 운영의 파일 업로드/저장/검사·경기 준비 요청에 language와 계약/산출물 참조를 연결한다. 작성 원문은 계속 파일로 보관한다.
- 기존 언어 필드가 없던 알고리즘/기록은 JS 호환 정책으로 해석하고, 새 데이터는 명시적으로 언어를 보관한다. 언어가 바뀐 원문에 이전 캐시/진단이 적용되지 않게 한다.
- 본인 이전 경기 재대결은 당시 원문/언어를 기준으로 다시 준비하거나 호환 산출물을 검증해 사용한다. 혼합 언어 참가자·별도 code validation·준비 한도·취소를 연결한다.
- 수락/준비/시작/종료·멱등 요청·결과 재전달과 권한을 검증한다. 엔진과 runner의 실제 턴 호출이 운영 API/DB를 거치지 않게 유지한다.

**완료 기준:** 게스트/계정/본인 이전 기록의 BE API로 언어별 준비·검사·혼합 실행·종료/요약·로그 조회가 가능하고 기존 JS 요청/기록이 동작한다. 이 단계의 BE 지원과 FE의 언어 선택/편집 기능 제공 완료를 구분한다.

### 10단계 — 통합·장애·부하·운영 검증

- 언어 조합과 참가자/위치 교환, 동시 게임·준비/컴파일·업로드·검사·SSE·전량 기록을 함께 검증한다.
- 루프/메모리/출력 초과·실행기/엔진/실행 관리 장애·부모 단절·저장/캐시 손상·컴파일 취소를 주입하고 잔류 자원/정리 기한·다른 게임 영향·결과/저널 상태를 확인한다.
- 반복 생성/종료와 장시간 동일 인스턴스 호출의 메모리·핸들·프로세스 누수를 검사한다. 운영 자원에 맞는 동시 실행/준비 한도를 제시한다.
- 개발/운영용 도구 체인 버전·빌드/캐시/검사/개별 실행·진단·복구·무효화/정리 절차와 지원 언어/제한 표를 보관한다. 로컬 검증과 원격 CI·컨테이너·실제 사내 배포 결과를 구분한다.
- 전체 변경의 적대적 리뷰 후 결함을 수정하고 재검증한다. 최종 결과를 보고하고 사용자 리뷰를 기다린다.

**완료 기준:** 실제 지원 언어별 검증표·소스/테스트·재현 가능한 계측/부하·장애 보고와 실행 문서. 보류/미통과 언어가 있다면 다국어 전체 완료로 표시하지 않는다. FE 언어 UI·실제 배포·개인정보 운영 준비가 끝났다고 간주하지 않는다.

## 5. 주요 코드 배치안

```text
backend/node/src/game/                규칙·독립 턴·진행/수명
backend/node/src/runtime/
  contracts/                         공통 runner/preparer·결과/상태 검증
  registry.js                        활성 언어와 factory 선택
  javascript/                        기존 PlayerProcess/worker/QuickJS의 어댑터
backend/node/src/execution/           엔진 진입점·준비/참가자 연결·기록
backend/runners/                      채택한 C#/C++/Python 호스트·wrapper 후보
backend/contracts/                   내부 DTO/언어·산출물·시간/오류 계약
backend/src/CoinHunter.Execution.Host 준비/게임 수명 관리·capability·오류 전달
backend/src/CoinHunter.Operations.Api 소유권·파일/메타데이터·검사/경기/기록
backend/tests/                       C# 계약/준비/권한 통합 검사
test/                               runner·게임 규칙·수명 회귀
scripts/                            후보 검증·계측·혼합 실행/장애 도구
```

세부 경로는 1~2단계에서 기존 호출/검사 경로를 확인해 확정한다. 아직 채택하지 않은 언어의 빈 production 프로젝트를 먼저 만드는 것을 산출물로 삼지 않는다. 기존 공개/내부 경로 변경이 필요하면 호환/버전 변경 근거를 함께 남긴다.
