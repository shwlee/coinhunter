# 새 게임 아키텍처 설계안

- 작성일: 2026-09-27
- 상태: 설계안과 첫 구현 기록. 현재 동작 범위는 [진행 결과](progress.md), 실행 검증은 [검증 보고서](runtime-verification.md)를 참고한다.
- 요구사항 기준: [전체 작업 계획](implementation-plan.md)
- 준비 및 실행 항목: [작업 준비 체크리스트](work-checklist.md)
- 사용자가 확정한 규칙과 아래 기술 제안을 구분한다. 요구사항을 기술 편의에 맞춰 변경하지 않는다.

## 1. 설계 목표

웹에서 파일 업로드, 알고리즘 작성·AI 생성·저장, 개인 경기와 더미 대결, 관리자 맵 편집을 제공한다. 첫 알고리즘 언어는 JavaScript다. 사용자 PC에는 별도 실행 프로세스를 설치하지 않는다.

게임 엔진과 사용자 알고리즘 실행을 분리한다. 플레이어별 턴은 독립적으로 진행하며, 각 알고리즘 호출은 최대 500ms다. 시간 초과 때 프로세스나 인스턴스를 재시작하지 않고 현재 호출만 중단해야 한다. 알고리즘 인스턴스는 경기가 완전히 끝날 때까지 유지한다.

## 2. 전체 구성 제안

```text
사용자 브라우저
 ├─ 게임 플레이
 ├─ 코드 편집 / AI 작성 / 디버그 출력
 └─ 관리자 화면
          │ HTTP API / 실시간 경기 연결
          ▼
애플리케이션 서버
 ├─ 인증·권한
 ├─ 알고리즘·맵·옵션 관리
 ├─ 경기 관리자
 │    └─ 경기별 게임 엔진
 │         └─ 실행 관리자
 │              ├─ 플레이어 A 실행 프로세스
 │              ├─ 플레이어 B 실행 프로세스
 │              ├─ 플레이어 C 실행 프로세스
 │              └─ 플레이어 D 실행 프로세스
 └─ AI 연결 계층
          ├─ 데이터베이스 / 임시 업로드 저장소
          └─ 별도 확정할 AI 중계 경로
```

초기에는 애플리케이션 서버를 하나의 배포 단위로 구성하고 알고리즘 실행을 별도 프로세스로 분리하는 방안을 제안한다. 인증·저장·경기·AI 모듈을 내부적으로 분리하여 후속 확장 시 경기 실행만 다른 서버로 옮길 수 있도록 한다. 서버 수, 프로세스 배치 및 동시 경기 한도는 측정 후 정한다.

브라우저는 입력과 표현을 담당한다. 서버가 위치·점수·효과·게임 종료의 최종 상태를 결정한다. 선택 기능인 공유 더미는 서버에서 실행하여 다른 사용자의 브라우저에 소스를 전달하지 않는다.

## 3. 모듈별 책임

| 모듈 | 책임 | 포함하지 않는 책임 |
| --- | --- | --- |
| 웹 UI | 화면, 입력, 애니메이션, 편집기, 출력 표시 | 최종 점수·획득 판정 |
| 인증·권한 | 세션, 역할, 소유권 검사 | 사용자 코드 실행 |
| 콘텐츠 관리 | 알고리즘·맵·옵션 저장과 조회 | 진행 중 경기 상태 변경 |
| 경기 관리자 | 참가 구성, 시작 준비, 종료, 실행 환경 수명 | 사용자 알고리즘 계산 |
| 게임 엔진 | 턴·이동·효과·기믹·점수·종료 판정 | 브라우저 렌더링, DB 직접 접근 |
| 실행 관리자 | 요청 식별, 프로세스 수명, 호출·출력·오류 전달 | 게임의 방향·점수 결정 |
| JS 실행 환경 | 제한된 코드 로딩, 인스턴스 유지, 호출별 중단 | 호스트 파일·네트워크·프로세스 API 제공 |
| AI 연결 | 규약·요청 구성, 제공자 연결, 응답 검증 | 게임 엔진 우회 실행 |

## 4. 경기 생명주기

1. 사용자가 본인 코드 또는 파일, 맵, 더미, 허용된 기믹 옵션을 선택한다.
2. 서버가 인증·소유권·입력값·맵 공개 상태를 검사한다.
3. 경기 ID를 발급하고 코드·맵·옵션을 시작 시점 값으로 고정한다.
4. 참가자별 실행 프로세스를 준비하고 클래스를 로딩한다.
5. initialize와 getName을 호출하여 시작 준비를 완료한다.
6. 경기 시작 후 플레이어별 독립 턴과 시간 기반 기믹을 진행한다.
7. 코인 소진 등 종료 조건이 확정되면 새 턴·새 기믹을 발행하지 않는다.
8. 경기 종료 처리에서 실행 환경을 정리하고 결과를 표시·기록한다.

시작 준비 실패, 사용자 종료, 연결 끊김, 서버 장애의 상태 전이는 상세 규칙에서 정의한다. 연결 끊김만으로 경기 종료나 프로세스 종료를 자동 결정하지 않는다. 종료 이후 도착한 결과가 상태를 바꾸지 않도록 한다.

## 5. 게임 엔진과 독립 턴

엔진은 맵 크기·타일·아이템, 플레이어 위치·점수·액션·효과, 턴 번호, 요청 상태, 경기 시각, HurryUp과 기믹 일정을 관리한다.

```text
판단 준비
 ├─ 일반: 사용자 알고리즘 호출 (최대 500ms)
 └─ 랜덤점프: 사용자 호출 없이 게임 측 목적지 선택
        ↓
현재 상태와 판단 결과 검증
        ↓
이동 / 벽 파괴 / 제자리 패널티 / 순간이동 / 점프 실패
        ↓
액션 시간 종료 → 적용 효과 횟수 갱신 → 다음 턴
```

- 한 플레이어의 이전 호출·액션이 완료되기 전에 다음 턴을 시작하지 않는다.
- 다른 플레이어는 동시에 알고리즘을 실행하거나 액션을 진행할 수 있다.
- 공통 턴이나 모든 플레이어의 응답을 기다리는 장벽을 도입하지 않는다.
- 맵·아이템 배열은 호출 시점 사본이다. 액션 적용 때 최신 맵을 확인한다.
- 공용 상태 변경은 경기 엔진이 순서대로 확정한다. 알고리즘 연산까지 순차 처리하는 것은 아니다.
- 동일 코인·아이템 중복 획득과 동일 벽 중복 차감을 막는다.
- 효과 차감은 해당 턴에 적용된 효과를 대상으로 한다. 이동 중 새로 얻은 효과를 이전 효과 대신 차감하지 않는다.
- -1 및 시간 초과는 이번 턴의 제자리 패널티이며 다음 턴을 추가로 소모하지 않는다.
- 이동과 대체 액션의 시간은 동일해야 한다. 신발은 알고리즘 계산 시간을 줄이지 않는다.

이동 도착·코인 획득·벽 파괴를 액션 종료 시 확정하는 방안을 제안한다. 이는 아직 확정 규칙이 아니다. 도중 맵 변화와 동시 완료 시 우선순위를 함께 정해야 한다. 신발 중 대체 액션 시간, 플레이어끼리 통행 방해 여부, 이동 중 배치 제외 기준 위치도 상세 규칙에서 고정한다.

## 6. 브라우저 표현과 동기화

엔진은 상태 변경 및 액션 이벤트를 발행한다. 이동 이벤트에는 경기·플레이어·턴 식별자, 출발·도착 위치, 서버 시작 시각, 액션 시간을 포함하는 방안을 제안한다.

브라우저는 해당 시간 동안 위치를 보간하고 아이템별 외형·이펙트를 표시한다. 서버의 진행을 브라우저 프레임 속도나 애니메이션 완료 응답에 의존시키지 않는다. 서버 시각과 클라이언트 시각 차이, 지연 수신 시 표시 보정은 통신 명세에 포함한다.

실시간 이벤트에는 순번을 부여하고 재연결 때 현재 상태와 기준 순번을 전달한다. 전체 경기 리플레이 저장은 별도 범위이며 이 구조만으로 자동 제공되는 기능은 아니다.

## 7. JavaScript 실행 환경

```text
플레이어 실행 프로세스 — 경기 동안 유지
 ├─ 실행 제어부 / 호출 식별 / 출력 수집
 └─ 제한된 JavaScript 실행 환경
      └─ 사용자 Player 인스턴스 — 경기 동안 유지
```

기존 클래스·module.exports 형식을 지원하는 로더를 제공하되, require를 비롯한 임의의 Node.js 기능을 허용한다는 의미는 아니다. built-in 허용 목록과 기존 작성 금지 사항을 실행 환경에 적용한다.

인터페이스 초안:

```javascript
class Player {
    initialize(myNumber, column, row) {
        this.myNumber = myNumber;
        this.column = column;
        this.row = row;
    }

    getName() {
        return "My Player";
    }

    moveNext(map, myPosition, items) {
        debug.print("현재 위치", myPosition);
        return 2;
    }
}

module.exports = Player;
```

- debug.print는 제안 이름이다. 실제 API와 직렬화 규칙은 algorithm-api.md에서 확정한다.
- 맵 크기는 initialize에서 전달한다.
- items는 `[신발, 망치, x2, 랜덤점프]`의 위치이며 없는 경우 -1이다.
- 기존 두 인자 moveNext와의 호환성을 확인한다.
- 랜덤점프 중 사용자 moveNext를 호출하지 않는다. 게임 측 플레이어 상태와 사용자 알고리즘 인스턴스를 혼동하지 않는다.
- 출력에는 경기·플레이어·턴을 붙인다. 메시지 길이·호출당 출력량을 제한하고 텍스트로 표시한다.

### 500ms 중단 검증

500ms는 사용자 함수 호출 직전부터 반환 또는 중단까지의 실행 구간에 적용한다. 시작 준비·대기열·브라우저 통신·액션 시간과 구분한다. 시간 측정 방식과 관측된 중단 지연을 기록한다.

필수 실험은 같은 프로세스·인스턴스로 다음 순서를 수행하는 것이다.

1. 정상 호출에서 인스턴스 필드를 기록한다.
2. 다음 호출에서 무한 루프를 실행한다.
3. 현재 호출만 시간 제한으로 중단한다.
4. 다음 호출에서 기존 필드를 읽고 정상 반환한다.
5. 다른 플레이어의 턴이 그동안 정상 진행되었는지 확인한다.

try/catch·finally, 종료되지 않는 built-in 연산, 과도한 출력, 시간 초과 후 재호출도 시험한다. 단순 타이머·Promise.race·응답 폐기·프로세스 재시작은 이 요구의 구현으로 인정하지 않는다.

첫 구현은 시간 초과 이전 필드 변경을 유지한다. 메모리 고갈과 프로세스 자체 장애는 500ms 초과와 구분한다. QuickJS 기반 검증에서 같은 인스턴스를 유지한 무한 루프 중단·정상 재호출을 확인했다. 측정과 한계는 runtime-verification.md에 기록했다.

## 8. 데이터 설계 방향

| 데이터 | 주요 필드 |
| --- | --- |
| 사용자 | ID, 로그인 식별 정보, 역할, 계정 상태 |
| 알고리즘 | ID, 소유자 ID, 이름, 언어, 코드, 생성·수정 시각, 선택적 더미 허용 |
| 맵 | ID, 이름, 가로·세로, 타일 배열, 공개 상태, 아이템·기믹 설정 |
| 게임 설정 | 기본 액션 시간, 효과별 횟수, 운영 설정 |
| 경기 결과 | 경기 ID, 참가 정보, 맵 식별 정보, 점수, 종료 사유 |

DB 제품과 실제 테이블·제약 조건은 아직 선정하지 않았다. 저장은 현재 코드를 갱신하고, 새 이름으로 저장은 새 알고리즘을 생성한다. 사용자용 이력 테이블·복원 UI는 만들지 않는다.

진행 중인 경기의 코드·맵·옵션 사본은 실행 일관성을 위한 것이며 영구 코드 이력과 구분한다. 결과·턴 로그·임시 업로드의 보존 기간은 별도로 정한다. 소유자 ID는 서버 인증 정보로 부여하고 모든 조회·변경 요청에서 검사한다.

## 9. API와 실행 프로세스 통신

| 경계 | 정보 |
| --- | --- |
| 브라우저 → HTTP API | 로그인, 파일 업로드, 코드·맵 저장과 조회, 경기 생성 |
| 서버 → 실시간 연결 | 상태 사본, 위치·액션·점수·효과 이벤트, 출력, 오류, 종료 |
| 경기 엔진 → 실행 관리자 | 로딩, 초기화, 이름 조회, 이동 요청, 경기 종료 |
| 실행 환경 → 실행 관리자 | 결과, 출력, 시간 초과, 예외, 준비 상태 |

실제 URL·메시지 스키마·전송 기술은 data-and-api.md에서 정한다. 프로세스 간 통신에 기존 HTTP 구조를 반드시 유지할 필요는 없다. 모든 호출은 경기·플레이어·요청 ID로 연결하며 잘못된 요청 또는 이전 턴의 결과를 거부한다. 대기열·연결 해제·메시지 크기 제한도 정의한다.

## 10. AI 연결

```text
자연어 요청 + 현재 코드 + 공통 게임 작성 규약
 → AI 연결 계층 → 확정할 중계 경로 → 제공자
 → 응답 검사 → 편집기 반영 → 공통 테스트 플레이 → 저장
```

AI 생성 코드에도 같은 제한·검증·실행 경로를 사용한다. 최초 생성과 수정 모두 지원하고 실패 시 기존 코드 보존 방식을 정의한다. 별도 영구 이력은 추가하지 않는다.

게임 호스트는 외부망에 직접 접근할 수 없으므로 외부 API 직접 호출을 가정하지 않는다. 사내망에서 접근 가능한 중계 위치, Azure VPN 경로, 인증, 자격 증명 보관, 요청 데이터 이동 범위를 조사한다. 이 조사는 게임 구현과 병행하여 조기에 시작한다. 개발용 대체 응답은 가능하지만 실제 연결 전에는 AI 필수 기능을 완료 처리하지 않는다.
