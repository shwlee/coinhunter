# 전량 턴 로그 저장소·저장 모듈 분석

- 분석일: 2026-11-15
- 책임 경계 보완: 사용자 정의의 **게임 운영 BE**와 **게임 실행 BE/실행 데이터 수집**을 분리한다. 운영 NoSQL은 업무 데이터, 이 문서의 저널은 언어 중립 실행 데이터의 저장 계약이다. [백엔드·데이터 경계](game-backend-boundaries.md)를 우선한다. Node 모듈 후보는 현재 수집기 구현 후보이며 타 언어 실행을 Node 로거에 종속시키지 않는다.
- 신규 요구: 매 턴 발생하는 게임 결과를 빠짐없이 기록한다. JSONL과 같은 순차 이벤트 형식을 검토한다.
- 상태: 현재 코드와 공식 문서를 근거로 한 분석/설계 제안. 저장소 선정 확정·패키지 설치·기능 구현·배포는 하지 않았다.
- 추천: **메타데이터 DB + 경기별 JSONL 저널 + 전용 writer worker**, 이후 필요하면 완결 파일을 Azure Blob Storage에 보관한다. 운영 로그와 전량 경기 기록은 수명·필터·완전성 계약을 분리한다.
- 기존 결정: 알고리즘 원문은 파일로 유지한다. 프롬프트 수정·다국어 보류를 유지하고 FE/BE는 최신 사용자 결정에 따라 [BE 분리 계획](backend-separation-implementation-plan.md)부터 진행한다. 이 문서가 해당 분리 구현이나 DB 제품 전환을 완료했다는 의미는 아니다.
- 모듈 설계: [로그 수집 모듈·추상화 계약](game-log-collection-modules.md)에 공개 인터페이스·구현 주입·수집 정책/저장 어댑터 분리·교체 보장·단계별 검증을 구체화했다. 아래 JSONL/worker는 첫 구현 후보이며 엔진의 필수 의존성이 아니다.

## 1. 현재 구현에서 확인한 차이

- [Match](../backend/node/src/game/match.js)의 로그 배열은 debug 출력이 있거나 오류/-1인 경우에만 추가하고 최근 40건만 유지한다. 성공 이동 전체나 실제 액션 완료 전체가 아니며 영구 기록도 아니다.
- `publish()`는 20ms tick의 화면용 상태 사본과 최근 로그를 SSE에 전달한다. 이 순번은 전량 턴 이벤트 순번이 아니다. SSE 구독은 연결 지연/종료에도 영향을 받으므로 저장 원본으로 사용하지 않는다.
- [GameState](../backend/node/src/game/state.js)의 `beginAction`은 실행할 액션을 정하고 `completeAction`에서 실제 위치·코인·아이템·벽·효과·점수를 확정한다. 알고리즘 방향만 기록하면 실제 경기 결과를 복원할 수 없다.
- 랜덤점프 턴은 moveNext를 호출하지 않는다. 턴 완료·실패를 별도로 기록해야 한다.
- 현재 실행기는 잘못된 반환값을 -1로 정규화하고 일반 경기의 임의 예외 객체를 펼쳐 전달하지 않는다. 잘못된 원본 반환의 유형/제한된 표현이나 상세 예외 메시지까지 필요하면 실행 결과 계약도 확장해야 한다. live guest 객체의 JSON 직렬화로 해결하지 않으며 진단 수집 비용·시간 제한도 검증한다.
- Hurry Up, 아이템 출현, BlackMatter, 랜덤 벽 파괴는 플레이어 턴 바깥에서 맵을 변경한다. 변경 결과도 기록해야 한다.
- 같은 tick에서 완료 처리는 안정적인 플레이어 순서로 적용되지만 알고리즘 결과 도착은 비동기다. 공통 1~4인 라운드를 가정하지 말고 경기 전역 이벤트 순번과 플레이어별 턴 번호를 함께 사용해야 한다.
- [서버](../backend/node/src/server.js)는 현재 종료 시 계정 경기 요약/코드 사본을 기록하며 일부 종료 사유와 게스트는 경로가 다르다. 전량 저널은 계정 경기 요약과 별도의 수명으로 일반/대결/테스트/게스트·초기화 실패·중단도 처리해야 한다.

## 2. 저장할 범위와 형식

| 이벤트                             | 기록할 내용                                                                                                                                        |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| match.started / player.initialized | 로그 schema/엔진 버전, 맵 크기·초기 배치·옵션·시작 위치·캐릭터·참가자 식별자, 알고리즘 해시/기존 보관 참조, 초기화 결과                            |
| turn.started                       | 경기 전역 seq, playerId, turnId, 단조 증가 경과 시간, 호출 당시 위치·아이템·맵 상태 버전                                                           |
| algorithm.result                   | 정상/timeout/exception/잘못된 반환, 정규화된 방향, 알고리즘 소요 시간, 제공되는 제한된 오류 정보/debug 출력과 생략 수. 랜덤점프는 호출 생략을 명시 |
| action.started                     | 서버가 선택한 move/confused/penalty/break/jump/jump-failed, 출발/목표·시작/예정 종료 시각·효과                                                     |
| turn.completed                     | 실제 확정 위치·점수 증감·코인/아이템 획득·벽 파괴·효과 교체/차감 및 관련 맵 변화                                                                   |
| world.changed                      | 아이템 출현, Hurry Up 시작/코인 소멸, BlackMatter 생성, 랜덤 벽 파괴의 실제 위치·값·시각                                                           |
| turn.cancelled / result.discarded  | 종료로 완료하지 못한 턴과 늦게 도착해 적용하지 않은 결과. 같은 턴을 완료와 취소로 중복 집계하지 않음                                               |
| match.ended                        | 최종 상태·점수·통계·종료 사유·턴별 완료/취소 수와 최종 seq                                                                                         |

한 JSONL 줄은 직렬화된 이벤트 하나다. 새 journal seq를 BE가 부여하고, 같은 경기의 writer 하나가 순서대로 기록한다. 코드 원문·OAuth 이메일/sub·토큰·내부 경로는 매 턴 본문에 넣지 않는다. 초기 상태와 모든 확정 변화, 호출 당시 상태 버전으로 입력을 재구성하고 주기적 체크포인트를 검토한다. 매 턴 독립적인 전체 입력 사본이 필요하면 full-input 모드를 별도로 정하고 용량을 측정한다.

이벤트에는 라이브 guest 객체를 넘기지 않고 엔진의 검증된 DTO/사본만 넘긴다. JSON 문자열 안의 개행은 escape해 JSONL 레코드 경계를 유지한다. 초기/주기적 상태와 실제 랜덤 결과·적용 순서를 남기므로 알고리즘을 다시 실행하지 않는 화면 재생을 설계할 수 있다. 시드만 보관해서 비동기 경기를 동일하게 재실행할 수 있다고 가정하지 않는다. 리플레이 UI 자체는 별도 작업이다.

엔진 결과는 샘플링·최근 N건 잘라내기 없이 기록한다. `debug.print`는 기존 실행 규약의 30개/메시지 길이 제한을 유지하고 생략 수를 남긴다. 무제한 debug 텍스트 수집까지 요구하는 경우에는 별도 정책 변경이며 현재 분석에서 임의로 실행 제한을 해제하지 않는다.

로그 기능 때문에 기존 원문 보관 정책을 확대하지 않는다. 기존에 보관하는 원문/경기 사본은 참조하고 그 외에는 해시 등만 기록할 수 있다. 게스트 원문을 자동 영구 보관하지 않으며 로그 기반 화면 재생에 코드 원문 재실행은 필요하지 않다. 참가자별 debug 출력의 조회 권한도 분리해 경기 조회 권한만으로 타인의 비공개 출력까지 공개하지 않는다.

## 3. 저장소 비교

| 후보                               | 이 요구에서의 장점                                                          | 추가 설계/운영 부담                                                         | 제안                                                   |
| ---------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------ |
| 영구 볼륨의 경기별 JSONL           | 순차 append, 경기별 조회·전송·삭제·압축·복구가 단순하고 추가 DB 서버 불필요 | 쓰기 큐·순서·동기화·중간 실패·공간 부족·검색 인덱스를 구현해야 함           | 1차 전량 기록 원본으로 추천                            |
| MongoDB의 이벤트별 문서            | matchId/seq/player/status 등으로 턴 조건 검색·집계 가능                     | 모든 이벤트의 DB 쓰기/인덱스·접속·배치 실패·재시도/중복 처리·운영 필요      | 처음부터 턴 단위 온라인 검색이 핵심이면 유력 후보      |
| 관계형 DB의 이벤트별 행/JSON 컬럼  | 계정/경기와 연결한 검색·집계·트랜잭션                                       | 전량 이벤트 쓰기와 인덱스·보관/삭제 비용을 메타데이터 운영과 함께 감당      | 가능하지만 JSONL 보관을 위해 필수인 선택은 아님        |
| Azure Block Blob의 완결 JSONL/gzip | 완결 파일의 원격 보관·배포 호스트와 독립된 수명에 적합                      | 경기 도중 로컬 큐/파일의 내구성과 업로드 실패 재시도 필요                   | 2차 아카이브로 추천                                    |
| Azure Append Blob에 실시간 append  | 클라우드가 append를 받아 보관할 수 있음                                     | 네트워크 지연/중단, append 횟수 한도, 조건부 append와 재시도 중복·순서 관리 | 로컬 내구 저장을 둘 수 없는 배포 등 별도 조건에서 검토 |

MongoDB는 경기 전체 로그를 문서 하나의 배열로 계속 키우는 대신 이벤트/적당한 청크별로 나눠야 한다. BSON 문서 최대 크기는 16MiB다. 정규 컬렉션이라면 `(matchId, seq)` 고유 인덱스 등으로 재전송 중복을 통제하는 구조를 검토한다. [MongoDB 크기 제한](https://www.mongodb.com/docs/manual/reference/limits/), [공식 Node 드라이버](https://www.mongodb.com/docs/drivers/node/current/).

Azure Append Blob은 blob당 append 횟수가 제한되어 있고 중복·지연 append 방지를 애플리케이션에서도 다뤄야 한다. 한 턴마다 독립된 네트워크 요청을 보내는 구성을 기본으로 잡지 않는다. 완결 파일 업로드에는 `@azure/storage-blob`의 BlockBlobClient `uploadFile`/`uploadStream`을 사용할 수 있다. [Append Block](https://learn.microsoft.com/en-us/rest/api/storageservices/append-block), [BlockBlobClient](https://learn.microsoft.com/en-us/javascript/api/@azure/storage-blob/blockblobclient?view=azure-node-latest).

## 4. 저장 모듈 비교와 추천 구조

| 모듈                    | 역할                                                     | 판정                                                                                                                                   |
| ----------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Node `fs` / `stream`    | JSONL 파일 append, backpressure, 완료/오류 처리와 동기화 | 전량 경기 기록의 기본 writer로 추천                                                                                                    |
| Node `worker_threads`   | 인코딩·쓰기 작업을 메인 게임 루프와 분리                 | 한 프로세스/컨테이너 안에서 적용 가능. IPC 복사·CPU·디스크 자원 사용은 여전히 측정해야 함                                              |
| Node `zlib`             | 완결 JSONL의 스트리밍 gzip 압축                          | 경기 종료 후 압축/검증하여 보관. 원본 삭제는 검증·보관 정책 이후                                                                       |
| Pino / worker transport | JSON 구조의 일반 운영 로그와 worker 출력                 | 운영 로그에 적합. 경기 저널은 레벨 필터·샘플링/드롭·종료 flush·복구 계약을 별도로 통제해야 하므로 단순 logger 교체만으로 완성되지 않음 |
| `@azure/storage-blob`   | 완결 파일 업로드·읽기 또는 Append Blob adapter           | Azure 보관 단계에서 도입                                                                                                               |
| 공식 `mongodb` 드라이버 | 이벤트 문서 insert/bulkWrite·인덱스·조회                 | MongoDB 이벤트 저장 방식을 선택할 경우 사용                                                                                            |

Node stream의 `write()`가 false를 반환하면 drain을 기다리는 등 backpressure를 처리해야 한다. stream 쓰기 완료와 저장 장치 동기화는 구분하며 `filehandle.sync()`의 실제 보장은 OS·장치에 의존한다. [Node stream](https://nodejs.org/api/stream.html), [Node fs](https://nodejs.org/api/fs.html#filehandlesync).

Pino transport는 worker thread 실행을 지원하지만 logger/transport 레벨로 이벤트가 걸러질 수 있다. 전량 경기 기록을 일반 debug 로그 레벨에 종속시키지 않는다. [Pino transports](https://github.com/pinojs/pino/blob/main/docs/transports.md).

추천 모듈 경계는 다음과 같다. 이름/경로는 구현 전 제안이다.

```text
Match / GameState의 확정 이벤트
  → MatchEventRecorder        seq·turnId·DTO·이벤트 생성
  → MatchJournalWriter        크기 제한 큐·writer ack·flush/sync·실패 통지
  → writer worker
  → LocalJsonlMatchLogStore   경기/청크별 단일 작성자·완결·복구·스트리밍 읽기
      → 선택: AzureBlobArchiveStore

실행 기록 catalog            실행 영역에서 위치·상태·크기·해시·seq 관리
게임 운영 DB                 최종 결과/조회용 참조·기록 완결 상태만 반영
```

저장 계약에는 `open`, 순서 있는 `append`, `syncThrough(seq)`, `finalize`, `stream`, `recoverIncomplete`, 소유자별 조회/삭제와 만료 정리를 포함한다. enqueue된 seq와 내구성 확인을 받은 seq를 구분한다. EventEmitter의 async listener가 자동으로 await되거나 생산자까지 backpressure를 전달한다고 가정하지 않는다.

DB에는 경기별 로그 키·소유자·시작/종료 시각·레코드 수·마지막 내구 seq·바이트 수·해시·형식 버전·보관 만료·업로드 상태를 넣는다. 경기 결과(finished/aborted/failed), 기록 상태(recording/sealed/incomplete), 아카이브 상태를 분리한다. 중단/초기화 실패도 전부 기록되어 sealed일 수 있고, 정상 경기 결과라도 기록 오류가 있으면 incomplete다.

## 5. 전량 기록과 장애 내구성

다음 둘은 구분해 확정해야 한다.

1. **정상 종료까지 모든 턴을 남김:** 누락/샘플링 없는 큐, 순서·상한 통제, 종료 시 drain·sync·close 후 완결 확인. 이를 1차 기본 계약으로 제안한다.
2. **전원/호스트 장애에도 이미 확정한 모든 결과가 보존됨:** 각 결과의 내구 저장 확인을 엔진의 외부 확정/전달보다 먼저 수행하거나 durable journal에서 확정 상태를 복구할 수 있게 설계해야 한다. 디스크/네트워크 지연이 확정 지연에 반영되므로 별도 비용·지연 검증이 필요하다.

worker·비동기 버퍼만으로 2번까지 보장하지 않는다. 일정 주기 sync 방식은 마지막 sync 이후 손실 구간이 있을 수 있으며, 구현 전에 허용 범위를 정해야 한다. fsync도 저장 장치/호스트의 보장을 넘어선 절대 무손실 약속이 아니다.

큐는 레코드 수뿐 아니라 바이트 상한으로 관리한다. 큐 포화·디스크 부족·worker 오류에서 데이터를 버리고 경기를 정상 진행하는 fallback은 사용하지 않는다. 저장 복구를 기다리며 새 처리/경기 수락을 제한하거나 기록 실패로 경기를 종료하고 incomplete를 명시하는 정책을 구현 전에 선택한다. 이를 무제한 메모리 증가로 해결하지 않는다. 저장 장치가 실패한 상태에서 종료 이벤트까지 같은 파일에 반드시 쓸 수 있다고 가정하지 않는다.

정상 종료에서는 새 턴 요청 중단 → 진행 중 턴의 완료/취소 정리와 늦은 결과 분류 → 실행기 종료/대기 호출 정리 → 최종 이벤트 → 큐 drain/sync/close → 파일 완결·인덱스 갱신 순서를 맞춘다. stdout/컨테이너 로그 드라이버만으로 원본 저널을 대체하지 않는다.

작성 중 파일은 `.jsonl.partial` 등으로 구분하고 검증/동기화한 파일만 완결 처리한다. 재기동 시 마지막 줄의 잘림·UTF-8 경계·seq 누락·중복을 검사해 읽을 수 있는 구간과 incomplete 상태를 식별한다. 정상 종료로 위장하거나 손상된 원본을 무조건 덮어쓰지 않는다. 파일 완결과 DB 인덱스 갱신 사이의 장애도 복구/정합 점검 대상으로 둔다.

클라우드 업로드 재시도는 경기 진행과 분리하고 로컬 원본을 유지한다. 로컬 디스크의 보관 한도·업로드 실패 적체도 수락 제한에 연결한다. Azure 관리형 컨테이너의 임시 디스크를 사용한다면 컨테이너 삭제 이전 업로드만으로 활성 경기 내구성이 보장되지 않으므로 실제 영구 저장/원격 durable sink를 먼저 확정해야 한다.

## 6. 용량·비용의 1차 판단

현재 샘플의 초기 화면 snapshot JSON을 한 번 직렬화한 결과는 다음과 같다. 실제 부하/처리량 벤치마크가 아니라 debug 로그가 없는 초기 상태 크기 측정과 주기 환산이다.

| 샘플                  | 초기 snapshot 크기 | 현재 20ms 주기를 그대로 파일에 쓰면 |
| --------------------- | ------------------ | ----------------------------------- |
| crossroads 12×10      | 2,600바이트        | 약 7.80MB/분/경기                   |
| four-courtyards 20×16 | 3,158바이트        | 약 9.47MB/분/경기                   |

실제 snapshot은 debug 출력/상태에 따라 더 커질 수 있다. 프레임별 상태를 전부 저장하는 대신 초기 상태와 모든 이벤트·필요한 체크포인트를 보관하는 이유다. 이벤트 자체를 생략하는 의미는 아니다.

예를 들어 액션 400ms, 4명, 계산 시간 무시 조건이면 약 10턴/초다. 한 턴 관련 레코드 합계가 평균 1KB라면 10분에 약 6MB이며 맵 기믹·체크포인트·debug 출력은 별도다. 신발·짧은 액션·출력 증가·동시 경기 수에 따라 늘어난다. 압축률과 디스크 처리량은 실제 기록으로 측정해야 한다.

## 7. 구현 전 검증 기준

- 일반 성공·-1·timeout·exception·invalid-result·벽 충돌·파괴·점프/실패·효과 교체·획득/점수 경합을 기록하고 실제 엔진 상태와 대조한다.
- 완료 턴마다 terminal 이벤트 하나, 미완료 턴은 취소 하나를 확인한다. 마지막 코인으로 종료되는 순간의 다른 플레이어 액션·계산 중 응답도 누락/중복 없이 처리한다.
- 기믹·아이템·Hurry Up과 랜덤 결과를 initial state+이벤트로 적용한 상태가 엔진과 일치하는지 검증한다. 알고리즘 재실행으로 검증을 대신하지 않는다.
- 긴 경기·동시 경기에서 이벤트 크기·큐 bytes·writer 지연·durable seq 차이·디스크 사용·게임 루프 지연과 알고리즘 시간 제한을 측정한다.
- 느린 디스크·disk full·쓰기 오류·worker 종료·정상/강제 종료·부분 줄·중복 업로드와 파일/인덱스 불일치를 주입해 누락을 숨기지 않는지 확인한다.
- 조회는 한 줄/청크씩 스트리밍하고 전체 경기를 메모리에 모두 읽지 않는다. 계정/게스트 소유권을 검사하고 물리 경로나 공개 blob URL로 우회 조회하지 못하게 한다.
- 보관 기간·압축/원격 이전·사용자별 삭제·DB/코드/맵과 로그의 백업·복구 기준을 정한다. 진단/로그에는 원문 자동 영구 보관이나 다른 사용자 공개를 추가하지 않는다.

## 8. 추천 결론과 아직 열린 결정

**경기별 전량 원본은 JSONL, 메타데이터/검색 목록은 DB, 장기 보관은 필요 시 Blob Storage**를 추천한다. DB가 SQLite/MongoDB/PostgreSQL 중 무엇이든 이 구성이 가능하다. 턴 데이터의 온라인 조건 검색이 주요 기능으로 확정되면 MongoDB/관계형 이벤트 저장 또는 JSONL에서 만드는 검색 인덱스를 비교한다. JSONL 보관 요구가 곧 MongoDB 필수 도입을 뜻하지 않는다.

저장 모듈은 Node 기본 기능을 사용하는 전용 MatchLogStore/worker writer를 우선하고 Pino는 일반 운영 로그 용도로 검토한다. 기존 FileSourceStore의 `.js` 파일 쓰기 코드를 전량 로그 append·완결·복구 계약으로 그대로 재사용하지 않는다.

구현 전에는 장애 시 내구성 범위, 저장 지연/실패 시 경기 처리, full-input 필요성, 게스트·테스트 로그 조회/보관 정책과 실제 배포 저장소를 확정해야 한다. 개인정보 운영 준비를 마지막에 수행하더라도 소유권·열거/삭제·보관 정책 연결 지점은 새 로그 저장 계약에 처음부터 포함한다.
