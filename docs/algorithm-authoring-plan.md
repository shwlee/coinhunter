# 알고리즘 작성 페이지 작업 계획

- 작성일: 2026-09-29
- 상태: 구현 전 계획. 기술 후보와 미정 운영 조건은 확정 요구사항과 구분한다.
- 기준: [전체 기획](implementation-plan.md), [아키텍처](architecture.md), [알고리즘 API](algorithm-api.md), [이전 알고리즘 대결](algorithm-duel.md), [결과 분석](result-analysis.md).
- 이번 작업은 작성 페이지와 이에 필요한 계정·코드 저장·AI 연결을 대상으로 한다. 전체 관리자 화면보다 작성 페이지를 먼저 구현한다.

## 1. 목표와 완료 범위

로그인 사용자가 자연어로 전략을 설명하고 AI가 만든 코드를 테스트한 뒤 본인 계정에 저장하는 흐름을 제공한다. 직접 코드를 작성하거나 로컬 파일을 가져오는 방법도 지원한다. 저장한 코드는 다른 사내 PC에서도 같은 계정으로 열 수 있고, 게임 플레이 및 이전 알고리즘 대결에서 선택할 수 있어야 한다.

게스트는 기존 파일 업로드 플레이만 이용한다. 작성 페이지, AI 생성, 계정 저장 API는 로그인 사용자 전용이다. 현재 게스트 식별 쿠키를 사용자 계정으로 간주하지 않는다.

이번 범위에서 제외하는 기능:

- 코드 변경 이력, 과거 버전 자동 보관·복원, 자동 저장.
- 브레이크포인트, 단계 실행, 변수 조사 도구.
- 다른 사용자 코드 열람, 공동 편집, 공유 더미, 대회.
- 여러 언어 지원, 자동 반복 대결, AI의 무인 생성·실행 반복.

AI 실제 연결까지 완료해야 전체 작성 기능을 완료 처리한다. 화면이나 개발용 대체 응답만 제공한 상태는 중간 단계다.

## 2. 현재 구현과 재사용 경계

| 현재 구성 | 활용 및 필요한 변경 |
| --- | --- |
| `public/app.js`의 플레이 화면 | 경기 연결·캔버스 렌더링·결과 표시를 페이지 생명주기와 분리하여 재사용 |
| `src/server.js`, `Match`, `GameState` | 기존 경기 생성·SSE·중단·종료 경로 사용. 작성 전용 게임 엔진을 추가하지 않음 |
| `src/runtime/policy.js`, 실행 프로세스 | 직접 작성·AI 생성·파일 가져오기 모두 같은 검증과 실행 제한 적용 |
| 결과 분석·순위·포디엄 모듈 | 테스트 경기에서도 사용 |
| 이전 알고리즘 대결 | 편집 중 코드와 본인의 저장 코드 또는 로컬 파일을 1:1 비교 |
| 게스트 쿠키와 경기 소유권 | 계정 세션과 구분하고 로그인 경기 소유권 검사로 확장 |
| 맵 파일 저장소 | 공개 맵 목록만 재사용. 사용자 코드 저장소는 별도 구현 |

현재 계정, 알고리즘 영구 저장, 작성 화면, 실제 AI 연결은 구현되어 있지 않다. 정적 파일 허용 목록과 CSP도 새 페이지·편집기 자원에 맞게 조정해야 한다.

## 3. 화면 구성과 사용자 흐름

별도 `/editor` 페이지를 제공하고 헤더에서 게임 플레이와 이동한다. 게임판 위에 편집기를 겹쳐 놓지 않는다.

### 기본 화면

1. 상단: 알고리즘 이름, 저장 여부, 새로 만들기, 열기, 저장, 새 이름으로 저장, 파일 내보내기.
2. 작성 영역: **AI로 작성 / 코드 편집** 탭. 기본은 AI로 작성이다.
3. AI 탭: 전략 입력, 생성·수정 버튼, 진행·취소·실패 상태, 생성 결과 설명 및 적용 버튼.
4. 코드 탭: JavaScript 구문 강조, 줄 번호, 들여쓰기, 검색, undo/redo, 오류 위치 표시. 게임 API 안내와 예제는 접을 수 있는 도움말로 제공한다.
5. 테스트 영역: 테스트 설정 → 플레이 → 결과 분석 전환. 코드 편집 영역의 크기를 경기 상태에 따라 바꾸지 않는다.
6. 디버그 영역: 출력/실행 오류, 플레이어·턴, 지우기, 자동 스크롤 켜기/끄기, 잘린 출력 안내.

넓은 화면에서는 작성 영역과 테스트 영역을 나란히 배치한다. 좁은 화면에서는 작성/테스트 탭으로 전환하여 게임판을 과도하게 축소하지 않는다. 편집기와 디버그 창의 내부 스크롤은 허용하되, 경기 상태 전환 때문에 페이지 전체 높이가 요동하지 않도록 한다.

### 핵심 흐름

`로그인 → 새 코드/본인 코드/파일 열기 → AI 작성 또는 직접 수정 → 테스트 → 결과·출력 확인 → 수정 → 저장`

- 새 코드는 유효한 기본 템플릿으로 시작한다.
- 열기 창은 본인 저장 목록과 로컬 파일 가져오기를 구분한다.
- 저장하지 않은 코드도 테스트할 수 있다.
- 테스트 선택지는 혼자, 기존 더미, 이전 알고리즘과 대결이다. 더미 전략 다양화는 이번 범위가 아니다.
- 이전 알고리즘은 저장 목록 또는 파일에서 명시적으로 선택한다. 자동 버전 히스토리를 만들지 않는다.
- 현재 저장본을 이전 알고리즘으로 선택하면 편집 중 변경과 마지막 저장본을 비교할 수 있다. 기준 코드를 유지하려면 새 이름으로 저장하도록 안내한다.
- 게임 플레이 화면에도 로그인 사용자용 저장 알고리즘 선택을 추가한다. 게스트의 기존 흐름은 유지한다.

## 4. 편집·저장 상태와 데이터

편집 상태는 `algorithmId`, 이름, 편집 코드, 마지막 저장 내용, 저장 충돌 확인값, 변경 여부를 갖는다. AI 요청 상태 및 테스트 경기 상태는 별도로 관리한다.

| 동작 | 처리 |
| --- | --- |
| 저장 | 기존 항목 갱신. 새 문서는 이름을 입력하고 새 항목 생성 |
| 새 이름으로 저장 | 새 ID로 별도 항목 생성. 기존 항목 유지 |
| 로컬 파일 가져오기 | 새 미저장 문서로 열기. 기존 계정 코드를 자동 덮어쓰지 않음 |
| 내보내기 | 현재 편집 내용을 `.js` 파일로 내려받기 |
| 다른 문서 열기·새 문서·페이지 이동 | 변경이 있으면 저장/버리기/취소 제공. 브라우저 종료는 기본 이탈 경고 사용 |
| 저장 중 추가 편집 | 저장 요청에 포함한 내용만 저장 완료 처리. 이후 편집은 미저장 상태 유지 |
| 다른 PC에서 먼저 저장 | 충돌로 알리고 현재 편집 내용을 보존. 다시 불러오기 또는 새 이름 저장 제공 |
| 로그아웃·세션 만료 | 계정 데이터 접근 차단. 자동 저장하지 않고 현재 편집 내용을 보존한 채 재로그인 안내 |

알고리즘 데이터: `id`, `ownerId`, `name`, `language: javascript`, `source`, `createdAt`, `updatedAt`, `revision`.

`revision`은 동시 저장 충돌 방지를 위한 숫자이며 과거 소스를 보관하지 않는다. 소유자는 서버 인증 정보에서 결정한다. 파일 경로나 요청의 사용자 ID를 신뢰하지 않는다. 코드 크기는 기존과 동일하게 64 KiB다. 구문 오류가 있는 작업 중 코드도 저장할 수 있게 하되, 검증 상태를 표시하고 실행 전에는 반드시 공통 검증을 통과시킨다.

저장소는 계정·알고리즘의 영구 저장, 소유권 조회, 원자적 갱신, 백업을 지원해야 한다. DB 제품·드라이버는 현재 Node 버전과 배포 OS를 확인한 뒤 선정한다. 브라우저 저장소를 계정 저장소로 사용하지 않는다.

## 5. 계정 기반과 API 계획

기존 기획에 따라 인증이 선행되어야 한다. 사내 인증 연동 여부와 계정 발급 방식을 먼저 결정한다. 자체 계정 방식을 택한다면 초기에는 관리자 발급 방식으로 범위를 제한하는 것을 제안한다. 임의 고정 사용자나 게스트를 로그인 사용자로 취급하는 우회는 운영 기능에 넣지 않는다.

다음은 구현할 API 계약의 초안이다.

| API | 책임 |
| --- | --- |
| `GET /api/session` | 로그인 여부·사용자 정보. 인증 방식에 따른 로그인/로그아웃 경로는 별도 확정 |
| `GET /api/algorithms` | 본인 알고리즘의 이름·수정 시각 등 목록 |
| `POST /api/algorithms` | 새 저장 및 새 이름 저장 |
| `GET /api/algorithms/:id` | 본인 코드 열기 |
| `PUT /api/algorithms/:id` | revision을 확인하여 갱신. 충돌 시 409 |
| `POST /api/algorithms/validate` | 크기·구문·금지 구문 검사. 사용자 코드를 실행하지 않음 |
| `POST /api/ai/requests` | 로그인 사용자의 생성·수정 요청 |
| `GET /api/ai/requests/:id/events` | 진행 상태와 완료·실패·취소 결과 |
| `DELETE /api/ai/requests/:id` | 취소 요청 및 지연 응답 적용 방지 |
| 기존 경기 API 확장 | 참가자별 업로드 소스 또는 본인 저장 알고리즘 ID 선택 |

서버는 미인증 작성 API를 거절하고, 타인 데이터는 조회·수정·경기 실행 모두 차단한다. 세션 만료, 로그아웃, 변경 요청의 출처 검사, 로그인 시도 제한도 인증 범위에 포함한다. 현재 같은 게스트 세션에 적용하는 동시 경기 제한은 로그인 시 계정 단위로 적용하도록 정리한다.

## 6. 테스트 플레이·디버깅 통합

- 테스트 시작 시 편집 코드와 선택한 상대 코드·맵·옵션을 복사하여 고정한다. 이후 편집·저장은 진행 중 경기에 영향을 주지 않는다.
- 저장된 상대를 선택하면 서버가 소유권 확인 후 코드를 읽어 경기 사본을 만든다. 프런트에서 전달한 소유권 주장은 사용하지 않는다.
- 초기화, 메서드 형태, 실제 실행 오류는 기존 제한된 실행 환경에서 확인한다. 정적 검사 통과가 정상 실행을 보장한다고 표시하지 않는다.
- 각 호출 500ms, 시간 초과 후 인스턴스 유지, 현재 턴 패널티, 랜덤점프 중 호출 생략 등 기존 규칙을 유지한다.
- `debug.print`와 오류 출력을 참가자·턴별로 구분한다. 기존 서버 출력 제한을 유지하고 클라이언트 로그도 상한을 둔다. HTML로 렌더링하지 않는다.
- 편집 후에는 오류가 발생한 실행 코드와 현재 코드가 다를 수 있으므로 실행 시점 정보와 함께 표시한다. 다른 코드의 줄에 오류를 표시하지 않는다.
- 코드 변경 후 재테스트는 기존 경기 중단·정리 완료 후 새 경기로 시작한다. 일반 편집 때문에 실행 프로세스를 재시작하지 않는다.
- 페이지를 떠날 때 진행 중 테스트의 중단/이동 취소를 선택하게 한다. 연결 끊김은 기존 재연결 정책을 유지한다.
- 테스트 결과는 기존 분석 항목을 재사용한다. 결과에서 작성 영역으로 복귀할 때 코드·커서·선택한 설정을 보존한다.

## 7. AI 작성 설계

자연어 전략 입력을 중심에 두되, AI 응답이 도착했다고 기존 코드를 즉시 덮어쓰거나 자동 실행하지 않는다.

1. 요청 시 현재 코드, 요청문, 게임 규칙·API·제한 사항·예제를 묶는다.
2. 최초 생성 또는 수정 요청을 AI 연결 어댑터에 전달한다.
3. 응답에서 코드와 설명을 분리하고 코드 크기·구문·금지 기능을 검사한다.
4. 생성 결과를 임시 후보로 표시한다. 사용자가 적용하면 편집기의 한 번의 변경으로 반영하여 undo로 취소할 수 있게 한다.
5. AI 응답 대기 중 직접 코드를 변경했다면 요청 시점과 달라졌음을 표시하고 덮어쓰기 여부를 명시적으로 선택하게 한다.
6. 실패·취소·잘못된 응답에서는 기존 코드를 보존한다. 취소한 요청의 늦은 응답을 적용하지 않는다.
7. 테스트 후 사용자가 필요한 출력·오류를 선택하여 수정 요청에 포함할 수 있게 한다. 전체 디버그 로그를 무조건 외부로 보내지 않는다.

AI와 도움말이 같은 규약 자료를 참조하도록 `algorithm-api.md`, `game-rules.md`, 기존 작성 주의사항과 런타임 정책을 대조하여 공통 지침을 구성한다. 규약 변경 시 AI 입력·도움말·검증 테스트를 함께 갱신한다.

네트워크는 `게임 서버 → 접근 허용된 중계 서비스 → AI 제공자`를 우선 검토하되 실제 연결 가능 여부를 검증하기 전 확정하지 않는다. 게임 호스트는 외부망에 직접 접근할 수 없으며, 브라우저에 제공자 비밀키를 넣는 방식은 사용하지 않는다.

제공자·모델, 중계 위치, VPN/방화벽 경로, 인증과 키 보관, 코드 전송·보관 정책, 요청 길이·시간·동시 요청·사용량 한도를 실제 연결 전에 결정한다. 중계 경로가 정해지기 전에도 화면과 어댑터 계약은 개발할 수 있지만 실제 AI 완료 검증은 대체할 수 없다.

| 순서 | 구체 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 계약 정리 | 인증·저장 방안 결정, 작성 상태·API 계약 고정, AI 중계 조건 조사 착수, 편집기 후보 검토 | 게스트 권한과 저장·실행·AI 요청 경계가 문서화됨 |
| 2. 공통 플레이 모듈 추출 | `app.js`의 경기 연결, 렌더링, 결과 표시를 분리. 기존 페이지는 같은 모듈 호출 | 기존 플레이·대결·결과 분석 브라우저 회귀 검사 통과 |
| 3. 계정·저장 기반 | 인증, 세션, DB 마이그레이션, 계정별 저장·조회·갱신, 충돌 처리 | 서버 재시작 및 다른 브라우저 로그인 후 코드 유지, 타인 접근 차단 |
| 4. 작성 화면 | 페이지 경로·탭·편집기, 템플릿, 파일/저장 코드 열기, 저장·새 이름 저장·내보내기, 미저장 표시 | 로그인 사용자의 직접 작성→저장→다시 열기 동작, 게스트 접근 차단 |
| 5. 테스트 통합 | 편집 사본 실행, 테스트 설정, 디버그 출력, 결과 분석, 이전 저장 코드 대결 | 실행 중 편집이 경기에 영향을 주지 않고 코드 상태를 보존한 채 반복 테스트 가능 |
| 6. 플레이 화면 연결 | 로그인 사용자의 저장 알고리즘을 본인·이전 코드 참가자로 선택 | 저장→플레이→대결 연결 및 게스트 파일 업로드 회귀 검사 통과 |
| 7. AI 통합 | 공통 지침, 제공자 어댑터·중계 인증, 생성/수정/취소/검증/적용 UI | 실제 AI 생성→테스트→수정→저장 성공, 실패 시 기존 코드 유지 |
| 8. 통합 검증·문서 | 전체 흐름·반응형·권한·자원 정리 검사, 백업/복구와 설정 문서 갱신 | 아래 필수 검증 통과 및 실제 연결 범위·남은 배포 조건 기록 |

화면 골격은 인증 작업 중 개발용으로 준비할 수 있지만, 공개된 게스트 작성 기능으로 배포하지 않는다. AI 경로 조사는 1단계부터 병행한다. 각 단계는 독립적으로 검토 가능한 변경 단위로 구성한다.

편집기 라이브러리는 현재 프레임워크 없는 페이지와의 통합, undo 트랜잭션, 로컬 정적 자원 배포, CSP, 한국어 입력, 작은 화면에서의 사용성을 확인한 뒤 선정한다. 작성 화면을 위해 전체 게임을 다른 UI 프레임워크로 재작성하지 않는다.

## 9. 필수 검증

- 계정 A의 코드 ID를 계정 B와 게스트가 열기·변경·실행할 수 없다.
- 다른 PC에서 본인 저장 코드를 다시 열 수 있고, 동시 저장 충돌에서 작업 내용이 소실되지 않는다.
- 가져온 코드·AI 응답·알고리즘 이름·출력의 문자열이 화면에서 실행되지 않는다.
- 저장 실패, 세션 만료, AI 실패·취소·지연 응답이 편집 내용을 지우지 않는다.
- AI 적용 undo/redo, 저장 중 편집, 미저장 상태에서 열기·이동을 검증한다.
- 편집 중 코드와 실행 코드가 분리되고, 이전 알고리즘 대결은 선택 당시 코드로 완료된다.
- 무한 루프·예외·출력 과다 시 기존 런타임 제한과 다음 턴 복구를 유지한다.
- 테스트 중단·초기화 실패·페이지 이동 후 프로세스와 이벤트 구독이 정리된다.
- 게스트 플레이, 기존 대결·캐릭터·맵·아이템·결과 분석 기능이 유지된다.
- 데스크톱과 작은 화면에서 작성/테스트 전환, 한국어 입력, 파일 선택, 저장·실행 버튼 접근을 확인한다.

## 10. 구현 전 결정 사항과 착수 가능 범위

| 결정 | 필요 시점 |
| --- | --- |
| 사내 인증 연동 또는 자체 계정, 계정 발급·복구 방식 | 실제 인증 구현 전 |
| 저장 DB·드라이버·데이터 경로·백업 위치 | 계정·저장 구현 전 |
| 편집기 라이브러리 및 자원 빌드 방식 | 코드 편집 UI 구현 전 |
| AI 제공자·모델·중계 위치·접속 권한·데이터 정책 | 실제 AI 연결 전 |

지금은 공통 플레이 모듈 분리, 화면 골격, 작성 상태·API 계약 정리부터 착수할 수 있다. 인증과 AI의 실제 환경 정보가 필요한 시점에는 해당 항목을 확정한다. 이 문서 작성은 구현 또는 배포 완료를 의미하지 않는다.
