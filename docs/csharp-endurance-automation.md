# C# 장시간 동시 실행·장애 검증 자동화

기존 [GC 진입 복구](csharp-gc-entry-recovery-2026-11-20.md)를 실제 게임의 장시간 실행과 수명 관리에 적용해 검증한다. 일반 `npm test`/BE 회귀에 30분 시험을 자동으로 넣지 않는다. 이 도구는 공개 C# 지원이나 서비스의 자원 기본값을 활성화하지 않는다.

## 실행

```powershell
# 짧은 도구·장애 경로 검사. 장시간 검증 통과로 인정하지 않는다.
node scripts/csharp-endurance.js --smoke

# 기본: 게임 2개, 30분 동시 실행, 시작/종료 3회
node scripts/csharp-endurance.js

# 선택 가능한 범위: 30~55분, 게임 1~4개, 시작/종료 1~20회
node scripts/csharp-endurance.js --minutes 30 --games 2 --cycles 3
```

Node와 .NET SDK가 필요하다. 별도 `artifacts/csharp-endurance-build`로 빌드하고 매 실행마다 새로운 `artifacts/csharp-endurance-<UUID>`를 만든다. `.env`와 실제 계정/맵/코드/서버 데이터를 읽거나 수정하지 않는다. FE 웹서버나 Google/OAuth 연결도 시작하지 않는다. 실제 Node 게임 엔진과 C#·JS 알고리즘 프로세스를 실행하는 서버 측 검증이다.

## 수행 순서

1. C# 계산이 진행 중인 게임을 시작하고 중지한다. 지정 횟수만큼 새 게임으로 반복한다.
2. 소유한 게임 엔진 프로세스 하나를 강제 종료한다. 게임 실패·부분 JSONL 복구·전체 자원 회수를 확인한다.
3. 소유한 C# 실행기 하나를 계산 도중 강제 종료한다. 사용자 패널티로 위장하지 않고 실패를 완결 로그에 남기는지 확인한다.
4. 장애 후 새 게임이 새로운 인스턴스로 정상 실행되는지 확인한다.
5. 준비가 끝난 게임들을 함께 실행한다. 모든 참여자의 진행을 확인한 뒤 30분 이상 실시간으로 측정한다.
6. 종료 후 전체 JSONL을 스트리밍으로 검사하고 최종 결과/receipt·프로세스 종료·예약 반환을 대조한다.

강제 종료 대상은 검증이 생성한 프로세스뿐이다. PID와 시작 시각을 보관하고 동일 프로세스인지 확인한 뒤 열린 핸들로 종료한다. 자동 재시작으로 같은 게임의 실패를 숨기지 않는다. 장애 후 실행은 별도의 새 게임이다.

## 부하 조건과 검사

- 최대 맵 40×30. 게임마다 C# 2명과 JavaScript 1명이다.
- C#마다 128MiB 상태를 유지하고 정상 턴마다 64KiB 배열을 새로 할당한다. 반복 timeout과 잘못된 방향 반환을 넣어 인스턴스/필드 상태가 계속 유지되는지 확인한다.
- 액션 시간은 50ms다. 계산 완료 즉시 액션을 시작하는 기존 동작을 유지한다. 검증 도구의 샘플 간격은 게임 실행을 기다리게 하지 않는다.
- 5초마다 엔진·C# 실행기의 PID/시작 시각/메모리/CPU와 부모 OS 그룹, 진행 턴, 전역 예약을 기록한다. 20초 동안 한 참여자가 진행하지 않거나 예상 외 실행기/예약 증가가 있으면 실패한다.
- 게임당 예약 2,304MiB, C# 호스트당 768MiB, 엔진/JS 그룹 512MiB를 시험에서만 사용한다. 전체 시험 예산은 `게임 수 × 2,304 + 1,536MiB`다. 배포 권장 사양이 아니다.
- 로그 합계 기본 상한은 4GiB, 디스크 여유 기준은 1GiB다. 초과하면 실패 처리하고 종료/회수를 수행한다. 로그를 자동 삭제하지 않는다.

JSONL 검사는 전체 이벤트를 메모리에 보관하지 않는다. 한 줄 길이를 제한하고 UTF-8/스키마/연속 seq, 경기·플레이어·실행·호출·인스턴스 식별자, 필드 카운터의 진행, timeout/방향 판정, GC 구간/진입 관측을 대조한다. 정상 종료의 결과와 GC 관측 개수가 같아야 하며 최종 receipt도 일치해야 한다. 엔진 강제 종료의 부분 로그는 유효한 연속 prefix와 실제 보존 seq를 비교한다.

## 출력과 판정

| 파일                   | 의미                                          |
| ---------------------- | --------------------------------------------- |
| `options.json`         | 이번 실행의 시험 옵션                         |
| `progress.json`        | 현재 단계·경과 시간·검사 수·실행기 수         |
| `samples.jsonl`        | 시간별 프로세스/게임/예약 관측                |
| `report.json`          | 단계별 결과·전체 로그 집계·최종 자원 상태     |
| `supervisor.json`      | 감시 프로세스의 종료 코드·중단/강제 종료 여부 |
| `execution/journals/*` | 실제 전체 경기 로그와 최종 receipt            |

`passed`는 선택한 검증 모드의 성공이다. `qualifiedLongRun`은 smoke가 아니고 실제 동시 실행 시간이 1,800초 이상이며 모든 단계/최종 회수가 성공했을 때만 true다. smoke 통과나 중단된 시험으로 장시간 통과를 표시하지 않는다.

종료 코드 0은 해당 모드 통과, 1은 검증/감시 실패, 2는 운영자 중단이다. 별도 감시가 제한 시간을 넘기면 정상 중단을 요청하고, 45초 동안 종료하지 못하면 자식을 강제 종료한다. 강제 종료는 자원 회수 확인으로 취급하지 않고 실패로 남긴다. Linux의 강제 종료 이후 외부 감독/cgroup 회수는 별도 채택 관문이다.

## 진행 확인·중단

도구가 출력한 실행 폴더의 `progress.json`을 확인한다. 터미널에서 Ctrl+C 또는 표준 입력에 `stop`을 보내 정상 중단을 요청할 수 있다. CI나 입력이 닫힌 환경에서는 다음 파일을 만든다.

```powershell
Set-Content -LiteralPath 'artifacts/csharp-endurance-<실행ID>/stop.request' -Value stop
```

중단된 시험은 실패/중단 결과로 남고 장시간 통과로 인정하지 않는다. 해당 실행 폴더는 그대로 보관한다.

실제 결과는 [장시간 검증 기록](csharp-endurance-2026-11-20.md)에 별도로 정리한다. 분 단위/30분 로컬 시험은 운영 환경 전체 용량, 정확한 500ms 선점, Linux 파일·네트워크 격리의 증명이 아니다.
