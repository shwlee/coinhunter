# 프롬프트 중심 작성 전환과 개선 아이디어

- 작성일: 2026-11-14
- 제품 방향: 직접 API 연결보다 사용자가 외부 AI에 전달할 프롬프트 생성을 중심으로 알고리즘 작성을 지원한다.
- 상태: 아이디어 검토 기록. 이후 사용자 요청으로 직접 AI 연결 제거를 완료했으며 구현 상태·구체 순서는 [후속 계획](prompt-authoring-improvement-plan.md)을 따른다. 아래 제거 전 관찰과 제안은 당시 기록이다.
- 관련: [기존 프롬프트 구현](prompt-assistant-plan.md), [검증 기록](prompt-assistant-verification.md), [기존 직접 연결 계획](ai-scripting-plan.md).

## 1. 유지할 기반

명시적 프롬프트 생성, 항상 표시되는 미리보기, 생성 본문 복사, 입력 변경 후 재생성 안내, 최대 3개 전략과 순서, 선택적 현재 코드 포함, 코드 가져오기·실행 검사·명시적 적용·undo, 테스트 플레이·저장을 유지한다. 프롬프트 자동 갱신·코드 자동 적용·자동 저장은 도입하지 않는다.

게임의 규약·실행 제한은 공통 원본과 일치시킨다. 현재 원문은 파일로 보관하고 프롬프트 이력·외부 대화 수집·새 DB 저장은 기본 범위에 추가하지 않는다. 외부 AI 이용은 사용자가 선택한 서비스의 조건에 따르며 게임에서 API 키를 요구하지 않는 경로를 제공한다.

## 2. 현재 코드에서 확인한 개선 지점

- 사이드바에 프롬프트/AI 연결 탭, 공통 전략, 템플릿 코드 생성, API 후보 영역이 공존한다. 기본 작성 경로를 하나로 읽기 어렵다.
- 템플릿 코드 생성은 자유 입력 요청을 반영하지 않는다. 프롬프트 작성과 다른 결과를 내는 별도 경로여서 혼동 가능성이 있다.
- 요청의 신규 작성/수정 여부가 현재 코드 포함 체크로 결정된다. 사용자가 하려는 작업을 먼저 선택하는 구조를 검토할 수 있다.
- 검사 오류는 표시하지만 실패한 코드·진단을 수정 프롬프트로 연결하는 액션은 없다.
- 경기 결과 분석 지표는 있으나 결과를 선택해 개선 프롬프트로 연결하지 않는다.
- 복사용 입력에는 API 문서·게임 규칙 전체와 기준 예제를 넣는다. 근처 코인 전략 하나만 고른 신규 요청은 현재 6,797자이며 수정 코드가 포함되면 더 길어진다. 이 수치는 로컬 생성 측정치로 토큰 수·비용·품질 저하를 뜻하지 않는다.

## 3. 우선 추가할 아이디어

| 우선순위 | 아이디어                                             | 기대하는 사용자 경험                                           |
| -------- | ---------------------------------------------------- | -------------------------------------------------------------- |
| 1        | 신규 작성·전략 개선·오류 수정의 작업 목적 구분       | 코드 포함 체크의 의미를 추측하지 않고 요청 목적을 선택         |
| 1        | 검사 실패에서 수정 프롬프트 생성                     | 실패한 코드와 진단으로 재질문하고 반환 코드를 다시 검사        |
| 1        | 프롬프트 복사→외부 AI→코드 가져오기→검사→테스트 안내 | 다음 액션과 현재 진행 상태를 짧게 표시                         |
| 2        | 결과 분석에서 개선 프롬프트 생성                     | 본인 점수·호출/패널티·아이템 사용 등 선택한 근거로 개선 요청   |
| 2        | 작성용 규약의 정리                                   | 필수 규칙은 보존하면서 반복 설명과 작성에 불필요한 내용을 축약 |
| 2        | 전략 요약과 빠른 시작 조합                           | 순서와 추가 요청을 사람이 이해할 수 있게 확인하고 시작         |
| 3        | 짧은 프롬프트 파일 내보내기·재사용 가능한 요청 설정  | 실제 반복 사용 수요를 확인한 뒤 추가 여부 결정                 |

오류 수정은 현재 편집 코드와 과거 실패 코드를 섞지 않아야 한다. 진단에 코드 스냅샷·문서 버전을 연결하고 변경 시 오래된 진단임을 표시한다. 검사 통과와 모든 맵에서의 성공을 구분한다.

결과 개선은 사용자 본인 지표와 선택한 로그를 중심으로 구성한다. 망치 사용 0회만으로 코드가 잘못됐다고 단정하지 않는다. 데이터로 관찰한 사실과 사용자의 개선 목표를 구분하고, 다른 사람 코드나 계정·키 정보를 포함하지 않는다. 맵·옵션·시작 위치·난수 조건이 다른 결과를 단순 승패로 평가하지 않는다.

## 4. 덜어낼 UI와 범위 제안

- 기본 작성 화면의 AI 연결 탭, 연결/모델 선택, 키 발급·결제 안내, API 진행 표시를 제외하는 것을 제안한다. 기존 직접 연결 코드의 삭제 여부는 별도로 정하며 저장된 키·연결 정보를 임의 삭제하지 않는다.
- Claude·Gemini 직접 생성 어댑터는 현재 서비스 완성을 위한 필수 남은 작업에서 제외한다. 향후 직접 연결을 다시 제공할 때 검토한다.
- 템플릿 코드 생성은 일반 작성 경로에서 제외하고 필요하면 명확한 샘플 코드 기능으로 옮긴다. 자유 입력까지 반영하는 생성 기능처럼 표시하지 않는다.
- API 후보 코드와 외부 응답 가져오기의 중복 UI를 통합 후보로 검토한다. 검사 후 명시적 적용·기존 코드 보존은 유지한다.
- 수동 복사 실패에 필요한 전체 선택 기능은 유지하되 주 액션과 같은 비중으로 노출할 필요는 없다. 미리보기는 기존 사용자 요청대로 숨기지 않는다.

UI를 숨기는 것과 서버 기능을 비활성화하는 것은 구분한다. 전환 구현 시 서버 정책·기존 요청 수명·저장 자격 증명 관리도 함께 정한다. CSS로 숨긴 것만으로 외부 호출이나 비밀 보관 책임이 사라졌다고 처리하지 않는다.

## 5. 전략 구성에 대한 검토 아이디어

주요 목표는 최대 3개와 우선순위를 유지한다. 아이템 회피는 목표와 성격이 다르므로 별도 준수 규칙으로 분리하는 방안을 검토한다. 이는 현재 선택 개수·가중치 의미를 바꾸는 제안이며 확정 구현이 아니다. 숫자 가중치 편집 UI를 다시 도입하지 않는다.

빠른 시작은 기존 전략의 조합을 선택해 주는 방식으로 시작할 수 있다. 무작정 템플릿 수를 늘리지 않는다. 알고리즘에 전달되지 않는 상대 위치·보유 아이템 상태 등을 AI가 읽을 수 있다고 가정하는 전략은 제공하지 않는다.

## 6. 프롬프트 개선 원칙

신규 작성에는 최소 유효 골격, 수정에는 현재 코드를 중심으로 구성하는 방안을 비교한다. 완성 예제를 모든 요청에 넣어야 하는지 실제 결과로 평가한다. 예제 축약으로 필수 함수·방향·타일·아이템·시간·금지 API 규칙을 누락하지 않는다.

출력은 기존처럼 완성된 단일 JavaScript 파일을 코드 블록 하나로 받는 방식을 유지한다. 외부 AI 응답 전체를 복잡하게 파싱하거나 작은 변경을 위해 diff 적용기를 만드는 일은 우선순위를 낮춘다. 원문이 크면 길이를 안내하되 사용자의 코드를 조용히 자르지 않는다.

첫 요청은 독립적으로 사용할 수 있는 규약을 포함한다. 이후 사용자 요청으로 같은 외부 대화의 후속 요청에서 전체 규약·예제를 생략하는 방식을 [분량 축소 계획](prompt-context-reduction-plan.md)에 구체화했다. 대화 모드는 사용자가 선택하며 단순 생성 횟수로 자동 전환하지 않는다. 제공자·모델 선택이나 AI 사이트 자동 조작은 요구하지 않는다.

## 7. 구현 전 평가 기준

신규 작성·현재 전략 수정·문법 오류 수정·시간 초과 개선 사례를 같은 입력 기준으로 비교한다. 실행 검사 통과, 요청한 전략의 반영, 복사부터 테스트까지의 사용자 행동 수, 오류 후 재시도 성공을 평가한다. 외부 AI의 출력은 매번 같다고 가정하지 않으며 대체 응답 테스트를 실제 AI 품질 검증으로 표시하지 않는다.

권장 검토 순서는 기본 작성 경로 정리 → 오류 수정 프롬프트 → 작성용 규약 정리 → 결과 개선 프롬프트다. 현재는 아이디어 수집 단계이며 구체적인 구현 범위와 UI는 다음 작업 계획에서 정한다. FE·BE 분리·다국어 지원의 기존 구현 보류 결정은 유지한다.
