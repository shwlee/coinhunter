# 프롬프트 중심 알고리즘 작성 — 후속 작업 계획

- 작성일: 2026-11-14
- 기준: 직접 AI 연결 UI·브라우저 모듈·서버 서비스 연결을 제거한 상태.
- 상태: 0단계 완료. 1단계 중 신규/수정 목적 분리와 불필요한 생성/가져오기 UI 제거를 완료했다. 나머지 단계는 아래 후속 범위를 따른다.
- 관련: [사용법](local-authoring.md), [개선 아이디어](prompt-first-improvement-ideas.md), [기존 프롬프트 구현](prompt-assistant-plan.md).

2026-11-14 계획 보완: [프롬프트 분량 축소 하위 계획](prompt-context-reduction-plan.md)의 1~3단계를 구현했다. 작성용 규약·내용 버전·두 모드 생성과 선택 UI·문서 수명을 연결했다. 리뷰 수정에서 새 작성/기존 수정 목적을 대화 방식과 분리했으며, 후속 수정의 원문 재첨부는 별도 선택이다. 2026-11-15에는 별도 코드 가져오기와 템플릿 코드 생성/후보 UI를 제거하고 하위 4단계 조합/실패/실제 경기 회귀를 완료했다. 목적 UI 구분과 이 제거·검증 작업은 재구현하지 않는다. 오류/결과 목적 액션과 하위 5단계 실제 외부 AI 평가는 남아 있다.

## 1. 목표와 유지할 조건

사용자가 전략을 구성하고 프롬프트를 복사해 원하는 외부 AI에 질문한 뒤, 받은 코드를 편집기에 직접 붙여 넣어 검사·테스트·저장하는 흐름을 완성한다. 게임에는 API 키·제공자·모델 등록을 요구하지 않는다. 외부 AI의 사용 조건과 이용 가능 범위는 해당 서비스에 따른다.

기존 최대 3개 전략과 순서, 명시적 프롬프트 생성, 항상 표시하는 미리보기, 코드 포함 선택, 입력 변경 후 재생성 안내, 복사 실패 시 수동 선택을 유지한다. 코드 원문 파일 저장·실행 검사·명시적 적용·undo·테스트 플레이·미저장 변경 보호를 유지한다. 코드 이력·대화 수집·자동 저장·외부 AI 자동 조작은 추가하지 않는다.

## 2. 단계별 작업 순서

### 0단계 — 직접 AI 연결 제거: 완료

- 연결/모델 탭과 관리 모달, 키·결제 안내, 직접 생성·수정·진행 UI 및 전용 브라우저 모듈을 제거했다.
- 서버에서 자격 증명 저장소·카탈로그·생성 큐·제공자 서비스를 초기화하거나 API를 연결하지 않는다. `/api/ai`와 하위 경로는 HTTP 410으로 종료한다.
- 기존 AI_* 환경변수를 읽지 않으며 `.env.example`에서 직접 연결 설정을 제거했다. 기존 사용자 `.env`는 수정하지 않는다.
- 기존 저장된 연결·키·후보 파일은 읽기·변경·삭제하지 않는다. 이전 서버는 재시작해야 변경이 적용된다. 영구 데이터 삭제·외부 제공자 키 폐기는 별도 명시적 작업이다.
- `src/ai`의 과거 서버 모듈과 독립 테스트는 미연결 코드로 보관한다. 일반 서버 진입점에서 가져오지 않고 브라우저에 제공하지 않는다. 제거한 API/브라우저 회귀 검사는 기능 종료·파일 보존·외부 호출 없음 검사로 대체했다.
- 로컬 `템플릿 코드 생성`과 후보 적용은 최초 제거에서 유지했지만 후속 사용자 결정으로 삭제했다. 별도 응답 가져오기 모달도 제거했다. 전략 선택은 프롬프트 작성 용도로 유지한다.

### 1단계 — 작성 목적과 액션 흐름 정리

1. 신규 작성·현재 전략 개선·오류 수정의 의미와 초기 상태를 분리한다. 신규는 원문 없이, 개선/수정은 사용자가 확인한 코드 문맥을 포함하도록 설계한다.
2. 생성 → 복사 → 외부 AI 사용 → 편집기에 붙여 넣기 → 검사 → 테스트·저장의 흐름을 사용한다. 복사 성공만으로 외부 AI 응답을 받은 것으로 표시하지 않는다.
3. `템플릿 코드 생성`과 별도 응답 가져오기·적용 UI 제거는 완료했다. 외부 응답은 일반 편집기 입력과 같은 경로로 취급한다. 별도 샘플 메뉴는 현재 요구 범위에 포함하지 않는다.
4. 미리보기는 숨기지 않고 편집기·그립·접기·최대화·키보드·모바일 기능을 유지한다. 전략 종류·개수·회피 규칙 변경은 이 단계에 섞지 않는다.

완료 기준: API 키 없이 신규/기존 코드에서 의도한 요청을 만들고, 다음 행동과 현재 코드 포함 여부를 확인할 수 있다. 목적 전환·문서 교체·취소로 코드가 자동 변경/저장되지 않는다.

### 2단계 — 검사 오류 수정 프롬프트

1. 편집기 검사 실패에 수정 프롬프트 액션을 추가한다. 진단과 검사 대상 원문 스냅샷·문서 식별/버전을 연결한다.
2. 구문·미선언 이름·필수 함수·실행 예외·시간 초과 등 실제 진단을 사용한다. 없는 원인이나 해결책을 단정하지 않는다.
3. 사용자가 포함 내용을 확인하고 프롬프트를 생성·복사한다. 변경된 편집 코드와 이전 실패 원문을 조용히 혼합하지 않고, 오래된 진단은 명시하거나 재검사를 요구한다.
4. 편집기에서 수정 요청으로 이동할 때 명시적 액션으로 필요한 실패 코드와 진단을 전달하고, 취소·문서 교체·로그아웃 시 임시 문맥을 정리한다. 새 DB/코드 이력 저장은 만들지 않는다.

완료 기준: 실패 코드 → 수정 프롬프트 → 반환 코드 재검사 → 명시적 적용 → 테스트가 이어진다. 진단/코드 불일치·늦은 검사 응답·입력 변경·다른 문서 전환을 자동 검증한다.

### 3단계 — 작성용 규약과 출력 품질 정리

1. 현재 전체 문서·완성 예제를 넣는 구성을 분석하고 작성용 규약의 필수 항목을 목록화한다. 실제 API·실행 제한·게임 규칙의 공통 원본과 자동 대조한다.
2. 신규 작성은 최소 유효 골격, 수정은 요청 대상 원문을 중심으로 구성하는 방식을 비교한다. 예제 전략을 무조건 복제하도록 유도하지 않는다.
3. 완성된 단일 JavaScript 파일을 코드 블록 하나로 받는 출력 규칙을 유지한다. 코드 크기를 임의로 제한·절단하거나 부분 diff 적용기를 추가하지 않는다.
4. 새 대화는 독립적인 전체 규약을 포함하고, 사용자가 같은 대화의 후속 요청을 선택하면 전체 규약·예제를 생략하고 짧은 요약·출력 지시를 유지한다. 생성 횟수로 외부 문맥을 추정하지 않는다. 규약 내용 변경·새 문서에서는 전체 규약 모드로 돌아간다. [상세 모드·상태 정책](prompt-context-reduction-plan.md)을 따른다.

완료 기준: 필수 규칙·제한 누락 없이 중복을 줄인다. 길이 감소만으로 품질 개선을 선언하지 않고 동일 신규/수정/오류 사례의 실행 검사·요청 준수로 평가한다.

### 4단계 — 테스트 결과 기반 전략 개선

1. 본인 테스트/완료 경기의 점수·패널티·충돌·계산 시간·아이템 사용 등 실제 분석 지표를 선택해 개선 요청으로 연결한다.
2. 경기 당시 원문과 맵·옵션·실행 조건을 연결한다. 현재 코드와 다르면 알려주고 사용자가 개선 대상을 결정하게 한다.
3. 통계로 관찰한 사실과 개선 목표를 구분한다. 예를 들어 망치 사용 0회만으로 코드 결함이나 원인을 단정하지 않는다.
4. 선택한 본인 로그·요약만 포함하고 다른 사용자 원문·계정·키·내부 경로를 전달하지 않는다. iframe 메시지는 기존 Origin·송신 창·경기/문서 식별 경계를 유지한다.

완료 기준: 결과 선택 → 개선 프롬프트 → 코드 검사·적용 → 재테스트가 이어진다. 조건이 다른 경기 점수를 단순 개선 증거로 표시하지 않으며 무조건적인 승률 향상을 약속하지 않는다.

### 5단계 — 실제 사용 평가·마무리

1. 신규 전략·기존 전략 수정·문법 오류 수정·시간 초과 개선 시나리오를 정한다. 실제 외부 AI 사용은 사용자의 선택과 액션으로 확인하며 유료 API를 대신 호출하지 않는다.
2. 복사부터 테스트까지 필요한 행동 수, 오류에서 회복하는 흐름, 검사 통과·요청 반영을 비교한다. 모델마다 결과가 같다고 가정하지 않는다.
3. 대체 코드/클립보드 자동 검사와 실제 AI 출력·사내 브라우저 복사 검증 범위를 분리해 기록한다.
4. 기존 저장·권한·게임·관리자·Google 인증 회귀와 원문/진단/결과 문맥 정리를 확인하고 사용법을 갱신한다.

완료 기준: API 연결 없이 생성·수정·오류 복구·결과 개선 전체 흐름을 사용할 수 있고, 기존 사용자 데이터와 코드 소유권 경계가 유지된다.

## 3. 이번 계획에서 보류할 아이디어

빠른 시작 조합, 아이템 회피를 별도 준수 규칙으로 분리, 프롬프트 파일 내보내기, 부분 코드 변경·차이 적용, 요청 설정 저장은 실제 반복 사용 필요성을 확인한 뒤 별도 범위로 정한다. 전략 선택 수를 무조건 늘리지 않는다.

직접 API 연결·Claude/Gemini 생성 확장은 필수 작업이 아니다. FE·BE 분리와 여러 언어 지원은 기존 고도화 보관 상태를 유지한다. DB·컨테이너·사내 배포는 별도 작업이며 개인정보 운영 준비는 실서비스 개시 전 마지막 필수 단계다.

## 4. 진행 방식

1단계부터 순서대로 구현하고 각 단계에서 관련 검증·리뷰 후 결과를 설명한다. 다음 단계의 코드까지 이번 제거 작업에 섞지 않는다. 커밋은 사용자 요청에 따라 진행한다.
