- 상태: 현재 코드에 근거한 FE 요구사항·작업 순서 정리. 별도 FE 서버 구현·실행·배포는 아직 하지 않았다.

- 관련: [분리 계획](frontend-backend-separation-plan.md), [운영·실행 경계](game-backend-boundaries.md), [운영 DB 계획](game-operations-database-plan.md).

## 1. 첫 분리의 목표

브라우저는 하나의 공개 서비스 주소로 접속한다. FE 웹서버는 화면/정적 파일을 제공하고 API 요청을 내부 BE로 중계한다. 기존 Node 기반 화면 제공 로직을 독립 FE 진입점으로 옮기는 구성을 1차 기준으로 삼는다. 현재 UI와 브라우저의 `/api/...` 경로를 유지하며 프런트엔드 프레임워크 전환을 선행 조건으로 삼지 않는다.

```text
브라우저 → 공개 HTTPS 주소 → FE 웹서버
                            ├─ 페이지·JS/CSS·게임 에셋·영상
                            └─ /api/* → 내부 BE
                                         ├─ 인증·권한·게임 운영 API
                                         └─ 현재 경기 실행·SSE·알고리즘 프로세스
```

TLS 종료는 실제 배포의 진입 프록시 또는 FE 계층에서 결정한다. FE/BE 프로세스는 독립 포트/기동/종료를 지원하고 한 컨테이너 배치와 각각의 컨테이너 배치 모두 가능한 설정 경계를 둔다. 실제 이미지/프로세스 관리자 선정은 패키징 단계에서 한다.

이번 분리에서 BE를 다시 운영/실행 서비스로 물리 분리하거나 DB 전환·다국어 실행기를 함께 구현하지 않는다. 그 책임 경계를 향후 유지할 수 있게 하되 별도 작업으로 진행한다. 직접 AI 연결은 제거 상태를 유지하고 프롬프트 생성·코드 검사·테스트 플레이만 현재 기능으로 검증한다.

## 3. BE와 먼저 맞춰야 할 계약

FE만 작성해 현재 BE 앞에 그대로 붙이는 것으로 완료되지 않는다. 현재 BE는 localhost/HTTP/자신의 수신 포트를 기준으로 Host/Origin을 검사하고 있으므로 내부 주소와 외부 주소를 분리하는 공통 요청 컨텍스트가 선행되어야 한다.

- **공개 주소:** 브라우저 접속·Google 시작/콜백·리다이렉트·쿠키는 공개 주소를 기준으로 한다. 내부 BE 포트를 OAuth 콜백에 노출하지 않는다.
- **신뢰 경계:** FE는 외부가 보낸 전달 헤더를 제거/재설정하고 BE는 허용된 경로의 FE만 신뢰한다. BE 포트가 외부에서 직접 접근되지 않는 배포 정책과 함께 검증한다. CORS 전체 허용을 해결책으로 삼지 않는다.
- **쿠키:** 로그인/게스트/OAuth 쿠키를 별도 `Set-Cookie` 헤더로 보존한다. 공개 HTTPS 기준의 Secure·Path·SameSite 정책을 유지하고 FE 세션 조회에서 받은 갱신/삭제 쿠키도 필요한 경우 브라우저로 전달한다.
- **권한:** FE의 페이지 접근 확인은 UX다. API의 최종 인증·역할·소유권·변경 요청 검사는 항상 BE에서 수행한다. 정적 JS가 비공개 데이터의 접근 제어를 대체하지 않는다.
- **스트리밍:** 일반 JSON API·파일 전송·SSE의 시간 제한/버퍼를 구분한다. 연결 전용 헤더는 중계 규칙대로 처리하며 업로드 취소와 SSE 종료가 BE 자원 정리에 전달돼야 한다. 경기 SSE 단절 자체는 경기 중단 명령이 아니다.
- **오류 계약:** JSON 오류 형식·HTTP 상태·경기 이벤트 구조를 유지한다. API 404를 홈 HTML로 바꾸지 않고 연결 실패 시 비밀/내부 경로를 노출하지 않는다.
- **기존 자원 수명:** FE는 게임/세션을 보관하지 않는다. FE만 재시작할 때 BE의 세션·경기는 유지되지만 브라우저 재접속/복귀 동작은 별도로 검증한다. BE 재시작 후 현재 메모리 세션/경기가 유지된다고 약속하지 않는다.

Node HTTP 중계는 스트림/헤더를 애플리케이션에서 명시적으로 다뤄야 한다. SSE는 이벤트 경계와 연결 수명에 맞게 전달하고 여러 쿠키는 합쳐 하나로 만들지 않는다. 구현 기준: [Node HTTP](https://nodejs.org/api/http.html), [SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events), [Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).

## 4. 빌드와 실행 설정

현재 저장소는 하나로 유지하고 FE와 BE 진입점/산출물은 구분한다. 브라우저에는 공개 에셋/클라이언트 코드만 배포하고 FE 프로세스에는 내부 BE 주소 등 필요한 연결 설정만 주입한다. Google client secret·DB 비밀·사용자 원문/실행 기록 저장 경로는 BE에만 둔다. 기존 루트 `.env` 전체를 FE 실행 환경에 무조건 전달하지 않는다.

구현 시 정할 설정은 FE 수신 주소/포트, BE 내부 수신 주소/포트, 고정 BE 대상 URL, 공개 서비스 URL, 신뢰 프록시 범위, 요청/스트림 시간 정책이다. 실제 운영 도메인·TLS 위치·방화벽은 배포 테스트에서 맞춘다. FE 분리 개발은 외부 도메인 확정 없이 localhost의 두 포트로 검증할 수 있다.

보호 HTML·인증/API는 no-store를 유지한다. 해시/버전 없는 기존 정적 파일에 무조건 장기 immutable 캐시를 적용하지 않는다. 파일명 버전 또는 재검증 정책으로 FE 코드/에셋/BE 규약의 일치를 보장한다. 로그인 배경 영상은 크기와 실제 서비스 전송 방식에 맞춰 스트리밍·범위 요청 처리를 검증한다.

접속 점검에는 상태·지연·연결 수·프록시 실패 등 필요한 지표만 남긴다. 쿠키·인증 헤더·OAuth code/state·코드 원문·민감 쿼리/본문을 일반 접근 로그로 수집하지 않는다. FE 관측 로그와 게임 실행 전량 로그는 별도다.

## 5. 권장 작업 순서

1. **현재 경로/의존성 목록과 FE/BE 계약 확정:** 정적 파일·공통 코드·인증·SSE·업로드·설정 범위를 고정한다.
2. **공통 코드·요청 주소 정책 정리:** 통합 실행 회귀를 유지하면서 BE가 FE 경유 요청을 정확히 판단할 기반을 만든다.
3. **독립 FE·API 중계 구현:** 정적 자산, API, 스트림, 취소, 오류를 연결한다.
4. **페이지 접근·OAuth·CSP 이전:** 실제 공개 경로에서 로그인/관리자/편집기/iframe을 검증한다.
5. **개별 빌드·기동·배포 산출물:** 설정 예제·비밀 경계·상태/종료·캐시·영상 전송을 준비한다.
6. **통합/장애 리뷰 후 기본 실행 전환:** 게스트/로그인 게임·원문 저장/재대결·프롬프트/검사/테스트·맵 편집/게시를 모두 FE 주소로 검증한다.

외부 Google 검증은 우선 테스트 대체 응답으로 수행하고 실제 배포 OAuth는 사용자 환경에서 최종 확인한다. 기존 계정/원문/키를 자동 검사에 사용하지 않는다. DB 전환·단일 컨테이너 패키징은 이 경계를 기준으로 별도 진행하고 개인정보 운영 준비는 실제 서비스 개시 전 마지막 필수 단계로 유지한다.
