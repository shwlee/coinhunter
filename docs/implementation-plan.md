# 새 게임 전체 작업 계획

- 작성일: 2026-09-26
- 대상 저장소: 현재 작업 폴더 `coinhunter`의 Git 저장소
- 상태: 기획 기준 및 구현 순서 정리 완료. 제품 코드는 아직 구현하지 않음.
- 기준: 사용자와 합의한 최신 기획을 우선한다. 기존 저장소는 규칙·자산·알고리즘 규약의 참고 구현이다.
- 관련 문서: [아키텍처 설계안](architecture.md), [작업 준비 및 구현 체크리스트](work-checklist.md).

## 1. 목표와 범위

기존 Coin Challenger를 웹 기술로 새로 구현한다. 사내 네트워크에서 접근하는 웹 서비스로 시작하며, 게임 호스트는 Azure VPN으로 접근 가능한 영역에 배치할 예정이다. 실제 접근 경로와 배포 구성은 배포 단계에서 확정한다.

사용자는 설치 없이 웹에서 알고리즘 파일을 업로드하거나, 로그인 후 직접 또는 AI로 알고리즘을 작성하고 저장하여 게임에 사용한다. AI 코드 생성은 부가 기능이 아닌 첫 서비스의 필수 기능이다.

구현은 게임 플레이부터 시작한다. 이후 코드 작성 화면의 테스트 플레이가 동일한 게임 엔진과 실행 환경을 사용하도록 연결한다.

### 첫 서비스에 포함

- JavaScript 알고리즘 실행
- 게스트 파일 업로드 플레이
- 사용자 로그인, 계정별 알고리즘 저장·불러오기·새 이름으로 저장
- 개인 플레이와 더미 대결, 최대 4인 경기 구성
- 관리자 등록 맵 선택
- 기존 코인·HurryUp·랜덤 기믹 계승
- 신발·망치·x2·랜덤점프 아이템과 시각 효과
- 코드 편집기, 테스트 플레이, 디버그 출력 창
- AI 알고리즘 생성·수정
- 관리자 사용자·게임 옵션·대칭 맵 관리

### 선택 확장

- 소유자가 허용한 알고리즘을 타 사용자가 더미로 선택하는 기능. 사용자가 가능성을 제시한 항목이므로 첫 서비스 필수 범위와 구분한다. 구현 여부는 단계 5에서 확정한다.

### 첫 서비스에서 제외

- 사용자 간 소스 코드 공개 및 일반 공유
- 편집기 undo/redo 외 코드 변경 이력·버전 복원 UI
- 브레이크포인트·단계별 코드 실행 디버거
- 사용자 PC에서 별도 알고리즘 프로세스 실행
- Python·C#·C++ 지원
- 대회 기능: 후속 확장. 현재 단계에서는 확장을 방해하지 않는 데이터·실행 경계만 마련한다.

## 4. 알고리즘 작성 및 실행 계약

### 4.1 기존 작성 규칙 유지

기존 게임 README의 '알고리즘 작성 주의 사항'을 사용자 문서, 코드 검증, AI 지침에 공통으로 반영한다.

- 언어의 built-in 기능만 사용한다. 외부 라이브러리와 제3자 코드 import는 금지한다.
- 타입에 고정된 공유 참조를 만드는 코드를 금지한다. 기존 문서는 C#의 static을 예로 들며, JavaScript 적용 범위는 규약 문서에 명시한다.
- 비동기·병렬·스레드·Task 기반 알고리즘을 금지한다.
- sleep 등 호출을 의도적으로 대기시키는 기능을 금지한다.
- 내부·외부 web/socket 접근을 금지한다.
- 게임 진행을 방해하거나 중단하는 기능을 금지한다.
- 알고리즘에 필요한 코드는 한 파일에 작성한다.
- '언어 built-in'과 Node.js의 파일·네트워크·프로세스 API를 구분한다. 실행 환경에서 허용할 기능 목록을 명시하고 제한한다.

### 4.2 JavaScript 인터페이스

- 기존 클래스와 `module.exports` 형식을 호환 대상으로 삼는다.
- `initialize(myNumber, column, row)`: 경기 시작 시 플레이어 번호와 맵 크기를 전달한다.
- `getName()`: 표시 이름을 반환한다.
- `moveNext(map, myPosition, items)`: 현재 맵·본인 위치·아이템 위치를 받아 방향을 반환하는 확장 계약을 제안한다. 구현 착수 시 API 문서에서 최종 고정한다.
- 맵 크기는 경기 중 불변이므로 initialize에서 한 번 전달한다.
- map은 기존처럼 1차원 정수 배열이다. `-1`은 벽, `0`은 빈칸, 양수는 코인 점수다.
- 반환 방향은 `0=왼쪽`, `1=위`, `2=오른쪽`, `3=아래`다. `-1`은 이번 턴 패널티다.
- items는 길이 4의 정수 배열이며 `[신발, 망치, x2, 랜덤점프]` 위치를 전달한다. 없는 아이템은 `-1`이다.
- 기존 두 인자 moveNext 예제의 호환성을 검증한다.
- 호출할 때 맵과 아이템의 사본을 전달하여 사용자 코드가 실제 게임 상태를 수정하지 못하게 한다.
- 효과 종류·남은 횟수 등 추가 상태 제공은 아직 확정하지 않았다. 임의로 필수 인자를 추가하지 않는다.
- 디버그 출력 API를 제공한다. 이름·출력량 제한·문자열 처리 규칙은 API 명세에서 결정한다.

### 4.3 실행 수명과 500ms 제한

- 플레이어별 알고리즘 실행 프로세스와 인스턴스는 경기 동안 유지한다.
- 정상적인 정리·종료는 게임이 완전히 끝났을 때 수행한다.
- 매 턴의 사용자 알고리즘 실행 시간은 독립적으로 최대 500ms다.
- 500ms의 측정 구간은 실행 환경에서 사용자 함수를 호출하기 직전부터 반환 또는 중단까지로 정의한다. 프로세스 시작, 호출 대기열, 브라우저 통신, 이동·대체 액션 시간과 구분하고 시간 측정 방식·중단 지연을 기술 검증에서 기록한다.
- 시간 초과에 대응하기 위해 프로세스를 종료·교체하거나 인스턴스를 초기화하는 방식은 사용하지 않는다.
- 시간 초과 시 현재 호출만 중단하고 이번 턴을 -1에 해당하는 패널티로 처리한다. 다음 턴에는 같은 인스턴스를 호출한다.
- 결과만 무시하고 연산을 계속 실행시키거나, 이전 호출과 다음 호출을 겹쳐 실행시키는 방식은 사용하지 않는다.
- 일반 타이머나 Promise.race만으로는 이 요구를 충족했다고 판단하지 않는다.
- 종료 이후 또는 다른 턴에 속한 결과를 수락하지 않도록 경기·플레이어·호출 식별자를 관리한다.
- 코드 로딩·생성자·initialize·getName의 제한은 이동 판단 500ms와 별도의 시작 전 정책으로 명시한다.
- 시간 초과 이전의 인스턴스 변경을 되돌리지 않는 방안은 제안 상태다. 실행 환경 검증 결과와 함께 확정한다.

이 요구는 가장 먼저 검증할 기술 조건이다. 함수 중단 후 동일 인스턴스를 재사용할 수 있는 JavaScript 실행 환경을 선정하고 실제로 검증한다. 충족하지 못하면 요구를 임의로 완화하거나 프로세스 재시작으로 대체하지 않고, 실패 원인과 선택지를 제시한다.

## 5. 경기 진행과 동시성

- 일반 턴은 '알고리즘 수행 결과 + 플레이어 이동 또는 대체 액션' 완료까지다. 랜덤점프 효과 중에는 사용자 알고리즘 수행을 게임 측 목적지 결정으로 대체한다.
- 각 플레이어는 독립적으로 턴을 진행한다. 공통 턴에 맞추거나 모든 플레이어의 응답을 기다리지 않는다.
- 같은 플레이어의 두 턴은 겹치지 않는다. 서로 다른 플레이어는 동시에 진행할 수 있어야 한다.
- 서버가 실제 맵, 위치, 점수, 효과와 경기 종료를 관리한다. 브라우저는 상태와 액션을 표시한다.
- 공용 맵 변경은 서버가 순서를 확정하여 코인·아이템 중복 획득과 벽 중복 파괴를 방지한다.
- 방향 계산 당시와 액션 실행 당시의 맵이 다를 수 있으므로 액션 확정 시 최신 상태를 확인한다.
- 플레이어 간 통행 방해 여부와 동일 시점 획득 우선순위는 상세 규칙에서 고정한다. 플레이어끼리 통행을 막지 않고 먼저 확정된 획득을 인정하는 방안이 제안되어 있다.

### 5.1 패널티와 액션 시간

- -1이면 이번 턴의 이동만 제자리 패널티 액션으로 바꾼다.
- 다음 턴을 추가로 건너뛰는 페널티는 없다.
- 시간 초과도 동일한 이번 턴 패널티로 처리한다.
- -1은 명시적 패널티 반환값이다. 예외·잘못된 반환형·-1 및 0~3 이외 반환값은 별도 오류로 분류하되, 이번 턴의 실패 액션에 연결한다.
- 이동 시간과 이동 대신 수행하는 액션의 시간은 같아야 한다.
- 망치 없이 벽 방향을 선택하면 물음표와 고개 갸웃 액션을 수행한다.
- 알고리즘 계산에 걸리는 시간은 별도이며, 신발은 계산 시간을 줄이지 않는다.
- 신발 중 대체 액션에도 절반 시간을 적용하는 방안은 직전 응답의 해석이다. 세부 명세에서 확인한다.

## 6. 게임 규칙과 아이템

### 6.1 기존 규칙 계승

- 코인: Copper 10, Silver 30, Gold 100, Diamond 200, BlackMatter 500.
- 기본 이동은 상하좌우 한 칸이며 테두리 밖으로 나갈 수 없다.
- 기존의 네 모서리 시작과 최대 4인 구성을 계승한다.
- 기존 코인 소진·점수 순위·HurryUp을 계승한다. 새 아이템이 경기 종료를 지연시키지 않도록 종료 조건을 명세한다.
- BlackMatter 생성과 랜덤 벽 파괴는 별도 옵션으로 분리한다.
- 경기 시작 전 사용자가 맵·본인 알고리즘·더미·허용된 랜덤 기믹 옵션을 선택한다.

### 6.2 효과

| 아이템 | 효과 및 소모 기준 | 표현 |
| --- | --- | --- |
| 신발 | 획득 다음 턴부터 기본 3턴 동안 이동 시간 절반. 한 번에 한 칸 이동한다. | 날개 달린 신발, 잔상 |
| 망치 | 방향에 내부 벽이 있을 때 이동 대신 벽 파괴. 기본 3개 파괴까지 유지. 파괴한 턴에는 벽 칸으로 진입하지 않는다. | 안전모, 망치, 벽 파괴 액션 |
| x2 | 다음 기본 3개 코인의 획득 점수 두 배. 실제 획득한 코인 수만 차감한다. | 머리 위 돈다발, 코인 획득 시 코인 분사 |
| 랜덤점프 | 획득 다음 턴부터 기본 3턴 동안 사용자 알고리즘 호출 없이 게임 측 플레이어 인스턴스가 유효한 랜덤 목적지를 결정하고 순간이동한다. | 머리 위 굴러가는 주사위, 순간이동 |

- 지속 턴 수·파괴 벽 수·코인 수는 조정 가능하게 구성한다. 옵션의 관리 범위는 관리자 설정 명세에서 고정한다.
- 테두리 벽은 망치로 파괴할 수 없다.
- 신발·랜덤점프는 실패 턴도 지속 횟수에 포함한다. 망치·x2는 실제 파괴·획득 때만 차감한다.
- 한 플레이어가 보유하는 효과는 한 종류다. 새 아이템을 획득하면 같은 종류라도 기존 효과를 삭제하고 새 효과를 적용한다.
- 효과 소모는 해당 턴 시작 시 적용된 효과에 연결한다. 이동 중 새로 획득하거나 교체한 효과를 이전 턴 효과의 차감 대상으로 처리하지 않는다.
- 효과 변경·종료 때 외형과 이펙트도 함께 갱신한다.
- 번개·마비 기능은 구현하지 않는다.
- 점프할 위치가 없으면 제자리에서 주사위 파괴와 고개 갸웃 액션을 수행하고 한 턴을 소모한다.
- 점프 실패 후 남은 효과 유지 및 다음 턴 주사위 재표시의 세부 동작은 명세에서 확정한다.

### 6.3 아이템 출현과 배치

- 한 번에 네 종류를 하나씩 함께 배치한다.
- 배치된 아이템이 하나라도 남아 있으면 다음 묶음을 생성하지 않는다.
- 기존 플레이어 효과가 남아 있는지는 재출현 조건과 별개다.
- 출현 시점·주기는 관리자가 맵에 설정하며 일반 사용자는 변경하지 못한다.
- 아이템은 랜덤 기믹과 별도 설정으로 발동하며 HurryUp에도 종속되지 않는다. 경기 종료 이후에는 생성하지 않는다.
- 배치 공간은 빈칸 기준이며 모든 플레이어의 현재 칸 및 상하좌우 직선 두 칸을 제외한다. 대각선을 포함한 사각형 반경으로 바꾸지 않는다.
- 랜덤점프 목적지도 같은 제외 규칙을 사용한다.
- 네 종류를 모두 배치할 수 없으면 그 묶음을 생성하지 않는다.
- 생성 실패 후 재검사 시점, 기존 아이템과의 중복 방지, 이동 중 플레이어의 기준 위치는 상세 배치 규칙에서 고정한다.

## 7. 관리자와 맵

- 관리자 로그인으로 사용자 관리, 게임 옵션 관리, 맵 생성·편집 메뉴를 제공한다.
- 가로·세로 크기를 입력하면 맵 베이스를 생성한다.
- 벽·코인 편집은 상하좌우 대칭 위치에도 동일하게 반영한다. 삭제·수정도 대칭을 유지한다.
- 중앙 행·열에 위치한 셀은 중복 처리하지 않는다.
- 랜덤 맵 생성도 동일한 대칭 규칙을 따른다.
- int[] import/export를 지원하고 맵 크기는 별도로 함께 전달하거나 파일 메타데이터에 포함한다.
- import 시 배열 길이·지원 값·대칭·시작 위치·테두리·도달 가능성을 검사한다.
- 네 시작점의 접근 가능한 공간과 도달 불가능한 코인을 검증한다. 대칭만으로 공정성을 보장했다고 판단하지 않는다.
- 맵에 아이템 출현 설정을 저장한다.
- 일반 사용자에게 표시할 맵의 공개 상태를 관리한다.
- 시작된 경기는 시작 시점의 맵·옵션을 사용한다. 이후 관리자 편집이 진행 중인 경기를 바꾸지 않는다.

## 8. 코드 작성 화면과 데이터 저장

- 로그인 사용자는 로컬 파일 또는 본인 저장 목록에서 코드를 불러온다.
- 새 코드 생성, 직접 편집, 저장, 새 이름으로 저장을 제공한다.
- 편집기 undo/redo는 제공하지만 별도 변경 이력·과거 버전 복원 기능은 제공하지 않는다.
- 저장 전 변경 사항이 있는 상태에서 화면을 나갈 때의 동작을 정의한다.
- 코드 작성 화면에서 같은 게임 엔진으로 테스트 플레이한다.
- 디버그 창에는 플레이어·턴 식별 정보와 출력·실행 오류를 구분하여 표시한다.
- 출력량·한 메시지 길이에 제한을 두며 텍스트로 표시한다.
- 저장 데이터에는 알고리즘 ID, 소유자 ID, 이름, 언어, 코드, 생성·수정 시각, 더미 사용 허용 여부를 포함한다.
- 계정 식별자로 경로를 직접 신뢰하기보다 서버의 소유권 검사를 거쳐 지정된 저장소에 보관한다.
- 실행 중에는 시작 시 선택한 코드를 사용한다. 편집·저장은 다음 실행에 반영한다. 사용자용 버전 이력을 만들 필요는 없다.

## 9. AI 연동

- AI 최초 생성과 기존 코드 수정을 모두 지원한다.
- 사람이 코드를 읽지 않아도 자연어 요청 → 생성 → 테스트 → 저장으로 작업할 수 있게 한다.
- AI에는 확정된 게임 규칙, JavaScript 함수 계약, 제한 사항, 샘플 알고리즘을 제공한다.
- 생성 코드도 파일 업로드·직접 작성 코드와 동일하게 검증하고 실행한다.
- 에디터 내용을 덮어쓰는 방식과 실패 시 기존 코드 유지 동작을 정의한다. 별도 영구 이력 저장은 추가하지 않는다.
- 연결 정보·자격 증명을 브라우저나 알고리즘 실행 환경에 노출하지 않는다.

### 네트워크 조건과 미정 사항

- 사내 네트워크는 외부 네트워크에 접근 가능하다.
- 게임 호스트 자체는 외부 네트워크에 직접 접근할 수 없다.
- 게임 호스트는 Azure VPN 접근 영역에서 호스팅 예정이며 사내망에서의 접근에도 제한이 있다.
- 따라서 게임 서버가 외부 AI API를 직접 호출할 수 있다고 가정하지 않는다.
- AI 제공자, 호출 중계 위치, 인증·자격 증명 보관, 데이터 이동 경로를 별도 설계한다.
- 경로가 확정되기 전에는 AI 연결 인터페이스와 개발용 대체 응답으로 UI를 검증할 수 있으나, 실제 AI 연결 전에는 필수 기능 완료로 표시하지 않는다.

## 10. 논리 구성과 기술 선정 원칙

```text
웹 클라이언트
  ├─ 플레이 화면 / 코드 작성·AI 화면 / 관리자 화면
  └─ 서버 API 및 경기 이벤트 연결
        ├─ 인증·알고리즘·맵·설정 저장
        ├─ 경기 관리 및 게임 엔진
        │    └─ 실행 관리자 → 경기 동안 유지하는 플레이어별 JS 실행 환경
        └─ AI 연결 계층 → 별도 확정할 중계 경로
```

- 게임 엔진은 화면과 분리하고 테스트 가능하게 만든다.
- 향후 언어 확장은 실행 어댑터 추가로 처리할 수 있도록 계약을 분리한다.
- 플레이어별 500ms 중단·인스턴스 유지 검증 후 실행 기술을 선택한다.
- 프런트엔드 프레임워크, 서버 프레임워크, DB, JS 엔진, 에디터 제품은 아직 확정하지 않았다.
- TypeScript 기반 게임 로직·웹 UI는 후보이며, 앞선 제안을 사용자 확정 선택으로 취급하지 않는다.
- 배포 환경의 운영체제와 자원 제한을 확인하고 기술 선택을 기록한다.

## 11. 구체적인 작업 순서와 완료 기준

### 단계 0. 명세와 기준 자료 고정

1. 본 문서를 기준으로 기존 코드·README의 관련 규칙을 대조한다.
2. 턴 상태도, 경기 종료, 효과 변경, 동시 획득, 배치 실패 규칙을 작성한다.
3. 알고리즘 API와 허용 기능·금지 기능을 문서화한다.
4. 맵·알고리즘·경기·사용자 데이터 계약을 작성한다.
5. 미정 항목을 결정 기록으로 관리하고 확정 사항과 구분한다.
6. AI 호출 경로에 대한 사내망·Azure 접속 조건 조사를 시작한다. 네트워크 검증은 단계 1~7과 병행하며, 실제 AI 화면 통합은 단계 8에서 수행한다.

산출물: `game-rules.md`, `algorithm-api.md`, `architecture.md` 등 상세 문서.

완료 기준: 구현자가 턴·아이템·API를 임의로 해석하지 않고 작업할 수 있다.

### 단계 1. JavaScript 실행 환경 기술 검증 — 최우선

1. 실행 중인 함수를 제한 시간에 중단하고 동일 인스턴스를 재사용하는 후보를 조사한다.
2. module.exports 형식 클래스와 필수 메서드 로딩을 검증한다.
3. 정상 코드·예외·무한 루프·과도한 출력·금지 기능 접근을 검증한다.
4. 정상 호출 → 무한 루프 호출 → 정상 호출을 같은 프로세스·인스턴스에서 수행한다.
5. 4개 플레이어를 동시에 실행하고 한 플레이어의 시간 초과가 나머지를 막지 않는지 확인한다.
6. 시간 측정 경계, 중단 후 상태, 메모리 제한 동작을 기록한다.
   - 사용자 코드의 try/catch·finally가 중단을 무력화하는지, 종료되지 않는 built-in 연산이 있는지 검증한다.
   - 시간 초과 전 저장한 인스턴스 필드와 프로세스 식별자가 다음 호출에도 유지되는지 확인한다.
   - 제한은 500ms로 고정하고 관측된 중단 지연을 기록한다. 테스트 통과를 위해 제한을 늘리지 않는다.
7. 실행 환경과 서버 기술을 선정한다.

완료 기준: 500ms 제한, 현재 호출만 중단, 프로세스·인스턴스 유지, 다음 턴 재호출이 모두 실제 검증된다. 실패하면 본 구현 확대 전에 기술 문제를 해결한다.

### 단계 2. 프로젝트 기반과 서버 게임 엔진

1. 웹·서버·공통 계약·테스트 디렉터리를 구성한다.
2. 개발 실행, 설정, 빌드, 테스트 명령을 마련한다.
3. 고정 맵과 샘플 JS 알고리즘으로 최소 경기를 구성한다.
4. 플레이어별 독립 턴과 실행 관리자 연계를 구현한다.
5. 이동·벽·코인 획득·점수·종료와 액션 시간 처리를 구현한다.
6. 동시 획득 및 맵 변경의 중복 적용을 방지한다.
7. 경기 종료 시 실행 환경을 정리한다.

완료 기준: 화면 없이 1~4개 알고리즘이 독립적으로 경기를 완료하고, -1·시간 초과·벽 충돌을 정해진 턴으로 처리한다.

### 단계 3. 최초 웹 플레이 완성

1. 로컬 JS 파일 업로드와 시작 전 검증을 구현한다.
2. 서버의 고정 맵 목록과 기본 더미를 선택하도록 한다.
3. 맵·캐릭터·이동·점수판·종료 결과를 표시한다.
4. 상태·액션 이벤트와 브라우저 표시를 연결한다.
5. 물음표·고개 갸웃·제자리 패널티 액션을 구현한다.
6. 시작 실패·실행 오류·연결 끊김 표시를 구현한다.

완료 기준: 브라우저에서 JS 파일을 올려 더미와 실제 경기를 끝낼 수 있다. 코드 에디터와 AI가 없어도 기본 게임을 검증할 수 있다.

1. 신발·망치·x2·랜덤점프 효과 모델을 구현한다.

4. 랜덤점프 중 사용자 알고리즘이 호출되지 않는지 검증한다.
5. 효과별 외형·액션·점프 실패 연출을 구현한다.
6. BlackMatter 생성과 벽 파괴 옵션을 분리한다.
7. HurryUp과 독립적인 아이템 생성을 연결한다.

완료 기준: 아이템 동작과 교체 규칙, 액션 시간, 생성 제한이 자동 검증되며 화면에서 효과를 구별할 수 있다.

1. 사용자·관리자 인증과 역할 검사를 구현한다.

6. 선택 확장인 더미 공유의 포함 여부를 확정하고, 포함 시 허용·취소와 소스 비공개 실행을 구현한다.

완료 기준: 권한표가 실제 API에서도 적용되고 계정 데이터가 세션·PC 변경 후에도 유지된다.

### 단계 6. 관리자 옵션 및 대칭 맵 편집

1. 사용자 관리 범위와 관리자 옵션 목록을 고정한다.

7. 플레이 화면의 선택 목록을 관리자 맵 데이터에 연결한다.

완료 기준: 관리자가 생성한 유효한 대칭 맵을 사용자가 선택할 수 있고 일반 사용자는 맵 전용 설정을 변경하지 못한다.

### 단계 7. 코드 에디터와 테스트 플레이

1. 새 코드·파일 열기·저장 목록 열기·저장·새 이름 저장을 구현한다.
2. 편집기 undo/redo와 미저장 변경 처리를 제공한다.
3. 공통 게임 실행 경로로 테스트 플레이를 연결한다.
4. 디버그 출력과 턴 오류를 플레이어별로 표시한다.
5. 실행 중 편집과 저장이 진행 중 경기에 영향을 주지 않는지 확인한다.
6. 게스트의 생성·편집 기능 접근을 차단한다.

완료 기준: 로그인 사용자가 작성 → 테스트 → 출력 확인 → 저장 → 플레이 화면에서 선택하는 흐름을 완료한다.

### 단계 8. AI 알고리즘 작성 통합

1. 앞 단계와 병행해 조사한 실제 사내망·Azure AI 호출 경로를 최종 검증한다. 경로가 미확정이면 연결 구현의 선행 조건으로 해결한다.
2. 제공자 어댑터와 자격 증명 관리 방식을 구현한다.
3. 공통 규약·금지 사항·예제를 AI 요청에 포함한다.
4. 자연어 최초 생성·수정과 편집기 반영을 구현한다.
5. 응답 실패·취소·형식 오류를 처리한다.
6. 생성 코드 검증·테스트 플레이·저장까지 연결한다.

완료 기준: 실제 연결된 AI로 생성한 코드가 규약을 만족하고 테스트·저장·플레이까지 이어진다. 개발용 대체 응답만으로 완료 처리하지 않는다.

### 단계 9. 통합 검증과 사내 배포

1. 아래 검증 표에 따라 회귀·통합 검증을 수행한다.
2. 동시 경기 수와 서버 자원 사용량을 측정하고 운영 한도를 정한다.
3. 사용자 이탈·연결 끊김·서버 재시작 시 경기와 프로세스 정리 정책을 검증한다.
4. VPN·접근 제한·TLS·실시간 연결·AI 중계 경로를 실제 환경에서 확인한다.
5. DB·저장 데이터 백업 및 복원, 로그 보관 정책을 마련한다.
6. 배포·설정·관리자 초기화·복구 절차를 문서화한다.
7. 사용자가 검토 가능한 배포 결과와 실행 절차를 준비하고 실제 배포 단계에서 네트워크 구성을 확정한다.

완료 기준: 사내 허용 경로에서 게스트 플레이와 로그인·AI 작성·저장·관리자 맵 기능이 동작하며 운영·복구 절차가 재현 가능하다.

## 14. 진행 관리 원칙

- 구현 착수 시 단계별 작업을 이슈 또는 체크리스트로 분해하고 완료 증거를 남긴다.
- 단계 1의 실행 제한 검증을 통과하기 전에 실행 구조에 의존하는 전체 기능을 확대하지 않는다.
- 상세 규칙 변경 시 관련 API 문서·AI 지침·테스트를 함께 갱신한다.
- 화면의 테스트 플레이를 위해 별도의 축소 규칙 엔진을 만들지 않는다.
- 코드 수정 이력 기능, 동기식 공통 턴, 번개, 사용자 PC 실행 프로세스는 다시 도입하지 않는다.
- 본 문서 작성은 구현이나 배포 완료를 의미하지 않는다. 현재 모든 구현 단계는 미착수다.
