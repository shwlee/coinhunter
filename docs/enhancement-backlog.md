# 추후 고도화 작업 보관 목록

- 작성일: 2026-10-17
- 상태: 향후 범위 수립을 위한 기록. 현재 구현 대상이 아니다.
- 진행 원칙: 사용자가 고도화 범위와 착수 시점을 새로 정할 때 아래 항목을 계획에 포함한다. 일반적인 남은 작업·계속 진행 요청으로 자동 착수하지 않는다.
- 전체 목표 구조: [Markdown 설명](service-architecture-target.md), [독립 HTML 설명](service-architecture-target.html). 고도화 완료를 가정한 구조이며 미검증 실행 환경은 별도로 표시한다.

## 1. FE 웹서버·BE 서버 분리

- 사용자 결정: 작업 계획만 보관하고 실제 구현은 추후 고도화 단계에서 진행한다.
- 상세 계획: [FE 웹서버·BE 서버 분리 작업 계획](frontend-backend-separation-plan.md).
- 목적: 단일 접속 주소를 유지하면서 화면 제공과 API·경기 실행을 독립 서버 프로세스로 분리한다.
- 검토할 범위: 공통 코드, 주소·인증·프록시 정책, FE 제공 계층, 페이지·CSP, SSE·업로드, 개별 실행·빌드·통합 검증.
- 범위 재설정 시 확인: 당시 단일 컨테이너 운영 조건, 배포 네트워크·TLS, 현재 인증·저장·경기 구조와 계획의 일치 여부.
- 현재 처리: 구현 보류. 현재 서비스 완성·배포의 선행 필수 작업으로 추가하지 않는다.

## 2. 여러 알고리즘 언어 지원

- 사용자 제시 언어: C#, C++, JavaScript, Python.
- 현재 상태: JavaScript는 QuickJS 기반으로 구현되어 있다. 나머지 언어는 지원 대상으로 검토하며 실행 환경·지원 문법/라이브러리를 확정하거나 구현한 상태가 아니다.
- 진행 시점: 추후 고도화 범위 수립 시 포함한다. 지금은 조사와 항목 보관만 수행하며 런타임 설치·프로토타입·실제 기능 구현은 진행하지 않는다.
- 필수 조건: 턴별 500ms 판정, 시간 초과 시 현재 호출 중단과 이번 턴 제자리 패널티, 경기 동안 동일 프로세스·플레이어 인스턴스 유지. 결과를 버리고 계산을 계속하거나 매 턴 프로세스를 종료·재시작하는 방식은 채택하지 않는다.
- 추가 성능 요구: 사용자는 경기 중 실시간 컴파일·인터프리팅으로 게임 성능에 영향을 주는 방식을 배제하려고 한다. 코드 로드·컴파일·필수 준비는 경기 전에 끝내고 경기별·참가자별 독립 인스턴스를 유지해 함수만 반복 호출한다. 매 턴 원문 재해석과 바이트코드 인터프리터 실행은 다른 개념이며, 인터프리터 실행 자체까지 금지하는 조건이면 현재 QuickJS도 재검토 대상이다. Python의 바이트코드 사전 준비나 C#의 DLL 생성만으로 인터프리터/JIT 배제를 충족했다고 처리하지 않는다. 언어 지원 확정 전에 이 성능 조건과 500ms 중단·상태 유지 조건을 함께 검증한다.

| 언어       | 초기 기술 판단                                                                                            | 핵심 검증                                                                  |
| ---------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| JavaScript | 기존 QuickJS 실행 계층 유지                                                                               | 공통 실행 계약으로 정리한 뒤 기존 동작 회귀 검증                           |
| Python     | 인터프리터 중단과 제한된 실행 환경 후보 검토                                                              | KeyboardInterrupt 포착·무시, 긴 내장 연산, 호스트 접근, 상태 유지          |
| C++        | 제한된 WebAssembly 대상 컴파일과 제어 가능한 런타임 후보 검토                                             | 중단 후 스택·힙·플레이어 객체 일관성, 표준 라이브러리 범위, 컴파일 격리    |
| C#         | 일반 .NET 호스트만으로 요구 조건 충족을 가정하지 않음. 제어 가능한 실행기·계측·제한된 실행 환경 후보 비교 | 강제 중단과 동일 객체 재호출, catch/finally 우회, 라이브러리·런타임 호환성 |

이 표는 현재 구조와 공식 문서에 근거한 기술 판단이며 해당 게임의 실행 검증 결과가 아니다. 특히 Wasm의 호출 중단 기능이 언어 런타임의 내부 상태까지 안전하게 복구해 주는 것은 아니므로 실제 지원 확정 전에 증명해야 한다. 실행 명령 수 제한과 경과 시간 500ms는 동일한 제한이 아니다.

고도화 착수 시 다음 순서로 구체화한다.

1. 공통 실행 계약을 정의하고 현재 JavaScript 구현을 연결한다. initialize/getName/moveNext, 출력·오류·시간 초과와 상태 수명을 일치시킨다.
2. 후보 언어마다 정상 호출 → 상태 변경 → 무한 루프 중단 → 동일 PID·인스턴스의 다음 정상 호출을 검증한다. 재귀·긴 내장 연산·예외 포착·메모리 고갈·다른 플레이어의 독립 실행도 확인한다.
3. 지원할 언어 버전·표준 라이브러리·패키지·파일 형식과 금지 기능을 확정한다. Python import, C++ include, C# using 등은 언어별 허용 목록으로 정하며 JS 규칙을 그대로 복사하지 않는다.
4. 컴파일/준비 단계의 별도 시간·메모리·동시 작업 한도를 설계한다. 컴파일도 신뢰하지 않는 코드 처리로 격리하며 턴 실행 시간과 구분한다. 원문 파일·언어 메타데이터·컴파일 캐시의 보관/정리 경계를 정의한다.
5. 언어 선택·문법 강조·코드 검사·샘플·디버그 출력·저장·경기 기록·AI 프롬프트를 함께 확장한다. 원문은 계속 파일로 보관하고 기존 JS 데이터 호환성을 유지한다.

서버 측 실행 구조를 유지한다. 각 언어의 일반 개발 환경과 모든 외부 패키지를 제공하는 것을 기본 범위로 가정하지 않는다. 런타임 기본 메모리와 알고리즘 메모리를 구분해 한도를 정하고 동시 경기 부하·언어별 성능 차이와 대회 공정성 정책은 별도로 검토한다. FE/BE 분리를 선행 조건으로 두지 않는다.
