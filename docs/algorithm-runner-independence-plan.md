# 알고리즘 실행기 추상화·독립 실행·호출 비용 최적화 계획

- 작성일: 2026-11-15
- 상태: 독립 턴·500ms 중단/상태 유지의 기본 원칙 문서. BE 분리의 JS factory·독립 진행/로그 기반에 이어, 새 실행기 계획 1단계의 [공통 계약 v1](algorithm-runner-contract.md)과 [JS 기준선](runner-stage1-results.md)을 완료했다. 실제 어댑터/registry 연결과 다국어는 후속이다.
- 최신 작업 순서: 사용자 결정에 따라 [게임 엔진·언어별 실행기 10단계 계획](game-engine-language-runners-plan.md)을 생성했다. 이번 실행 영역의 실제 단계/완료 기준은 새 계획을 우선하며 이 문서는 유지할 원칙과 초기 후보 검토를 보관한다.
- 적용: 다음 BE 집중 작업은 공통 계약·JS 어댑터 정리와 언어별 기술 검증/선정이다. 문서 생성만으로 런타임 설치·정식 구현을 시작하거나 언어 지원을 확정한 것은 아니다.
- 실행 순서 연결: [BE 분리 계획](backend-separation-implementation-plan.md)의 1단계에서 공통 계약을 정의하고 4단계에서 현재 JS 생성/주입·독립 진행을 적용한다. 비용/부하와 통합 회귀는 BE 계획 9단계에서 확인하며 다른 언어 후보 구현은 후속 범위를 유지한다.
- 관련: [전체 구현 계획](implementation-plan.md), [FE/BE 분리 계획](frontend-backend-separation-plan.md), [실행·렌더링 흐름](game-execution-rendering-flow.md), [호출 비용 분석](algorithm-invocation-cost-analysis.md).

## 1. 확정된 게임 진행 규칙

게임은 알고리즘의 전략과 실제 수행 성능이 승부에 반영되어야 한다. 플레이어마다 준비된 알고리즘 인스턴스를 유지하며 다음 흐름을 독립적으로 반복한다.

```text
Ready → Computing → Acting → Ready
        알고리즘     이동 또는
        판단         대체 액션
```

1. 알고리즘 결과가 준비되면 해당 플레이어의 액션을 바로 시작한다.
2. 액션이 완료되면 같은 인스턴스에 다음 판단을 요청한다. 액션 중 다음 판단을 미리 수행하지 않는다.
3. 다른 플레이어의 계산/액션 완료를 기다리지 않고 같은 플레이어의 계산/턴은 중첩하지 않는다.
4. 빠른 계산은 액션 시작과 이후 턴의 시간상 이점으로 이어질 수 있어야 한다. 고정 대기로 이를 상쇄하지 않는다.
5. 한 턴은 알고리즘 결과와 액션까지다. -1/timeout 패널티는 이번 턴의 제자리 액션이며 다음 턴을 추가 소모하지 않는다.
6. 랜덤점프는 사용자 알고리즘을 호출하지 않고 엔진이 처리한다. 기존 액션 시간·신발·망치·효과 교체 규칙은 유지한다.
7. 게임 시작 전 전체 참가자의 초기화/준비 완료 확인은 가능하다. 게임 중 매 판단마다 전원의 결과를 기다리는 장벽은 도입하지 않는다.

바로 시작한다는 것은 엔진이 처리 가능한 시점에 불필요한 대기를 추가하지 않는다는 의미다. OS/이벤트 루프 지연이 0이라는 보장은 아니며 현재 20ms tick 등 반영 지연도 계측/최적화 대상으로 다룬다.

## 2. 호출 공정성의 범위

줄일 대상은 입력 변환·복사·프로세스 전송·런타임 경계·스케줄링/락 등 호출 인프라의 불필요한 비용과 언어별 편차다. 사용자 알고리즘의 실제 계산 시간을 동일하게 맞추지 않는다.

- 공통 판단 지연이나 최소 계산 시간을 부여하지 않는다.
- 빠른 결과를 보류해 느린 실행기와 시작 시점을 맞추지 않는다.
- 계산 시간을 제외하는 논리 시간 스케줄러나 과거 시각으로의 결과 보정을 적용하지 않는다.
- 모든 언어에 고정 비용을 추가해 상대 배율만 비슷하게 만드는 것을 해결로 간주하지 않는다.
- 같은 Task/Promise 인터페이스·managed 래퍼·IPC 프로토콜만으로 언어별 비용이 같다고 가정하지 않는다.
- 지연 주입은 실제 영향/불필요한 대기 확인에 사용한다. 다른 호출 시간에도 최종 결과를 강제로 같게 만드는 시험을 완료 기준으로 삼지 않는다.

현재 JS 직접 QuickJS/IPC 측정은 한 언어의 경로 차이에 관한 자료다. 이를 언어별 편차나 .NET 직접 호스팅의 실측으로 사용하지 않는다. 빠른 계산이 항상 높은 점수/승리를 보장한다는 뜻도 아니다.

## 3. 공통 실행 계약과 수명

| 계약        | 필요한 보장                                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------ |
| 생성/초기화 | 플레이어별 독립 상태. 코드 준비·로드·필요한 컴파일·객체 생성·initialize/getName은 시작 전에 수행                         |
| 비동기 판단 | 준비된 객체의 moveNext 호출. 엔진은 Task/Promise 계약으로 결과를 받되 실제 실행 위치는 어댑터 책임                       |
| 입력        | map/myPosition/items의 의미·값·스냅샷 시점·소유/복사 정책 통일. 한 알고리즘이 다른 플레이어/맵 상태를 변경하지 못하게 함 |
| 반환        | 정상/-1/timeout/exception/invalid-result·방향·제한된 출력/생략 수·정의된 계측값 정규화                                   |
| 500ms       | 각 사용자 호출에 적용. 대기 Task 종료나 취소 요청만으로 중단됐다고 간주하지 않음. 실제 종료/중단 확인 후 다음 호출 허용  |
| 상태 보존   | 경기 동안 같은 인스턴스/실행 호스트 유지. 시간 초과 때 재생성하지 않고 이전 필드 변경의 자동 롤백을 가정하지 않음        |
| 종료/실패   | 게임 종료 때 정리. 호스트 무응답·메모리 고갈·프로세스 장애는 정상 500ms 패널티와 구분                                    |

입력 준비와 사용자 호출의 계측 경계는 언어별로 맞춘다. 현재 QuickJS elapsedMs에는 JSON.parse/dispatch가 포함되므로 순수 함수 시간으로 완전히 분리됐다고 설명하지 않는다. 입력 변환을 계측에서 제외하더라도 실제 액션 시작까지의 총 지연은 남으므로 양쪽을 함께 기록한다. 실제 처리 순서를 소급하지 않는다.

## 4. 실행 위치의 선택 원칙

게임마다 별도 엔진 프로세스를 두는 목표와 플레이어 실행기를 엔진 안/밖 어디에 호스팅할지는 구분한다. 엔진 분리가 알고리즘 호출에 IPC를 필수로 만드는 것은 아니다.

| 후보                   | 검토할 구성                                                                             | 확인할 점                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| .NET 내부 직접 호스팅  | 공통 인터페이스 구현 객체를 플레이어별로 로드. Native/스크립트는 managed 래퍼 뒤에 배치 | 마샬링·Task 큐·런타임 락·실제 중단/같은 객체 재호출·경기 프로세스의 자원/장애 영향 |
| 참가자별 실행 프로세스 | 공통 호출 객체가 IPC로 준비된 인스턴스에 접근                                           | 언어별 전송/역직렬화·객체 구성·OS 스케줄링·중단/정리·프로세스 수                   |

두 후보의 채택은 미확정이다. .NET 직접 호스팅은 엔진/호스트의 언어 선택과 함께 검토하고 현재 Node.js 엔진에 CLR 객체를 즉시 로드할 수 있다고 가정하지 않는다. 다국어 후보 검증은 해당 작업 착수 시 수행한다.

## 5. 단계별 작업 순서

아래 표는 BE 분리 이전의 초기 순서다. 현재 JS factory/독립 진행 검증 등 구현된 부분은 새 [10단계 계획](game-engine-language-runners-plan.md)의 기반으로 사용하고, 이 표의 과거 “문서화만 완료” 표현을 현재 상태로 해석하지 않는다.

| 단계            | 작업                                                        | 산출물·완료 기준                                                                             |
| --------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 0 · 문서화      | 독립 턴·실제 계산 성능 유지·논리 시간 제안 제외             | 이번 문서와 전체 계획/체크리스트 연결. 이 단계만 완료                                        |
| 1 · 계약 정의   | 공통 실행 인터페이스·결과/오류·상태 전이·수명·계측 경계     | 플레이어별 인스턴스, 준비/판단/종료 분리, 중단 확인·비중첩 계약                              |
| 2 · JS 추상화   | Match의 직접 new PlayerProcess 결합을 생성/주입 경계로 분리 | 기존 PlayerProcess를 첫 구현으로 연결. 게임 규칙·호출/액션 순서·저장/API 호환 유지           |
| 3 · 독립 진행   | 느린/빠른 참가자의 계산·액션 독립 검증                      | 한 참가자의 미완료 Task/Promise가 다른 참가자의 계산·액션·다음 턴을 막지 않음                |
| 4 · 비용 최적화 | 변환·복사·대기·호출·응답·tick 지연의 분해 측정              | 중복 변환/복사·공통 락·불필요한 큐 최소화. 고정 대기/언어별 보정 배율 미도입                 |
| 5 · 다국어 비교 | 착수 시 같은 입력 정책의 직접 호스팅/IPC 후보 검증          | 실제 언어별 무연산·입력 읽기·동시 호출·500ms 중단/재사용 비교. 허용 호출 편차/자원 기준 확정 |
| 6 · 통합/회귀   | 선택한 실행 형태를 게임별 엔진·화면·수집 경계에 연결        | 실제 완료 순서·아이템/기믹·패널티·종료/정리 유지. 부하/장애·누수 검증                        |

1~4단계는 현재 JS 실행기/엔진 분리·추상화 작업에서 수행할 범위다. 5단계 C#/C++/Python 구현과 설치는 다국어 작업 착수 시 진행한다. 운영 BE 포팅·DB 전환·전량 로그 구현은 각각의 계획에서 수행한다. 이 계획이 모두 동시에 구현하라는 지시는 아니다.

## 6. 필수 검증 항목

- 준비 단계와 게임 중 대기 정책을 구분하고 매 판단 결과 전체를 묶는 WhenAll/Promise.all 장벽이 생기지 않는지 확인한다.
- 같은 유효 방향을 반환하되 계산 시간이 명확히 다른 실행기로 빠른 계산이 고정 대기 없이 액션으로 이어지는지 확인한다. 맵/종료 조건을 통제한 조건에서 턴 처리량을 비교한다.
- 느린/timeout 참가자가 있는 동안 다른 참가자가 턴을 진행하는지 확인한다. OS 자원 부족과 엔진의 논리적 장벽을 구분한다.
- 로드/initialize/getName 횟수·필드·PID/호스트 ID로 인스턴스 재사용을 확인한다. 매 턴 재로드·시간 초과 후 재생성을 허용하지 않는다.
- 반환/예외/중단 후 실제 호출 종료와 비중첩을 확인한다. 취소 요청만으로 busy를 풀지 않는다.
- 입력/출력 크기·호출 순서·언어/자리 교환·동시 게임 수를 바꿔 p50/p95/p99와 편차를 측정한다. tick·GC·공유 큐/락 지연을 기록한다.
- 점프 호출 생략·벽 충돌/망치·신발·-1의 이번 턴 액션·종료 직전 호출/늦은 응답을 기존 규칙과 대조한다.
- 미측정 언어를 완료 처리하지 않고 허용 지연 수치는 비교 자료/배포 자원에 근거해 확정한다.

개인정보 운영 준비의 마지막 필수 단계와 원문 파일 저장·소유권·독립 로그 수집 경계는 기존 결정을 유지한다.
